# Этап 2: Классический апскейл, режим «одно изображение»

## Цель этапа

Первый сценарий, который делает что-то полезное: нажал кнопку — картинка на странице
стала больше и чётче, и её можно скачать.

Внутри это четыре задачи, каждая со своей неожиданной сложностью:

1. **Получить пиксели** картинки. Здесь ждёт CORS — и это не мелочь, а стена,
   об которую разбивается большинство самодельных расширений.
2. **Увеличить** их так, чтобы результат выглядел лучше оригинала, а не просто больше.
3. **Вернуть результат** на страницу так, чтобы он там остался.
4. **Не подвесить** браузер пользователя на время работы.

---

## Теория

### Что вообще значит «увеличить картинку»

У картинки 100×100 есть 10 000 известных цветов. У картинки 200×200 — 40 000 точек,
и три четверти из них неизвестны. Любой алгоритм увеличения — это способ **придумать**
недостающие цвета по известным соседям. Придумать «правильно» невозможно: информации
в оригинале физически нет. Можно только придумать правдоподобно.

Методы отличаются тем, сколько соседей учитывают и с какими весами:

| Метод | Соседей по оси | Результат |
|---|---|---|
| Nearest neighbor | 1 | Крупные квадраты, «лесенка» на диагоналях |
| Bilinear | 2 | Гладко, но мыльно: мелкие детали смазываются |
| Bicubic | 4 | Резче билинейной, стандарт «по умолчанию» во многих редакторах |
| **Lanczos** (наш выбор) | 4 или 6 | Самый резкий из классических; даёт «звон» на контрастных краях |

**Почему Ланцош.** В теории обработки сигналов идеальный фильтр для изменения частоты
дискретизации — функция `sinc(x) = sin(πx)/(πx)`. Идеальный, но бесконечный: чтобы
посчитать один пиксель, нужны все остальные, включая бесконечно далёкие.

Ланцош — это практический компромисс: `sinc` умножается на такое же, но растянутое окно
`sinc(x/a)` и обрезается за пределами `|x| < a`. Параметр `a` — радиус: сколько соседей
брать с каждой стороны. `a=2` учитывает 4 пикселя по оси, `a=3` — 6.

**Что такое «звон» (ringing).** У функции `sinc` есть отрицательные участки. Значит,
некоторые соседи входят в сумму с **отрицательным** весом. На резкой границе (чёрное
рядом с белым) это даёт выброс за пределы диапазона: рядом с белым краем появляется
пиксель ярче белого, рядом с чёрным — темнее чёрного. После обрезки в 0…255 это выглядит
как тонкий светлый ореол вдоль контрастных границ.

Это не баг, а плата за резкость, и она осознанная: тот же эффект есть в ImageMagick,
Photoshop и во всех приличных просмотрщиках. Радиус 2 звонит меньше, радиус 3 — резче,
но заметнее.

### Разделимость: почему два прохода вместо одного

Двумерный фильтр в лоб выглядит так: для каждого выходного пикселя пройти по квадрату
(2a)×(2a) входных пикселей. При `a=3` это 36 умножений на пиксель на канал.

Но ядро Ланцоша **разделимо**: вес двумерного соседа равен произведению одномерных
весов по X и по Y. Значит, тот же результат получается двумя одномерными проходами:
сначала растягиваем по горизонтали, потом по вертикали. Это 2a + 2a = 12 умножений
вместо 36 — втрое дешевле, и разрыв растёт с радиусом.

```
исходник            промежуточный          результат
srcW × srcH   →     dstW × srcH      →     dstW × dstH
            горизонт.            вертик.
```

Промежуточный буфер — единственная крупная аллокация в алгоритме.

### Предрасчёт весов

Вес соседа зависит от того, **насколько он далеко от центра** выходного пикселя.
А расстояния повторяются: для всех строк изображения набор весов по горизонтали
одинаков, он зависит только от номера столбца.

Значит, веса можно посчитать один раз на ось, а не для каждого пикселя. Для картинки
1920×1080 это разница между примерно тремя тысячами вычислений синуса и двадцатью
миллионами. Синус — дорогая операция; без предрасчёта алгоритм был бы медленнее
в разы.

### Premultiplied alpha — почему это обязательно

Фильтрация смешивает соседние пиксели. У полностью прозрачного пикселя цвет формально
есть, и обычно это `(0, 0, 0)` — чёрный. Если смешивать цвета напрямую, этот чёрный
попадёт в результат везде, где рядом есть прозрачность: у логотипов и иконок с
прозрачным фоном появится тёмная кайма по контуру.

Решение — смешивать **цвет, домноженный на альфу**, и делить обратно в конце.
Тогда прозрачные пиксели вносят в сумму ровно ноль.

Ровно та же математика и та же причина были в генераторе иконок на этапе 0.
Это общее правило: **всё, что усредняет пиксели с прозрачностью, обязано работать
с premultiplied alpha.**

### Нормировка весов

Сумма весов фильтра обязана равняться единице: иначе яркость результата изменится.
В середине картинки она равняется автоматически, а у краёв — нет: там окно фильтра
вылезает за границу изображения и его приходится обрезать или сдвигать.

Если этого не исправить, по краям картинки появляется видимая рамка — светлее или
темнее середины. Лечится делением всех весов на их сумму.

### Tainted canvas — главная стена этапа

Браузер разрешает **нарисовать** на canvas любую картинку, включая чужую с другого
домена. Но как только на canvas попала картинка из другого источника, canvas помечается
«испорченным» (tainted), и любая попытка **прочитать** из него пиксели — `getImageData`,
`toBlob`, `convertToBlob` — выбрасывает `SecurityError`.

**Зачем это сделано.** Без такой защиты любой сайт мог бы вставить
`<img src="https://банк.example/выписка.png">`, нарисовать её на canvas и прочитать
пиксели. Браузер-то отправит запрос с куками пользователя и получит его личную страницу.
Это была бы кража данных через картинку.

Для нас последствие тяжёлое: **улучшить картинку мало, к её пикселям надо ещё получить
доступ**. А большинство картинок в интернете лежат на CDN, то есть на другом домене.

**Что можно сделать:**

| Способ | Как работает | Когда срабатывает |
|---|---|---|
| **`crossOrigin="anonymous"`** (наш выбор) | Загрузить картинку заново, попросив браузер сделать CORS-запрос: без кук и с проверкой заголовка `Access-Control-Allow-Origin` в ответе | Если сервер прислал заголовок. Большинство CDN присылают `*` |
| Запрос из service worker | Запросы расширения из фонового контекста не подчиняются CORS вообще | Всегда, но требует разрешения `host_permissions` — пугающего «доступ ко всем сайтам» при установке |

На этом этапе делаем первый. Второй — этап 7, вместе с остальной обработкой ошибок:
там разрешение будет добавлено осознанно и объяснено пользователю.

Как узнать, испорчен ли canvas, **заранее**? Никак — нет такого свойства ни у картинки,
ни у `ImageBitmap`. Единственный надёжный способ — попробовать прочитать. Мы пробуем
на холсте 1×1: стоимость близка к нулю, ответ точный.

### Почему `OffscreenCanvas`, а не `<canvas>`

В content script доступны оба. Но `OffscreenCanvas` существует ещё и в Web Worker,
а `HTMLCanvasElement` — нет. Написав апскейлер сразу на `OffscreenCanvas`, мы получаем
код, который на этапе 4 переезжает в Worker **без единой правки алгоритма**.

Это стоило нуля усилий сейчас и экономит переписывание потом. Тот же принцип —
причина, по которой `core/enhance/` не импортирует ничего из `chrome.*` и не трогает DOM.

### Почему `srcset` ломает подмену картинки

Современная разметка задаёт картинку несколькими способами сразу:

```html
<picture>
  <source srcset="photo.avif" type="image/avif">   <!-- приоритет выше src -->
  <img src="photo.jpg" srcset="photo@2x.jpg 2x">   <!-- srcset тоже выше src -->
</picture>
```

Браузер выбирает источник сам, по плотности экрана и размеру окна, и **пересматривает
выбор** при изменении размера окна или переносе окна на другой монитор.

Если просто присвоить `img.src`, наша картинка проживёт до первого пересмотра, а потом
молча вернётся к оригиналу. Выглядит это как «расширение поработало и сломалось».
Поэтому `srcset`, `sizes` и `<source srcset>` приходится снимать — и запоминать,
чтобы вернуть.

## Что делаем

1. Пишем ресемплер Ланцоша — чистая функция `ImageData → ImageData`, без DOM.
2. Оборачиваем его в `CanvasEnhancer`, реализующий интерфейс `ImageEnhancer` из этапа 0.
3. Пишем получение пикселей с обходом CORS через повторную загрузку.
4. Пишем подмену картинки на странице, восстановление и скачивание.
5. Учим тосты показывать ход работы и кнопки действий.
6. Связываем всё в один поток и подключаем к кнопке и контекстному меню.
7. Проверяем: сначала численно (вне браузера), потом сквозным сценарием.

## Пошаговая инструкция

### Шаг 1. Ядро и веса

```ts
function lanczosKernel(x: number, a: number): number {
  if (x === 0) return 1
  const ax = Math.abs(x)
  if (ax >= a) return 0
  const pix = Math.PI * x
  return (a * Math.sin(pix) * Math.sin(pix / a)) / (pix * pix)
}
```

> **Почему `x === 0` обрабатывается отдельно**
>
> При `x = 0` формула даёт `0/0`. Математический предел равен 1, но в коде получилось бы
> `NaN`, который затем разошёлся бы по всему изображению: одно `NaN` в сумме делает
> `NaN` весь пиксель, а после нормировки — всю строку весов.
>
> Это классическая ошибка в реализациях `sinc`: картинка получается полностью
> прозрачной или чёрной, и причина совершенно не видна по результату.

Предрасчёт весов для одной оси:

```ts
function buildWeights(srcSize: number, dstSize: number, a: number): AxisWeights {
  const scale = dstSize / srcSize
  const filterScale = scale < 1 ? 1 / scale : 1
  const support = a * filterScale
  const taps = Math.min(srcSize, Math.ceil(support * 2) + 1)
  // ...
  for (let i = 0; i < dstSize; i++) {
    const center = (i + 0.5) / scale - 0.5
    let start = Math.ceil(center - support)
    if (start < 0) start = 0
    if (start + taps > srcSize) start = Math.max(0, srcSize - taps)
    // ... веса, затем нормировка
  }
}
```

> **Откуда слагаемые 0.5 в формуле центра**
>
> Координата пикселя указывает на его **левый край**, а фильтровать нужно относительно
> **центра**. Отсюда `+0.5` при переводе номера выходного пикселя в непрерывную
> координату и `−0.5` при обратном переводе в координаты исходника.
>
> Без них результат смещается ровно на полпикселя. На одном применении это почти
> незаметно, но при повторном улучшении уже улучшенной картинки сдвиг накапливается
> и становится очевидным.
>
> Это была реальная ошибка, пойманная тестом на симметрию: вертикальная полоса
> ровно по центру после увеличения переставала быть симметричной.

> **Что делает `filterScale` и зачем он при уменьшении**
>
> При **увеличении** входных пикселей с избытком, и окно фильтра можно оставить
> обычного размера. При **уменьшении** — наоборот: между соседними выходными пикселями
> оказывается несколько входных, и если окно не растянуть, часть из них вообще не будет
> учтена. Результат — алиасинг: муар на мелких деталях, рваные тонкие линии.
>
> Мы уменьшением не занимаемся, но код поддерживает и его: это две строчки, и без них
> функция была бы корректна только в половине случаев — ловушка для того, кто
> переиспользует её позже.

> **Почему окно сдвигается внутрь картинки, а не «повторяет крайний пиксель»**
>
> У границы окно фильтра вылезает за пределы изображения. Варианты обработки:
> повторять крайний пиксель, зеркалить, считать за пределами прозрачным, сдвинуть окно.
>
> Выбран сдвиг: он не требует дополнительных ветвлений в горячем цикле и не создаёт
> искусственных данных. Ценой небольшой асимметрии окна у самого края — но после
> нормировки это не даёт видимых артефактов.
>
> Вариант «за пределами прозрачно» был бы худшим: он даёт затемнение по всему периметру.

> **Почему нормировка обязательна**
>
> ```ts
> if (sum !== 0) {
>   const inv = 1 / sum
>   for (let t = 0; t < taps; t++) weights[offset + t]! *= inv
> }
> ```
> После обрезки и сдвига окна сумма весов у краёв не равна единице. Без нормировки
> яркость по краям поплывёт, и по периметру картинки появится видимая рамка.
>
> Поймано тестом «однородная картинка после увеличения остаётся однородной» — самая
> дешёвая и самая полезная проверка для любого ресемплера.

### Шаг 2. Два прохода

```ts
const tmp = new Float32Array(dstWidth * srcHeight * 4)
// проход 1: горизонталь, с домножением на альфу
// проход 2: вертикаль, с обратным делением
```

> **Почему промежуточный буфер — `Float32Array`, а не `Uint8ClampedArray`**
>
> Обрезка в 0…255 после **первого** прохода была бы потерей информации: выбросы,
> которые второй проход мог бы скомпенсировать, оказались бы срезаны навсегда.
> Промежуточные значения обязаны храниться с запасом по диапазону.
>
> `Float32` вместо `Float64` — вдвое меньше памяти при точности, заведомо избыточной
> для 8-битных пикселей.

> **Почему нет отдельного буфера под результат в float**
>
> Первая версия использовала три буфера: premultiplied-копия исходника, промежуточный
> и выходной в float. Для 1920×1080 → 3840×2160 это 33 + 66 + 133 = 232 МБ.
>
> Убрали два: домножение на альфу делается **на лету** при чтении исходника
> в первом проходе, а деление обратно — при записи результата во втором.
> Осталось 66 МБ. Никакой потери точности при этом нет — просто операции
> переехали в циклы, которые и так есть.

> **Почему присваивание в `Uint8ClampedArray` — это часть алгоритма, а не деталь**
>
> ```ts
> outData[o] = r * inv
> ```
> `Uint8ClampedArray` сам округляет и **обрезает** значение в 0…255. Именно здесь
> гасится «звон» Ланцоша, дающий выбросы за пределы диапазона. С обычным `Uint8Array`
> вместо обрезки было бы переполнение по модулю: яркий выброс стал бы чёрным пикселем,
> и вдоль контрастных краёв появилась бы рваная тёмная линия.

### Шаг 3. `CanvasEnhancer`

```ts
export class CanvasEnhancer implements ImageEnhancer {
  readonly backend: EnhanceBackend
  constructor(private readonly level: QualityLevel) {
    this.backend = level === 'fast' ? 'canvas-bilinear' : 'canvas-lanczos'
  }
  // ...
}
```

Два пути внутри:

```ts
private scaleNative(bitmap, width, height): OffscreenCanvas {
  const ctx = context2d(new OffscreenCanvas(width, height))
  ctx.imageSmoothingEnabled = true
  ctx.imageSmoothingQuality = 'high'
  ctx.drawImage(bitmap, 0, 0, width, height)
  return canvas
}
```

> **Зачем нужен быстрый путь, если есть качественный**
>
> `drawImage` со сглаживанием реализован в нативном коде браузера и обычно использует
> GPU. Он в десятки раз быстрее нашего JS-фильтра и не занимает главный поток
> сколько-нибудь заметно.
>
> Качество ниже: Chrome применяет билинейную фильтрацию по заранее уменьшенным копиям,
> результат мягкий. Но на слабой машине или для очень большой картинки это единственный
> вариант, не превращающий страницу в слайд-шоу.
>
> На этапе 6 пользователь получит этот выбор явно, под именем «быстро».

```ts
const sourceCtx = context2d(source, /* willReadFrequently */ true)
```

> **Что даёт `willReadFrequently: true`**
>
> Это подсказка браузеру держать буфер холста в оперативной памяти, а не в видеопамяти.
> Без неё `getImageData` вызывает копирование с GPU в ОЗУ — операцию, которая на больших
> холстах стоит десятки миллисекунд и вдобавок синхронизирует конвейер рендеринга.
>
> Ставим только на **исходном** холсте, откуда действительно читаем. На выходном
> холсте, куда только пишем и который затем кодируем, подсказка была бы вредна.

### Шаг 4. Получение пикселей и CORS

```ts
function isReadable(bitmap: ImageBitmap): boolean {
  const canvas = new OffscreenCanvas(1, 1)
  const ctx = canvas.getContext('2d', { willReadFrequently: true })
  if (!ctx) return false
  ctx.drawImage(bitmap, 0, 0, 1, 1)
  try {
    ctx.getImageData(0, 0, 1, 1)
    return true
  } catch {
    return false
  }
}
```

> **Почему проверка через попытку, а не через свойство**
>
> Свойства «испорчен ли будет canvas» не существует ни у `HTMLImageElement`,
> ни у `ImageBitmap`. Догадаться по URL нельзя: тот же домен ещё не гарантирует
> отсутствия перенаправления на CDN, а чужой домен — наличия CORS-заголовков.
>
> Холст 1×1 делает проверку почти бесплатной, а ответ — точным.

Порядок попыток:

```ts
let bitmap = await createImageBitmap(image)   // 1. уже загруженная картинка, без сети
if (isReadable(bitmap)) return bitmap

bitmap.close()                                 // 2. пробуем CORS-перезагрузку
const corsImage = await loadWithCors(url)
const corsBitmap = await createImageBitmap(corsImage)
if (!isReadable(corsBitmap)) { corsBitmap.close(); throw new ImageSourceError('tainted', ...) }
return corsBitmap
```

> **Почему сначала пробуем уже загруженную картинку**
>
> Она уже в памяти браузера. `createImageBitmap` из неё не идёт в сеть вообще —
> это самый дешёвый путь, и для картинок с того же домена он сразу срабатывает.
>
> Идти в сеть сразу было бы расточительно: лишний запрос на каждое действие
> пользователя, даже когда он не нужен.

> **Почему `crossOrigin = 'anonymous'`, а не `'use-credentials'`**
>
> `anonymous` отправляет запрос **без кук** и требует от сервера заголовок
> `Access-Control-Allow-Origin`. Большинство CDN отдают `*`, и это срабатывает.
>
> `use-credentials` отправил бы куки — но тогда сервер обязан ответить конкретным
> origin вместо `*`, чего почти никто не делает. То есть вариант с куками работал бы
> **реже**, а не чаще.

> **Почему `src` присваивается после обработчиков**
>
> ```ts
> probe.onload = () => { ... }
> probe.onerror = () => { ... }
> probe.src = url          // ← последним
> ```
> Если картинка есть в кеше, `onload` может сработать синхронно прямо при присваивании
> `src`. Обработчик, назначенный после, её уже не увидит, и промис никогда
> не разрешится.

> **Откуда таймаут 10 секунд**
>
> Картинка уже показана на странице, значит она либо в кеше, либо точно доступна.
> Повторный запрос обычно укладывается в доли секунды. 10 секунд — потолок на случай
> медленной сети, после которого честнее показать ошибку, чем оставить пользователя
> в неведении.
>
> Без таймаута висящий запрос заблокировал бы обработку навсегда: `onerror`
> при обрыве соединения срабатывает не всегда.

### Шаг 5. Возврат результата на страницу

```ts
const parent = image.parentElement
if (parent instanceof HTMLPictureElement) {
  for (const source of parent.querySelectorAll('source')) {
    pictureSources.push({ element: source, srcset: source.getAttribute('srcset') })
    source.removeAttribute('srcset')
  }
}
image.removeAttribute('srcset')
image.removeAttribute('sizes')
image.src = objectUrl
```

> **Почему одного `img.src` мало — и как это выглядит при ошибке**
>
> `srcset` у `<img>` и `<source srcset>` внутри `<picture>` имеют приоритет **выше**,
> чем `src`. Браузер пересматривает выбор при изменении размера окна.
>
> Симптом при неполной реализации: картинка меняется, а через некоторое время —
> или сразу при изменении окна — возвращается к оригиналу. Пользователь видит,
> что расширение «отработало и откатилось».
>
> Проверено на стенде: после подмены и события `resize` картинка остаётся результатом
> обработки.

```ts
const originals = new WeakMap<HTMLImageElement, OriginalState>()
```

> **Почему `WeakMap`, а не `Map`**
>
> Ключ — DOM-элемент. Обычный `Map` держал бы сильную ссылку на картинку и после её
> удаления со страницы. На бесконечной ленте, где элементы уничтожаются пачками,
> это утечка, растущая без предела: и сам элемент, и сохранённое состояние,
> и объектный URL с многомегабайтным Blob.
>
> `WeakMap` не мешает сборщику мусора: исчезла картинка — исчезла запись.

> **Почему `revokeObjectURL` — не формальность**
>
> `URL.createObjectURL(blob)` регистрирует ссылку, которая держит Blob в памяти
> **до явного освобождения**. Апскейл 4К весит десятки мегабайт. Забыть
> `revokeObjectURL` — значит дарить вкладке утечку размером с картинку на каждое
> действие пользователя.
>
> Отсюда же освобождение старого URL при повторном улучшении той же картинки.

```ts
link.click()
setTimeout(() => URL.revokeObjectURL(url), 10_000)
```

> **Почему нельзя освободить URL сразу после `click()`**
>
> `click()` только запускает скачивание, а не дожидается его. Освободив URL немедленно,
> получим скачивание пустого или битого файла.
>
> 10 секунд — с запасом достаточно, чтобы браузер успел забрать данные, и достаточно
> мало, чтобы память не висела до закрытия вкладки.

> **Почему `<a download>`, а не `chrome.downloads`**
>
> API расширения потребовало бы разрешения `downloads`, которое показывает пользователю
> отдельное предупреждение при установке. Ради сохранения файла, которое браузер умеет
> сам, это неоправданно.
>
> `chrome.downloads` станет нужен, когда понадобится сохранять пачку файлов в папку
> без диалога на каждый — то есть в режиме «вся страница», если он будет уметь
> массовое скачивание.

### Шаг 6. Не подвесить страницу

```ts
const PAINT_FALLBACK_MS = 50

function yieldUntilPainted(): Promise<void> {
  return new Promise((resolve) => {
    let settled = false
    const finish = () => { if (!settled) { settled = true; resolve() } }
    requestAnimationFrame(() => setTimeout(finish, 0))
    setTimeout(finish, PAINT_FALLBACK_MS)
  })
}
```

> **Зачем вообще отдавать кадр перед вычислениями**
>
> Мы показываем тост «Обрабатываю…» и тут же занимаем главный поток на сотни
> миллисекунд. Браузер рисует только **между** задачами — то есть тост не появится
> до самого конца работы. Пользователь увидит зависшую страницу без объяснений
> и решит, что расширение сломалось.
>
> `requestAnimationFrame` срабатывает **перед** отрисовкой, поэтому одного его мало;
> пара «rAF, затем `setTimeout`» возвращает управление уже после того, как кадр показан.

> **Почему страховочный таймер обязателен — и что было без него**
>
> В **невидимой** вкладке браузер не рисует кадры, и `requestAnimationFrame`
> не вызывается вовсе. Ожидание внутри него не закончилось бы никогда.
>
> Это не теория. На стенде обработка вставала намертво на «Обрабатываю…»: тост
> появлялся, картинка не менялась, ошибок не было. Реальный сценарий — пользователь
> нажал кнопку и переключил вкладку.
>
> Тот же класс ошибки был найден на этапе 1 в тостах. Общее правило:
> **`requestAnimationFrame` — не таймер, и полагаться на его срабатывание нельзя.**

### Шаг 7. Сколько увеличивать

```ts
export function resolveScale(displayWidth, naturalWidth, pixelRatio): number {
  if (naturalWidth <= 0) return MIN_SCALE
  const needed = (displayWidth * pixelRatio) / naturalWidth
  return Math.min(MAX_SCALE, Math.max(MIN_SCALE, Math.ceil(needed * 2) / 2))
}
```

> **Почему не просто «всегда в два раза»**
>
> Неочевидная вещь: если картинка показана в её собственном размере на обычном экране,
> увеличенную копию браузер тут же ужмёт обратно под тот же CSS-размер, и пользователь
> **не увидит ничего**. Расширение отработает, потратит время и память, а результата
> не будет.
>
> Видимый выигрыш есть там, где картинке не хватает пикселей:
> - её растянули стилями (`displayWidth` больше `naturalWidth`) — она мыльная;
> - экран HiDPI (`devicePixelRatio` 2 и выше) — на каждый CSS-пиксель нужно вдвое
>   больше настоящих.
>
> Поэтому коэффициент считается от реальной нехватки. Округление до половин
> (`Math.ceil(needed * 2) / 2`) — чтобы не плодить размеры вроде ×2.37, от которых
> ни пользы, ни понятности.

> **Откуда границы 2 и 4**
>
> Ниже 2 пользователь просто не заметит разницы — а он нажал кнопку и ждёт результата.
> Выше 4 классическая интерполяция уже не даёт полезной детализации: она умеет только
> сглаживать имеющееся, а не придумывать новое. Растянутая в 8 раз картинка будет
> большой и одинаково мыльной. Придумывать детали — задача ML-модели с этапа 5.

> **Откуда потолок 24 мегапикселя**
>
> ```ts
> const MAX_OUTPUT_PIXELS = 24_000_000
> ```
> Ограничение по памяти, а не по эстетике. На каждый выходной пиксель нужно 4 байта
> `ImageData` плюс 16 байт промежуточного `Float32`-буфера, плюс сопоставимый объём
> под PNG в худшем случае. 24 Мп — это порядка 600 МБ пиковой памяти вкладки; выше
> начинается риск, что вкладку убьёт сам браузер.
>
> Коэффициент при упоре в потолок **снижается**, а не отбрасывается: лучше увеличить
> в 1.4 раза, чем отказать.

## Код и разбор кода

Полные тексты — в репозитории. Здесь то, что не читается с первого взгляда.

### Горячий цикл первого прохода

```ts
for (let t = 0; t < hx.taps; t++) {
  const w = hx.weights[wOffset + t]!
  if (w === 0) continue
  const p = srcRow + (start + t) * 4
  const alpha = srcData[p + 3]! / 255
  const wa = w * alpha
  r += srcData[p]! * wa
  g += srcData[p + 1]! * wa
  b += srcData[p + 2]! * wa
  alphaSum += wa
}
```

Три вещи здесь неслучайны:

- **`if (w === 0) continue`** — у краёв изображения часть весов нулевая (окно `taps`
  фиксированной длины, а реальных соседей меньше). Пропуск экономит четыре умножения.
- **`const wa = w * alpha`** — домножение на альфу вынесено из трёх строк в одну.
  Внутренний цикл выполняется десятки миллионов раз, и лишнее умножение там стоит
  реального времени.
- **Восклицательные знаки** — следствие `noUncheckedIndexedAccess` из этапа 0.
  Опция считает `array[i]` типом `number | undefined`. В горячих циклах это визуальный
  шум, но отключать её ради одного файла хуже: она уже поймала пару ошибок индексации.

### Освобождение `ImageBitmap`

```ts
} finally {
  bitmap?.close()
  inFlight.delete(image)
}
```

> **Зачем звать `close()`, если есть сборщик мусора**
>
> `ImageBitmap` хранит несжатые пиксели **вне кучи JavaScript**. Сборщик мусора видит
> маленький объект-обёртку и не спешит его собирать — а за обёрткой стоит, например,
> 48 МБ для картинки 4000×3000.
>
> `close()` освобождает память немедленно. Без него после десятка улучшений вкладка
> распухает на сотни мегабайт, и связать это с расширением по симптомам почти
> невозможно.

### Защита от двойного клика

```ts
const inFlight = new WeakSet<HTMLImageElement>()
```

> Пользователь легко нажимает кнопку дважды: первое нажатие визуально ничего
> не меняет несколько сотен миллисекунд. Без защиты запустились бы две обработки
> одной картинки — двойной расход памяти и гонка за то, чей результат встанет
> на страницу.
>
> `WeakSet` по той же причине, что и `WeakMap` выше: ключ — DOM-элемент.

## Проверка

### Численная проверка ресемплера

Алгоритм — чистая функция без DOM, поэтому его можно проверить вне браузера.
Node 24 исполняет TypeScript напрямую, а `ImageData` подменяется десятью строками:

```ts
class FakeImageData {
  constructor(w, h) { this.width = w; this.height = h; this.data = new Uint8ClampedArray(w*h*4) }
}
globalThis.ImageData = FakeImageData
const { resampleLanczos } = await import('file:///.../src/core/enhance/lanczos.ts')
```

Что проверялось и что это ловит:

| Проверка | Что поймает |
|---|---|
| Однородная картинка 50×50 → 100×100 остаётся однородной | Ошибку нормировки весов (рамка по краям) |
| Симметричная полоса остаётся симметричной | Сдвиг на полпикселя (пропущенные `±0.5`) |
| Красный рядом с прозрачным чёрным не темнеет | Отсутствие premultiplied alpha (тёмная кайма) |
| Размеры результата | Ошибки округления |
| Уменьшение 200×200 → 50×50 сохраняет яркость | Отсутствие растяжения окна при downscale |
| Ширина переходной зоны на ступеньке | Потерю резкости |

Результат: все проверки пройдены при обоих радиусах, максимальное отклонение
на однородной картинке — 0, асимметрия — 0, минимальный красный там, где видно, — 255,
ширина перехода — 2 px.

Замеренная стоимость фильтра:

```
исходник      -> результат       a=2      a=3
640×480       -> 1280×960        46 мс    53 мс
960×540       -> 1920×1080       66 мс    85 мс
1280×960      -> 2560×1920      166 мс   200 мс
1920×1080     -> 3840×2160      253 мс   325 мс
3000×2000     -> 4472×2981      443 мс   578 мс
```

Это и есть время, на которое замирает страница. Терпимо для одной картинки,
неприемлемо для очереди — отсюда этап 4.

### Сквозная проверка

Дальше — стенд из этапа 1, дополненный генератором тестовых картинок и двумя
источниками: `localhost` и `127.0.0.1` (для браузера это **разные** origin,
что позволяет проверить CORS без внешних сайтов).

Проверено:

| Сценарий | Результат |
|---|---|
| Картинка 240×180, растянутая до 480 px | Стала 480×360, `src` — `blob:` |
| Картинка с прозрачностью 300×300 | Стала 600×600 |
| Кросс-домен **без** `Access-Control-Allow-Origin` | Картинка не тронута, тост «Сайт не разрешает читать эту картинку. Обход появится на этапе 7» |
| Кросс-домен **с** `Access-Control-Allow-Origin: *` | Сработала перезагрузка с `crossOrigin`, картинка стала 400×400 |
| `<picture>` + `srcset` | Оба атрибута сняты; после события `resize` подмена держится |
| Кнопка «Вернуть» | `src`, `srcset` и `<source srcset>` восстановлены, `naturalWidth` вернулся к 200 |
| Двойной клик | Второй запрос отклонён: «Эта картинка уже обрабатывается» |

Отдельно выяснилось, что **замеры времени на стенде недостоверны**: `convertToBlob`
занимал ровно ~1015 мс независимо от размера холста (480×360, 1200×900 и 2400×1800 —
все около 1015–1060 мс). Это артефакт среды без композитинга, а не стоимость
кодирования. Поэтому цифры выше получены вне браузера.

9. **Контекстное меню.** Правый клик по картинке → «Улучшить это изображение».

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Картинка целиком прозрачная или чёрная после обработки | В ядре не обработан случай `x = 0`, `NaN` разошёлся по весам | Возвращать 1 при `x === 0` |
| По периметру результата видна рамка светлее/темнее | Веса не нормированы; у краёв их сумма ≠ 1 | Делить веса на их сумму |
| Тёмная кайма вокруг прозрачных областей | Фильтрация без premultiplied alpha | Домножать цвет на альфу перед смешиванием, делить обратно после |
| Картинка «ползёт» при повторном улучшении | Пропущены `±0.5` в расчёте центра | `center = (i + 0.5) / scale - 0.5` |
| Рваная тёмная линия вдоль контрастных краёв | Результат пишется в `Uint8Array` вместо `Uint8ClampedArray`: переполнение по модулю вместо обрезки | Только `Uint8ClampedArray` |
| Муар на мелких деталях при уменьшении | Окно фильтра не растянуто при downscale | `filterScale = 1 / scale` при `scale < 1` |
| `SecurityError` в консоли при обработке | Картинка с чужого домена, canvas испорчен | Проверять читаемость до вызова апскейлера; повторная загрузка с `crossOrigin` |
| Картинка подменилась и через секунду вернулась | Не сняты `srcset` / `<source srcset>` | Снимать оба, сохранив для восстановления |
| Тост «Обрабатываю…» висит вечно | Ожидание построено на `requestAnimationFrame`, вкладка невидима | Обязательный страховочный `setTimeout` |
| Страница ощутимо тормозит после нескольких улучшений | Не вызывается `bitmap.close()` и/или `revokeObjectURL` | Освобождать и то, и другое явно |
| «Картинка слишком большая для обработки» | `RangeError` при выделении буферов | Ожидаемо на очень больших изображениях; потолок 24 Мп снижает коэффициент, но память может кончиться и раньше |
| Результат весит десятки мегабайт | PNG без потерь на фотографии | Ожидаемо; выбор формата — этап 6 |
| Визуально ничего не изменилось | Картинка показана в собственном размере на экране 1× — браузер ужал результат обратно | Не ошибка; смысл имеет «Скачать» |
| «Эта картинка уже обрабатывается» | Второй клик до завершения первого | Ожидаемо |

| `src/core/enhance/lanczos.ts` | Ресемплер. Чистая функция `ImageData → ImageData`, без DOM и chrome API |
| `src/core/enhance/canvas-enhancer.ts` | Реализация `ImageEnhancer` поверх `OffscreenCanvas`. Два пути: нативный и Ланцош |
| `src/core/enhance/index.ts` | Точка выбора реализации и расчёт коэффициента увеличения |
| `src/content/image-source.ts` | Получение читаемых пикселей, обход CORS через повторную загрузку |
| `src/content/apply-result.ts` | Подмена картинки, восстановление, скачивание |
| `src/content/enhance-flow.ts` | Оркестрация: одна точка для кнопки и контекстного меню |

Интерфейс `ImageEnhancer`, заведённый пустым на этапе 0, впервые получил реализацию —
и не потребовал изменений. Это и было проверкой того, что контракт спроектирован верно.

### Новые API

`OffscreenCanvas`, `createImageBitmap`, `ImageBitmap.close`, `getImageData`,
`putImageData`, `convertToBlob`, `URL.createObjectURL` / `revokeObjectURL`,
`HTMLImageElement.crossOrigin`, `WeakMap`, `WeakSet`, `Float32Array`, `Uint8ClampedArray`.

### Новых разрешений нет

Скачивание сделано через `<a download>`, обход CORS — через повторную загрузку
силами страницы. Ни `downloads`, ни `host_permissions` пока не потребовались.

### Что заложено под видео

Без изменений: `<video>` находится и считается, UI для них не рендерится.
Косвенно этап полезен и для видео: ресемплер работает с `ImageData`, то есть
с одним кадром, и в будущем видео-пайплайне он же будет обрабатывать кадры —
переписывать его не придётся.

### Что будет дальше

**Этап 3 — режим «вся страница».** Очередь обработки всех подходящих картинок,
ограничение параллелизма, прогресс и отмена.

Там сразу станет больно от того, что вычисления идут в главном потоке: 250 мс на
картинку терпимо, а двадцать картинок подряд — это пять секунд полностью замершей
страницы. Этап 3 покажет проблему в полный рост, этап 4 её решит переносом в Worker.
