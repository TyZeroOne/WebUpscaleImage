# Этап 9: Полировка и упаковка

## Цель этапа

Превратить работающий код в расширение, которое можно отдать постороннему человеку.

Это другая задача, чем предыдущие восемь. Там мы отвечали на вопрос «работает ли»,
здесь — на вопрос «можно ли это опубликовать». Разница в мелочах, которых много:
язык интерфейса, читаемость иконки в панели браузера, отсутствие следов разработки
в пакете, объяснение запрошенных разрешений, и проверки, которые не дадут выложить
сломанную сборку.

---

## Теория

### Локализация в расширениях: `chrome.i18n`

Chrome предлагает встроенный механизм. Строки лежат в `_locales/<язык>/messages.json`,
а браузер сам выбирает нужный файл по языку интерфейса пользователя.

```
_locales/
  ru/messages.json
  en/messages.json
```

Формат одного сообщения:

```json
"toastDone": {
  "message": "Готово: $SIZE$, $MB$ МБ, $MS$ мс.",
  "placeholders": {
    "size": { "content": "$1", "example": "3840×2160" },
    "mb":   { "content": "$2", "example": "4.2" },
    "ms":   { "content": "$3", "example": "253" }
  }
}
```

`$SIZE$` в тексте — именованная подстановка, `content: "$1"` связывает её
с первым аргументом вызова. Именованность важна: в разных языках порядок слов
разный, и `$MB$ МБ` может оказаться в начале строки.

**Где строки подставляются автоматически, а где нет:**

| Место | Как |
|---|---|
| `manifest.json` | Запись `__MSG_extName__` — Chrome подставляет сам |
| Код | `chrome.i18n.getMessage('key', [подстановки])` |
| HTML-страницы расширения | **Никак.** Только скриптом |

Последняя строка — источник постоянного недоумения. В HTML нет ничего похожего
на `__MSG_key__`: страницы расширения это обычные документы, и текст в них
подставляет ваш собственный код.

**Главная ловушка `chrome.i18n`:** на неизвестный ключ он возвращает **пустую
строку**, а не ошибку. Опечатка приводит к исчезнувшей надписи, и связать
пустое место с опечаткой в ключе тяжело.

### Почему локали расходятся молча

Добавили строку, дописали её в русский файл, про английский забыли. Ничего
не сломается: сборка пройдёт, типы сойдутся, тесты (если бы они были) не заметят.
У пользователя с английским интерфейсом просто исчезнет надпись.

Такие ошибки ловятся только проверкой при сборке — сравнением наборов ключей.
То же с плейсхолдерами: `$SIZE$` в тексте без объявления Chrome оставит
в строке **как есть**, и пользователь увидит «Готово: $SIZE$, 4.2 МБ».

### Почему иконка должна зависеть от размера

Расширение поставляет иконки нескольких размеров: 16, 32, 48, 128. Соблазн —
нарисовать одну и отмасштабировать. Так делать нельзя, и причина арифметическая.

Иконка 16×16 — это шестнадцать пикселей на всю картинку. Деталь толщиной 8%
от высоты превращается в ней в **1.3 пикселя**. После сглаживания получается
серая полоска: не читается как линия, но делает изображение грязным.

Поэтому маленькие размеры рисуют упрощённо: меньше деталей, толще линии,
меньше скругления. Это стандартная практика, и её отсутствие — главная причина,
по которой самодельные иконки выглядят мыльными в панели браузера, хотя
в большом размере смотрелись отлично.

### Что проверять перед публикацией

Магазин проверит формальности — манифест, размер, запрещённые API. Он **не**
проверит:

- что все файлы, на которые ссылается манифест, действительно в пакете;
- что локали согласованы;
- что в пакете не осталось следов разработки;
- что версия в манифесте совпадает с версией в проекте.

Первое приводит к расширению, которое не загружается; остальные — к тихим
дефектам у части пользователей. Всё это дешевле проверить скриптом, чем
обнаружить после публикации: обновление в магазине проходит модерацию,
и цикл исправления занимает дни.

### Формат ZIP в минимальном виде

Магазин принимает zip. Готовый архиватор в зависимости тащить не хочется, а формат
в простейшем варианте — три структуры:

```
[локальный заголовок + имя + сжатые данные]  ← для каждого файла
[локальный заголовок + имя + сжатые данные]
...
[запись каталога][запись каталога]...        ← центральный каталог
[конец каталога]                             ← где каталог начинается
```

Читается архив **с конца**: последняя структура говорит, где искать каталог,
каталог перечисляет файлы и смещения. Именно поэтому zip можно дописывать
и читать, не разжимая целиком.

Сжатие — deflate, он есть в стандартной библиотеке Node. Контрольная сумма —
CRC32, тот же алгоритм, что уже писался для PNG на этапе 0.

## Что делаем

1. Выносим все строки в `_locales/`, пишем обёртку и заполнение разметки.
2. Делаем глиф иконки зависящим от размера.
3. Пишем упаковщик: проверки плюс zip.
4. Решаем судьбу плашки над видео.
5. Пишем политику конфиденциальности.
6. Ставим версию 1.0.0 и собираем пакет.

## Пошаговая инструкция

### Шаг 1. Обёртка над `chrome.i18n`

```ts
export function t(key: string, ...substitutions: (string | number)[]): string {
  const message = chrome.i18n?.getMessage(key, substitutions.map(String))
  return message || key
}
```

> **Почему возвращается ключ, а не пустая строка**
>
> `getMessage` на неизвестный ключ отвечает пустой строкой. В интерфейсе это
> выглядит как исчезнувшая надпись, и понять, что дело в опечатке, тяжело:
> пустое место одинаково похоже на «забыли перевести», «сломалась вёрстка»
> и «не сработала логика».
>
> Ключ в интерфейсе некрасив, но диагностичен: видно `popupQuality` — знаешь,
> где искать.

> **Зачем `chrome.i18n?.`**
>
> В тестовом стенде и в воркерах объекта может не быть. Опциональная цепочка
> превращает падение в возврат ключа.

```ts
export function applyI18n(root: ParentNode = document): void {
  for (const node of root.querySelectorAll<HTMLElement>('[data-i18n]')) {
    const key = node.dataset.i18n
    if (key) node.textContent = t(key)
  }
  // ... и отдельно атрибуты через data-i18n-attr
}
```

> **Почему для HTML нужен отдельный механизм**
>
> В `manifest.json` работает запись `__MSG_key__` — Chrome подставляет значения
> сам. В HTML-страницах расширения ничего подобного нет: это обычные документы,
> и текст в них подставляет ваш код.
>
> Атрибут `data-i18n` выбран вместо, например, поиска по `id`, потому что
> он самодокументирующий: открыв разметку, сразу видно, какие строки
> локализуются и какими ключами.

### Шаг 2. Локализованные строки — это данные

Было:

```ts
button.innerHTML = `${ICON_SVG}<span class="label">Улучшить</span>`
```

Стало:

```ts
button.innerHTML = ICON_SVG
const label = document.createElement('span')
label.className = 'label'
label.textContent = t('overlayEnhance')
button.append(label)
```

> **Почему это не придирка**
>
> Со статическим русским текстом разницы не было. Но строка из `messages.json` —
> **данные**, а не код: файл редактируют переводчики, его может прислать
> сторонний контрибьютор.
>
> `innerHTML` разбирает содержимое как разметку. Строка перевода с угловой
> скобкой — уже потенциальная инъекция в наш собственный shadow root.
> Правило простое: `innerHTML` только для собственных констант,
> всё остальное — `textContent`.

### Шаг 3. Иконка, зависящая от размера

```js
function render(size) {
  // Ниже 32 px мелкие детали не выживают — рисуем упрощённый глиф.
  const detailed = size >= 32
  // ...
}

function insideGlyph(x, y, detailed) {
  if (detailed) {
    if (x >= 0.26 && x <= 0.74 && y >= 0.78 && y <= 0.86) return true  // опорная линия
    // ... стрелка обычной толщины
  }
  // упрощённо: только стрелка, крупнее и толще
  if (x >= 0.40 && x <= 0.60 && y >= 0.42 && y <= 0.80) return true
  // ...
}
```

> **Откуда порог 32**
>
> Опорная линия занимает 8% высоты. На 48 px это 3.8 пикселя — читается.
> На 32 px — 2.5, ещё различимо. На 16 px — 1.3, то есть после сглаживания
> серая полоска непонятного назначения.
>
> Порог поставлен между 32 и 16, где линия перестаёт быть линией.

> **Почему меняется и радиус скругления**
>
> ```js
> insideRoundedRect(x, y, detailed ? 0.22 : 0.18)
> ```
> Радиус 0.22 на 16 px — это 3.5 пикселя от каждого угла: иконка начинает
> выглядеть круглой, а не квадратной со скруглениями, и теряет узнаваемость
> рядом с другими иконками в панели.

### Шаг 4. Упаковщик: сначала проверки

```js
if (manifest.version !== pkg.version) {
  fail(`Версии разошлись: manifest ${manifest.version}, package.json ${pkg.version}`)
}
```

> **Почему версия проверяется, а не берётся из одного места**
>
> Взять её из одного места было бы правильнее, но манифест статический
> (он лежит в `public/` и копируется как есть), а генерировать его при сборке —
> отдельное усложнение, которое на этапе 0 решили отложить.
>
> Проверка закрывает конкретный риск: выложить сборку, номер которой
> ни с чем не совпадает, и потом не понять, что именно у пользователя стоит.

```js
const localeKeys = new Map()
for (const locale of localeDirs) { /* ... собираем множества ключей ... */ }
// затем сравниваем в обе стороны
```

> **Почему сравнение в обе стороны**
>
> Пропущенный ключ в английском — исчезнувшая надпись у англоязычного
> пользователя. Лишний ключ в английском — мёртвая строка, которая, скорее всего,
> означает, что её забыли удалить из русского при рефакторинге, и где-то остался
> вызов с несуществующим ключом.

```js
const used = new Set([...String(entry.message).matchAll(/\$([A-Z0-9_]+)\$/g)].map((m) => m[1]))
const declared = new Set(Object.keys(entry.placeholders ?? {}).map((n) => n.toUpperCase()))
```

> **Зачем проверять плейсхолдеры отдельно от ключей**
>
> Ключи могут совпадать полностью, а строка при этом быть сломанной. Chrome
> расхождение **игнорирует**: незнакомый `$NAME$` остаётся в тексте как есть.
> Пользователь увидит «Готово: $SIZE$, 4.2 МБ, 253 мс».
>
> Заметить это можно только глазами и только на том языке, где ошибка.
> Регулярное выражение находит её за миллисекунду.

```js
if (files.includes('dev-build-id')) fail('В пакете остался dev-build-id')
for (const file of files) if (file.endsWith('.map')) fail(`В пакете остался sourcemap: ${file}`)
```

> **Что именно этим ловится**
>
> `dev-build-id` появляется только в dev-сборке (этап 0), sourcemap — тоже.
> Их наличие означает, что упаковали не то: в магазин уехала бы сборка
> с неминифицированным кодом, работающим опросом файла и полными исходниками
> внутри.

### Шаг 5. Zip своими руками

```js
const local = Buffer.alloc(30)
local.writeUInt32LE(0x04034b50, 0)   // сигнатура локального заголовка
local.writeUInt16LE(8, 8)            // метод сжатия: deflate
local.writeUInt32LE(crc, 14)
local.writeUInt32LE(compressed.length, 18)
local.writeUInt32LE(content.length, 22)
```

Три структуры, о которых говорилось в теории: локальный заголовок перед каждым
файлом, запись центрального каталога на каждый файл, и конец каталога.
Всё — little-endian, отсюда `writeUInt32LE`.

> **Почему `deflateRawSync`, а не `deflateSync`**
>
> `deflateSync` добавляет заголовок zlib (два байта в начале и контрольную сумму
> в конце). В zip хранится **голый** поток deflate. С обычным `deflateSync`
> архив создастся, но ни один архиватор его не откроет — и понять почему,
> глядя на «файл повреждён», непросто.

```js
const DOS_TIME = 0
const DOS_DATE = ((2020 - 1980) << 9) | (1 << 5) | 1
```

> **Почему фиксированная дата, а не текущая**
>
> Даёт **воспроизводимую сборку**: два запуска на одном коде дают побайтово
> одинаковый архив. Это позволяет проверить, что выложенное собрано из этих
> исходников, и не создаёт бессмысленных различий при сравнении версий.
>
> Формат DOS: год отсчитывается от 1980 и занимает 7 бит, месяц — 4, день — 5.
> Отсюда сдвиги.

### Шаг 6. Судьба плашки над видео

```ts
export function videoBadgeMode(): VideoBadgeMode {
  return VIDEO_ENHANCEMENT_ENABLED ? 'interactive' : 'hidden'
}
```

> **Почему решение изменилось по сравнению с этапом 8**
>
> На этапе 8 плашка рендерилась с пометкой «скоро». Для разработки это было
> правильно: позиционирование, хит-тест сквозь слой управления плеера
> и поведение при прокрутке проверены на живом элементе, и будущему этапу
> остаётся только логика.
>
> Но в расширении, которое устанавливает посторонний человек, «скоро» — это
> обещание без срока. Пользователь либо ждёт напрасно, либо решает, что
> расширение недоделано. Ни то, ни другое не стоит выигрыша от того, что
> кто-то заранее узнает о планах.
>
> Код плашки остаётся и продолжает собираться. Вернуть её — одно значение здесь.

### Шаг 7. Политика конфиденциальности

Магазин требует её для расширений с широкими разрешениями. Но написать её стоит
не поэтому, а потому, что разрешение «доступ ко всем сайтам» звучит пугающе,
и пользователь имеет право знать, для чего именно оно.

Полезная политика отвечает на три вопроса: что происходит с данными, зачем
каждое разрешение, что сохраняется. Текст — в `docs/PRIVACY.md`, короткая
версия — прямо на странице настроек.

## Проверка

### Локализация

На стенде заглушка `chrome.i18n` читает русские сообщения и выполняет подстановку
именованных плейсхолдеров — то же, что делает Chrome.

| Что | Результат |
|---|---|
| Подпись кнопки | «Улучшить» |
| `aria-label` кнопки | «Улучшить это изображение» |
| Тост о готовности | «Готово: 480×360, 0.1 МБ, 8 мс.» — все три подстановки на месте |
| Кнопки в тосте | «Скачать», «Вернуть» |
| Заголовок панели | «Улучшаю изображения» |
| Счётчик панели | «12 из 14» |
| Кнопки панели | «Отмена», «Вернуть все», «Закрыть» |

Английские сообщения проверены структурно: совпадение набора ключей
и согласованность плейсхолдеров подтверждены упаковщиком.

### Негативные тесты упаковщика

Проверка бесполезна, если не убедиться, что она умеет падать.

| Что сломали | Результат |
|---|---|
| Удалили ключ `actionDownload` из `en` | `ОШИБКА: В локали en нет ключа "actionDownload"`, код возврата 1 |
| Добавили BOM в `messages.json` | Файл разобран, выдана та же осмысленная ошибка вместо падения |

Второй случай возник не по плану: BOM добавил PowerShell при подготовке первого
теста, и упаковщик рухнул с невнятным «Unexpected token». Это не искусственная
ситуация — `messages.json` правят руками чаще любого другого файла, а редакторы
под Windows ставят BOM охотно. Чтение JSON теперь отбрасывает метку.

### Архив

```bash
npm run package
```
```
[package] image-enhancer-1.0.0.zip: 23 файлов, 2.8 МБ -> 1.4 МБ
```

Архив распакован средствами Windows: 23 файла, все совпадают по размеру
с `dist/`, `manifest.json` читается, `default_locale` на месте. То есть
самописный zip действительно валиден, а не «открывается у нас».

### Проверка в браузере

```bash
npm run package
```

1. **Загрузка.** В `chrome://extensions` загрузить папку `dist`. Ошибок быть
   не должно, в списке — «ImageEnhancer 1.0.0».

2. **Иконка.** Посмотреть на иконку в панели браузера (16 px) и в списке
   расширений (48 px). В маленьком размере должна читаться стрелка, а не
   серое пятно.

3. **Язык.** Интерфейс на русском. Чтобы проверить английский: в
   `chrome://settings/languages` поставить English первым и перезапустить
   браузер. Все надписи должны смениться, включая пункт контекстного меню
   и описание в списке расширений.

4. **Пропущенные строки.** На каждом экране искать надписи вида `popupQuality` —
   это ключи, для которых не нашлось перевода.

5. **Плашка над видео.** Навести курсор на видео — плашки быть **не должно**.

6. **Страница настроек.** Раздел «Приватность» на месте, текст читается.

7. **Zip.** Файл `image-enhancer-1.0.0.zip` в корне проекта — именно его
   загружают в панель разработчика Chrome Web Store.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Надпись исчезла | Опечатка в ключе — `getMessage` вернул пустую строку | Обёртка `t()` возвращает ключ; проверка локалей при упаковке |
| Надписи не подставляются в popup/options | Ожидалось, что HTML поддерживает `__MSG_key__` | В HTML подстановки нет, нужен `applyI18n()` |
| В строке видно `$SIZE$` | Плейсхолдер не объявлен в `placeholders` | Проверка соответствия при упаковке |
| Расширение не загружается после смены языка | В `default_locale` указана локаль, которой нет | Проверка при упаковке |
| Иконка в панели выглядит мыльной | Один глиф на все размеры | Упрощённый глиф ниже 32 px |
| Архив не открывается | Использован `deflateSync` вместо `deflateRawSync` | В zip хранится голый поток deflate |
| Архив открывается, но Chrome его не принимает | В пакете лишние файлы или битые пути | Проверки перед упаковкой |
| `Unexpected token` при чтении `messages.json` | BOM в начале файла | Отбрасывать метку при чтении |
| Разные zip при сборке одного кода | В архив пишется текущее время | Фиксированная метка времени |
| Магазин отклоняет из-за разрешений | Не объяснено, зачем нужен доступ ко всем сайтам | Политика конфиденциальности и описание |

### Состояние проекта

Девять этапов закрыты. Расширение умеет:

- улучшать отдельную картинку по наведению или через контекстное меню;
- обрабатывать все картинки страницы очередью с прогрессом и отменой;
- считать фильтром Ланцоша или нейросетью, выбирая по возможностям устройства;
- работать в отдельных потоках, не подвешивая страницу;
- получать пиксели тремя способами, включая обход CORS силами расширения;
- объяснять отказы человеческим языком на двух языках.

### Что осталось за рамками

Помимо перечисленного в `..._Impl.md`, главное:

**Расширение ни разу не запускалось в настоящем Chrome.** Все девять этапов
проверялись в изолированном стенде: страница с заглушкой `chrome` API,
собранные файлы, эмуляция service worker'а прокси-сервером. Этого хватило,
чтобы найти десяток настоящих ошибок — от неверной нормализации модели
до зависания в невидимой вкладке, — но не заменяет запуска.

Перед публикацией обязательны ручные проверки из разделов «Проверка» всех
девяти гайдов. Особое внимание — тому, что стенд воспроизвести не мог:
`host_permissions`, `web_accessible_resources`, поведение CSP страницы
при компиляции WebAssembly, реальный канал сообщений с многомегабайтной строкой.
