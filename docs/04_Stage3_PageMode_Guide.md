# Этап 3: Режим «вся страница»

## Цель этапа

Одна команда — и все подходящие картинки на странице обработаны, с видимым прогрессом
и возможностью остановить процесс.

Кажется, что это цикл `for` вокруг готового кода с этапа 2. На деле здесь появляются
четыре задачи, которых в сценарии «одна картинка» не было:

1. **Планирование.** Какие картинки брать, в каком порядке, сколько сразу.
2. **Прогресс.** Пользователь должен понимать, что происходит, и сколько осталось.
3. **Отмена.** Двадцать картинок — это заметное время; должна быть кнопка «стоп».
4. **Отзывчивость.** Наивный цикл заморозит страницу на всё время работы, и нажать
   ту самую кнопку «стоп» будет физически невозможно.

Четвёртая задача — самая интересная, и она же покажет, почему следующий этап посвящён
переносу вычислений в Worker.

---

## Теория

### Почему наивный цикл не работает

Напрашивающееся решение:

```js
for (const image of images) {
  await enhanceImage(image)   // ← 250 мс синхронных вычислений внутри
}
```

Проблема не в `await`. Внутри `enhanceImage` есть участок, который выполняется
**синхронно**: фильтр Ланцоша — обычный цикл по пикселям, который нельзя прервать
и который не отдаёт управление браузеру, пока не закончит.

JavaScript в браузере однопоточный, и этот поток занят ещё и:
- отрисовкой страницы,
- обработкой кликов, прокрутки, ввода,
- выполнением скриптов самого сайта.

Пока считается фильтр, ничего из этого не происходит. Для одной картинки это 250 мс —
заметно, но терпимо. Для двадцати — пять секунд полностью замершей вкладки, в течение
которых:

- полоса прогресса не обновится ни разу (её просто некому нарисовать);
- нажатие «Отмена» не дойдёт до обработчика (событие встанет в очередь и подождёт);
- Chrome может показать «Страница не отвечает».

**Возврат кадра между задачами** — минимальное лекарство: после каждой картинки мы
на мгновение отдаём поток браузеру, он успевает нарисовать прогресс и обработать
накопившиеся клики. Страница остаётся «рваной», но управляемой.

Полное лекарство — вынести вычисления из главного потока совсем. Это этап 4.

### `requestAnimationFrame` — не таймер

Чтобы отдать браузеру кадр, напрашивается `requestAnimationFrame`: он вызывается перед
следующей отрисовкой.

Но `rAF` — не обещание «через 16 мс». Это обещание «перед следующим кадром», а кадра
может не быть никогда: **в невидимой вкладке браузер не рисует**. Ожидание внутри `rAF`
там не заканчивается вовсе.

Это уже дважды ломало проект: на этапе 1 так не появлялись тосты, на этапе 2 так вставала
обработка. Поэтому в `src/content/scheduler.ts` `rAF` всегда идёт в паре
со страховочным `setTimeout`.

### Ограничение параллелизма

Классический приём для очередей: не запускать все задачи разом, а держать не больше N
одновременно. Зачем:

- **память** — каждая задача держит буферы; двадцать одновременно означает двадцать
  наборов буферов;
- **сеть** — браузер всё равно ограничивает число одновременных запросов к домену
  (обычно 6), остальные просто ждут;
- **отзывчивость** — сто параллельных задач конкурируют за тот же единственный поток.

**Как это реализуется правильно.** Наивный вариант — заранее раздать задачи исполнителям
поровну: первому задачи 0–4, второму 5–9. Он плох, когда задачи разной стоимости:
у нас картинки бывают и 200×200 (10 мс), и 4000×3000 (600 мс). Один исполнитель
закончит сразу и будет простаивать, пока второй разбирается со своими.

Правильный приём — **пул с общим курсором**: исполнители в цикле берут следующую
свободную задачу. Кто освободился, тот и работает.

```
задачи:   [0][1][2][3][4][5][6][7]
             ↑ общий курсор
исполнитель A ──берёт 0──берёт 2──берёт 3──
исполнитель B ──берёт 1─────────берёт 4──
```

**Сколько ставить.** На этом этапе — **единицу**, и это не заглушка, а осознанный выбор.
Вычисления синхронные и в единственном потоке: две «параллельные» задачи всё равно
выполнятся последовательно. Ускорения не будет, а пик памяти удвоится. Параллелизм
начнёт давать выигрыш только когда задачи уедут в отдельные потоки — на этапе 4.
Разумное значение тогда — примерно половина `navigator.hardwareConcurrency`,
чтобы оставить воздух браузеру и системе.

### `AbortController` — стандартный способ отмены

`AbortController` — встроенный механизм отмены асинхронных операций. У контроллера есть
`signal`, который передаётся в операцию; вызов `controller.abort()` переводит сигнал
в состояние «отменено», и операция обязана это заметить.

```js
const controller = new AbortController()
doWork(controller.signal)
// позже
controller.abort()
```

Важно понимать границы: **`abort()` ничего не прерывает сам по себе**. Он только
поднимает флаг. Прерывание происходит там, где код этот флаг проверяет. Синхронный
цикл по пикселям флаг не проверяет (и не может — он не отдаёт управление), поэтому
отмена срабатывает **по границе задачи**: текущая картинка досчитается, следующая
не начнётся.

Это ограничение честнее убрать, чем спрятать: разбивать фильтр на прерываемые куски
ради задержки в доли секунды — усложнение ради усложнения, тем более что на этапе 4
Worker можно будет просто завершить.

### Где должна жить очередь

Вариантов два: content script (в каждой вкладке свой) или service worker (один на всё
расширение).

| | Content script (наш выбор) | Service worker |
|---|---|---|
| Ссылки на картинки | Прямые ссылки на DOM-узлы | Только URL; надо гонять данные между контекстами |
| Прогресс | Рисуется тут же | Нужны сообщения во вкладку на каждое изменение |
| Отмена | Локальная | Нужен идентификатор запуска |
| Выгрузка по простою | Не выгружается | **Выгружается через ~30 секунд**, состояние надо хранить в `chrome.storage` и восстанавливать |
| Несколько вкладок | Каждая сама по себе — то, что нужно | Нужен реестр запусков по вкладкам |

Решающий аргумент — предпоследняя строка. Очередь в service worker'е MV3 пришлось бы
делать устойчивой к тому, что исполнитель умирает посреди работы. Это оправдано для
задач, которые должны пережить закрытие вкладки (будущая фоновая обработка видео),
и совершенно не оправдано для задачи «улучшить картинки на этой странице».

### Почему `MutationObserver` так и не понадобился

На этапе 1 мы отложили `MutationObserver` до момента, когда понадобится актуальный
**список** картинок. Режим «вся страница» — как раз такой случай. И всё равно
не понадобился.

Причина: очередь со списком, который растёт на ходу, теряет смысл.

- Прогресс «N из M» перестаёт что-либо значить, если M увеличивается: полоса будет
  откатываться назад.
- На странице с бесконечной лентой очередь **никогда не закончится**: обработка картинок
  вызывает подгрузку следующих, те попадают в очередь, и так до бесконечности.
- Пользователь не поймёт, когда всё готово.

Поэтому список снимается **один раз, на старте**. Следствие, которое надо знать:
на страницах с ленивой загрузкой обрабатывается только уже загруженное. Чтобы захватить
больше, страницу нужно сначала прокрутить. Это ограничение, но предсказуемое —
в отличие от бесконечной очереди.

## Что делаем

1. Пишем обобщённую очередь: параллелизм, прогресс, отмена, возврат кадра.
2. Пишем панель прогресса с кнопками.
3. Разделяем поток обработки этапа 2 на ядро (без UI) и обёртку с тостами.
4. Пишем оркестрацию: сбор кандидатов, сортировка, запуск, группировка ошибок.
5. Добавляем две точки запуска: кнопку в popup и пункт контекстного меню.
6. Проверяем: прогресс, отмена, восстановление, повторный запуск, ошибки.

## Пошаговая инструкция

### Шаг 1. Очередь

```ts
export async function runQueue<T>(tasks: QueueTask<T>[], options: RunQueueOptions<T>) {
  const state: QueueProgress = { total: tasks.length, done: 0, failed: 0, running: 0 }
  let cursor = 0

  const worker = async (): Promise<void> => {
    for (;;) {
      if (options.signal.aborted) return
      const index = cursor
      cursor += 1
      const task = tasks[index]
      if (!task) return
      // ... выполнение, счётчики, отчёт
      await yieldUntilPainted()
    }
  }

  await Promise.all(Array.from({ length: Math.max(1, options.concurrency) }, worker))
  return { ...state }
}
```

> **Почему очередь ничего не знает про картинки**
>
> Задача здесь — просто асинхронная функция. Это не абстракция ради абстракции:
> на этапе 4 задачи станут сообщениями в Worker, а на будущем видео-этапе — обработкой
> кадров. Планирование, счётчики и отмена при этом не меняются ни на строчку.
>
> Проверка простая: в файле `queue.ts` нет ни слова «image».

> **Почему `cursor` — общий, а не своя порция у каждого исполнителя**
>
> Задачи у нас разной стоимости: картинка 200×200 считается за 10 мс, 4000×3000 —
> за 600. При делении задач поровну заранее один исполнитель закончил бы за секунду
> и простаивал, пока второй домучивает свои.
>
> С общим курсором каждый берёт следующую свободную, и работа распределяется сама.
> Это стандартный пул исполнителей, и он же используется во всех приличных
> реализациях `Promise.map` с лимитом.

> **Почему ошибка задачи не роняет очередь**
>
> ```ts
> } catch (error) {
>   if (!options.signal.aborted) {
>     state.failed += 1
>     options.onItemFailed?.(index, error)
>   }
> }
> ```
> Неудача отдельной картинки — штатное событие: она может быть закрыта CORS, слишком
> большой или битой. Если бы очередь на этом останавливалась, страница, где первая же
> картинка на CDN, обрабатывалась бы ровно на ноль картинок.
>
> Проверка `signal.aborted` внутри `catch` важна: при отмене задачи бросают `AbortError`,
> но это не неудача, а решение пользователя. Без этой проверки после отмены счётчик
> показывал бы «пропущено: 11», как будто что-то сломалось.

> **Почему `await yieldUntilPainted()` — обязательная строка, а не вежливость**
>
> Без неё очередь из двадцати картинок выполнилась бы одним куском: между задачами
> не было бы ни одного момента, когда браузер может нарисовать кадр.
>
> Симптомы: полоса прогресса не двигается вообще (перескакивает с 0% сразу на 100%),
> нажатие «Отмена» не срабатывает, Chrome предлагает закрыть «зависшую» страницу.
>
> Заметьте, что `await` внутри задачи (например, ожидание сети) не спасает:
> он отдаёт управление, но браузер не обязан рисовать кадр — он рисует, когда есть
> свободное время между задачами. `yieldUntilPainted` создаёт это время явно.

### Шаг 2. Панель прогресса

> **Почему панель, а не тост**
>
> Тост живёт секунды и не имеет состояния. Здесь нужно показывать меняющийся прогресс
> минутами и держать кнопку «Отмена» доступной всё это время.

> **Почему панель слева, а тосты справа**
>
> Они не должны перекрываться. Причём важно именно то, что **прогресс не должен
> скрываться под уведомлением об ошибке**: когда картинки начинают массово падать,
> пользователь как раз хочет видеть счётчик и нажать «Отмена».

```css
.panel[data-visible='false'] {
  pointer-events: none;
}
```

> **Зачем это правило**
>
> Панель скрывается через `opacity`, чтобы был плавный переход. Элемент с `opacity: 0`
> **продолжает ловить клики** — невидимая панель 260×120 в углу перехватывала бы клики
> по странице. Та же ошибка и то же лечение, что у кнопки-оверлея на этапе 1.

Кнопки в панели:

```ts
const stopClick = (handler: () => void) => (event: MouseEvent) => {
  event.preventDefault()
  event.stopPropagation()
  handler()
}
```

> Та же причина, что и на этапе 1: событие всплывает из shadow root до `document`,
> где его видят делегированные обработчики страницы — для них это клик
> по `<image-enhancer-root>`.

### Шаг 3. Разделение работы и UI

Код этапа 2 показывал тост на каждую картинку. В пакетном режиме это стена уведомлений.
Поэтому `enhance-flow.ts` разделён:

```ts
// работа без UI — вызывается и кнопкой, и очередью
export async function enhanceImageCore(image, trigger, signal?): Promise<EnhanceOutcome>

// сценарий «одна картинка»: та же работа плюс тосты
export function createEnhanceFlow({ toaster }) { ... }
```

> **Почему разделение обязательно, а не «для красоты»**
>
> Альтернатива — передавать в поток флаг «показывать тосты или нет». Это работает
> ровно до первого различия, которое не сводится к булеву флагу: в пакетном режиме
> не нужны кнопки «Скачать»/«Вернуть» на каждой картинке, нужен другой текст ошибки,
> нужен `AbortSignal`.
>
> Через месяц такой флаг обрастает условиями, и два режима начинают тихо расходиться
> в поведении. Разделение на «что делаем» и «как показываем» удерживает их на одном коде.

Функция `describeFailure` вынесена в экспорт: она нужна обоим режимам, но по-разному —
один показывает текст сразу, другой группирует по причинам.

### Шаг 4. Сбор и порядок

```ts
const candidates = scanMedia()
  .images.filter((image) => !hasOriginal(image))
  .sort(byViewportPriority)
```

> **Почему уже улучшенные пропускаются**
>
> Иначе повторный запуск обработал бы результаты предыдущего: улучшил бы уже
> улучшенное, потратив время и удвоив память. А кнопка «Вернуть» вернула бы
> не оригинал, а промежуточный результат.
>
> Проверено на стенде: после первого прогона (14 картинок) повторный запуск взял 11 —
> три уже обработанные пропущены, а закрытая CORS-ом снова попала в список.

> **Почему картинка, закрытая CORS, попадает в очередь снова**
>
> Она не считается улучшенной — улучшение не удалось. Это осознанно: разрешения
> на сервере могли измениться, а тихо игнорировать картинку навсегда хуже, чем
> попробовать ещё раз. Цена — одна неудачная попытка за запуск.

```ts
function byViewportPriority(a: HTMLImageElement, b: HTMLImageElement): number {
  const center = window.innerHeight / 2
  const distance = (image: HTMLImageElement): number => {
    const rect = image.getBoundingClientRect()
    return Math.abs(rect.top + rect.height / 2 - center)
  }
  return distance(a) - distance(b)
}
```

> **Зачем сортировать, если обработать надо всё равно все**
>
> Пользователь смотрит на видимую часть страницы. При обработке в порядке DOM первые
> результаты могут появиться далеко внизу, и первые несколько секунд будет казаться,
> что ничего не происходит — при том, что страница при этом ещё и подтормаживает.
>
> Сортировка по удалённости от центра экрана даёт видимый результат сразу. Стоимость —
> один `getBoundingClientRect` на картинку при старте.

> **Откуда потолок в 50 картинок**
>
> Ограничение по памяти, а не по времени. Каждая обработанная картинка остаётся
> на странице в виде Blob, который держится объектным URL до тех пор, пока пользователь
> не вернёт оригинал. Апскейл среднего изображения весит 1–3 МБ; пятьдесят штук —
> это больше сотни мегабайт сверх обычного расхода вкладки.
>
> Если картинок больше, обрабатываются первые 50 по приоритету видимости,
> **и пользователю об этом прямо сообщается**. Молча обработать часть и сделать вид,
> что всё сделано, — худший вариант из возможных.

### Шаг 5. Группировка ошибок

```ts
const failures = new Map<string, number>()
// ...
onItemFailed: (index, error) => {
  const reason = describeFailure(error)
  failures.set(reason, (failures.get(reason) ?? 0) + 1)
}
// после завершения
for (const [reason, count] of failures) {
  toaster.show(count > 1 ? `${reason} (картинок: ${count})` : reason, { tone: 'error' })
}
```

> **Почему не показывать ошибку сразу по каждой картинке**
>
> Самый частый сценарий неудачи — все картинки лежат на одном CDN без CORS-заголовков.
> Тогда упадут **все**, с одинаковой причиной. Сорок одинаковых уведомлений подряд
> не сообщают ничего сверх одного, зато полностью закрывают страницу (при лимите
> в три тоста они бы ещё и вытесняли друг друга, мелькая).
>
> Группировка по тексту причины даёт одно уведомление на реальную проблему.

### Шаг 6. Запуск не ожидается

```ts
void (async () => {
  // ... вся очередь
})()

return { started: true, total: batch.length }
```

> **Почему функция возвращает управление до того, как очередь отработала**
>
> Запуск приходит сообщением из popup или контекстного меню. Popup **уничтожается**
> при первом же клике вне себя — то есть через доли секунды. Ждать ответа сообщения
> минуту будет некому: канал закроется, и в консоли появится ошибка о недоставленном
> ответе.
>
> Поэтому ответ отдаётся сразу («запустил, картинок столько-то»), а сама очередь
> продолжает работать в content script — он никуда не денется и переживёт и закрытие
> popup, и переключение вкладок.

```ts
if (controller) {
  return { started: false, total: 0, reason: 'Обработка страницы уже идёт.' }
}
```

> **Зачем защита от второго запуска**
>
> Пользователь легко нажмёт кнопку дважды или откроет popup и продублирует через
> контекстное меню. Две очереди на одной странице боролись бы за те же картинки:
> вторая взяла бы в работу те, что первая ещё не успела заменить, и обе полезли бы
> в память одновременно.
>
> Проверено на стенде: второй вызов возвращает `started: false` с понятной причиной.

### Шаг 7. Точки запуска

**Popup.** Кнопка «Улучшить все на странице» блокируется, если картинок ноль или
страница служебная:

```ts
if (enhanceButton) enhanceButton.disabled = result.images === 0
```

и закрывает себя после отправки:

```ts
await sendToTab(tabId, 'ENHANCE_PAGE', {})
window.close()
```

> **Почему popup закрывается сам**
>
> Он всё равно закроется при первом клике мимо. Оставлять его открытым бессмысленно:
> прогресс он не показывает (это делает панель на странице), а висящее окно поверх
> контента только мешает смотреть на результат.

**Контекстное меню.** Второй пункт с `contexts: ['page']`:

> **Почему два пункта не появятся в меню одновременно**
>
> Контекст `'page'` означает «правый клик не по картинке, не по ссылке, не по выделению
> и не по полю ввода». Контекст `'image'` — «правый клик по `<img>`». Они взаимно
> исключают друг друга, поэтому меню не будет захламлено.

### На стенде

Стенд из этапов 1–2, дополненный пачкой из восьми картинок разного размера.

|---|---|
| Запуск | `{ started: true, total: 14 }`, панель появилась: «0 из 14», полоса 0% |

| Завершение | «14 из 14 · пропущено: 1», 100%, состояние `done`, заголовок «Готово» |

| Тост об ошибке | Один, сгруппированный: «Сайт не разрешает читать эту картинку…» |

Отмена, как и ожидалось, срабатывает **по границе задачи**: картинка, начатая
до нажатия, досчиталась. Это задокументированное ограничение, а не дефект.

### В браузере

```bash
npm run dev
```

1. **Запуск из popup.** Открыть страницу с несколькими картинками, нажать иконку
   расширения → «Улучшить все на странице». Popup закроется, в левом нижнем углу
   появится панель «Улучшаю изображения» со счётчиком.

2. **Прогресс.** Счётчик и полоса должны расти. Картинки в видимой части экрана
   должны обновляться **первыми** — это проверка сортировки по видимости.

3. **Отзывчивость.** Попробовать прокрутить страницу во время обработки. Прокрутка
   будет рваной — поток занят вычислениями, кадр возвращается только между картинками.
   Это ожидаемо и есть прямая мотивация этапа 4.

4. **Отмена.** Нажать «Отмена» на середине. Панель должна перейти в «Обработка
   остановлена», счётчик замереть, оставшиеся картинки остаться нетронутыми.
   Одна лишняя картинка может успеть обработаться — это нормально.

5. **Возврат.** Нажать «Вернуть все» — все подменённые картинки возвращаются
   к оригиналам, появляется тост с их числом.

6. **Повторный запуск.** Запустить снова, не восстанавливая. В счётчике должно быть
   **меньше** картинок, чем в первый раз: уже улучшенные пропускаются.

7. **Контекстное меню.** Правый клик по **пустому месту** страницы (не по картинке) →
   «Улучшить все изображения на странице». Работает так же.

8. **Страница без картинок.** Открыть popup — кнопка «Улучшить все на странице» должна
   быть неактивной, а счётчики показывать 0.

9. **Служебная страница.** Открыть popup на `chrome://extensions` — счётчики покажут
   «нет доступа», кнопка неактивна.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Полоса прогресса перескакивает с 0% сразу на 100% | Между задачами не возвращается кадр — браузеру некогда рисовать | `await yieldUntilPainted()` в конце каждой итерации исполнителя |
| «Отмена» не срабатывает | То же самое: клик встал в очередь событий, а поток занят | То же решение |
| Очередь никогда не заканчивается на бесконечной ленте | Список картинок пересобирается по ходу (например, через `MutationObserver`) | Снимать список один раз, на старте |
| После отмены в счётчике «пропущено: N» | `AbortError` считается неудачей задачи | Проверять `signal.aborted` внутри `catch` и не увеличивать счётчик неудач |
| Очередь останавливается на первой же плохой картинке | Ошибка задачи выбрасывается наружу вместо подсчёта | Ловить ошибку внутри исполнителя |
| Сорок одинаковых уведомлений об ошибке | Тост показывается на каждую неудачу | Группировать по тексту причины |
| Один исполнитель закончил, второй ещё работает половину времени | Задачи разделены между исполнителями заранее | Общий курсор: кто освободился, тот берёт следующую |
| Клики по странице в левом нижнем углу не работают | Скрытая панель ловит события | `pointer-events: none` при `data-visible='false'` |
| Повторный запуск обрабатывает уже улучшенное | Нет фильтра по `hasOriginal` | Фильтровать кандидатов |
| В консоли ошибка о недоставленном ответе после запуска из popup | Обработчик ждёт окончания очереди, а popup закрылся | Отвечать сразу, очередь запускать без ожидания |
| Вкладка съедает сотни мегабайт | Много обработанных картинок держат Blob'ы | Ожидаемо; «Вернуть все» освобождает память. Потолок 50 картинок за запуск |
| На странице с ленивой загрузкой обработалось три картинки из ста | Остальные ещё не загружены (`naturalWidth === 0`) | Прокрутить страницу перед запуском |

## Итог этапа

### Что появилось в архитектуре

| Модуль | Роль |
|---|---|
| `src/content/queue.ts` | Обобщённая очередь: параллелизм, прогресс, отмена. Про картинки не знает |
| `src/content/scheduler.ts` | Возврат кадра браузеру. Вынесен отдельно, потому что нужен и очереди, и одиночной обработке |
| `src/content/page-flow.ts` | Оркестрация пакетного режима: сбор, порядок, запуск, группировка ошибок |
| `src/ui/progress-panel.ts` | Панель хода обработки с кнопками |
| `src/content/enhance-flow.ts` | Разделён: `enhanceImageCore` (работа) и `createEnhanceFlow` (UI одной картинки) |

### Новое в контракте сообщений

| Сообщение | Направление | Назначение |
|---|---|---|
| `ENHANCE_PAGE` | popup / service worker → content | Запуск режима «вся страница». Отвечает сразу, не дожидаясь очереди |

Тип `EnhanceTrigger` получил третье значение — `'page'`.

`AbortController` / `AbortSignal`, `chrome.contextMenus` с `contexts: ['page']`,

### Новых разрешений нет

### Что заложено под видео

Очередь написана обобщённо и переиспользуется без изменений: задача — просто
асинхронная функция. Для видео задачами станут кадры, а типы `VideoProgress`
из `src/video/types.ts` описывают прогресс в кадрах именно потому, что счётчики
очереди рассчитаны на оба случая.

### Что будет дальше

**Этап 4 — вынос вычислений в Web Worker.** Проблема, которую этот этап показал
в полный рост: страница замирает на всё время работы, отмена срабатывает
с запозданием, параллелизм бессмыслен.

Решение упирается в ограничение из этапа 0: content script не может создать Worker
из файла расширения, а service worker в MV3 вообще не имеет конструктора `Worker`.
Поэтому на этапе 4 появится **Offscreen Document** — невидимая страница расширения,
у которой есть и DOM, и право создавать воркеры, — и цепочка
`content script → service worker → offscreen → Worker`.

Модуль `core/enhance/` к переезду готов с этапа 2: он работает только
с `OffscreenCanvas` и не трогает ни DOM, ни chrome API.
