# Этап 10: Выбор модели и целевого размера

Этап вне исходного плана. Появился после того, как расширение попробовали
в работе и выяснилось: увеличение «на один уровень» — не то, что нужно
человеку, у которого есть конкретное представление о нужном размере.

## Цель этапа

1. Дать выбор между лёгкой и тяжёлой нейросетью — с честным указанием цены.
2. Заменить «увеличить в N раз» на «привести к такому-то размеру», в обе стороны.
3. Не трогать картинки, которые уже подходят.

---

## Теория

### Чем отличаются модели одного семейства

Обе доступные модели — ESRGAN одного происхождения и, что важнее, **одной
архитектуры RDN с одинаковым диапазоном входа 0..255**. Это значит, что код
инференса для них общий: меняется только файл весов.

Различие — в размере сети. В метаданных пакета это видно прямо:

| | slim | medium |
|---|---|---|
| Плотных блоков (`D`) | 2 | 10 |
| Скорость роста (`G`) | 4 | 64 |
| Веса x2 | 0.9 МБ | 2.7 МБ |

Больше блоков и шире каналы — больше признаков сеть учитывает и больше
вычислений делает на каждый пиксель. Отсюда прямая зависимость: **втрое больше
весов — примерно вдвое больше времени**.

Что важно понимать про ожидания: рост качества с размером сети **не линеен**
и быстро выходит на плато. Замер на нашей тестовой картинке дал +3.6% резкости
за двукратное время. Это не «в два раза лучше» и никогда им не будет.

### Почему выбор модели — это выбор компромисса, а не «включить лучше»

Пользователю бесполезно сообщение «модель A лучше модели B». Полезно другое:
сколько это стоит и когда разница окупается.

Поэтому в интерфейсе у каждого варианта стоит не оценка («хорошо»/«отлично»),
а факты: размер весов, время на конкретной картинке, и предупреждение о том,
что без WebGPU тяжёлую модель включать не стоит.

### Целевой размер: почему длинная сторона

Естественная формулировка «привести к ширине 1920» ломается на вертикальных
картинках. Портрет 600×1200, приведённый к ширине 1920, станет 1920×3840 —
это 7.4 мегапикселя вместо ожидаемых двух, втрое больше памяти и времени.

Длинная сторона даёт предсказуемый потолок площади независимо от ориентации:
что баннер, что портрет после обработки не превысят заданного размера
ни по одному измерению.

### Почему уменьшение — не «ухудшение»

Уменьшение картинки алгоритмом Ланцоша — не порча, а корректная передискретизация.
Она нужна, когда картинка **больше**, чем нужно: страница с фотографиями
по 4000 пикселей, приведённая к 1200, весит в десять раз меньше и выглядит
так же.

Ключевая деталь заложена ещё на этапе 2: при `scale < 1` окно фильтра
растягивается (`filterScale = 1 / scale`). Без этого между выходными пикселями
остались бы неучтённые входные, и картинка покрылась бы муаром на мелких
деталях. Именно поэтому уменьшение здесь можно включать, не дописывая алгоритм.

### Отсев до очереди, а не внутри неё

Картинку, уже подходящую под цель, можно отбраковать двумя способами:

| Где | Что видит пользователь |
|---|---|
| Внутри очереди | «40 из 40 · пропущено 37» |
| До очереди (наш выбор) | «3 из 3» |

Первое формально верно и совершенно нечитаемо: непонятно, сломалось что-то
или так и задумано. Второе показывает реальный объём работы.

Цена — проход по всем картинкам с вычислением плана до старта. Он дешёвый:
чтение `naturalWidth` и деление.

## Пошаговая инструкция

### Шаг 1. Расчёт коэффициента по цели

```ts
export function resolveTargetScale(
  naturalWidth: number,
  naturalHeight: number,
  targetPx: number,
  skipIfLargeEnough: boolean,
  maxScale: number,
): TargetPlan {
  const longest = Math.max(naturalWidth, naturalHeight)
  if (longest <= 0 || targetPx <= 0) return { scale: 1, skip: true }

  if (skipIfLargeEnough && longest >= targetPx) return { scale: 1, skip: true }

  const wanted = targetPx / longest
  const scale = Math.min(maxScale, Math.max(MIN_DOWNSCALE, wanted))

  if (Math.abs(scale - 1) < 0.01) return { scale: 1, skip: true }
  return { scale, skip: false }
}
```

> **Почему возвращается пара «коэффициент и признак пропуска», а не просто число**
>
> «Ничего не делать» — не то же самое, что «умножить на 1». Умножение на единицу
> прогнало бы картинку через весь пайплайн, перекодировало её и подменило файлом
> того же размера. Признак `skip` позволяет вызывающему коду отказаться раньше
> и сказать об этом пользователю.

> **Откуда порог в один процент**
>
> Картинка 1000 пикселей при цели 1005 формально требует коэффициента 1.005.
> Результат визуально не отличается от оригинала, зато перекодирование в PNG
> может дать файл **больше** исходного JPEG. Работа, ухудшающая результат,
> лучше не выполняться.

> **Зачем нижняя граница уменьшения**
>
> `MIN_DOWNSCALE = 0.1`. Ниже десятой доли результат перестаёт быть картинкой
> и становится превью, а чаще означает опечатку в поле ввода — например,
> 64 вместо 640.

### Шаг 2. Переключение модели

```ts
export function getMlRuntime(model: ModelChoice): Promise<MlRuntime | null> {
  if (runtime && runtimeModel !== model) {
    const previous = runtime
    runtime = null
    void previous.then((instance) => instance?.destroy())
  }
  runtimeModel = model
  runtime ??= createRuntime(model).catch(/* ... */)
  return runtime
}
```

> **Почему старый воркер уничтожается, а не остаётся про запас**
>
> Он держит в памяти загруженные веса и буферы бэкенда. Хранить оба набора
> ради переключения, которое пользователь делает раз в месяц, — плата
> в мегабайтах за экономию четверти секунды в редком случае.

> **Почему `runtime` обнуляется ДО того, как старый уничтожен**
>
> `destroy()` вызывается на результате промиса, то есть асинхронно. Если бы
> обнуление шло после, между ними существовал бы момент, когда `getMlRuntime`
> вернул бы уже приговорённый рантайм.

```ts
maxInputPixels: model === 'medium'
  ? Math.round(basePixels / HEAVY_MODEL_PIXEL_DIVISOR)
  : basePixels,
```

> **Почему у тяжёлой модели свой потолок размера**
>
> Замер: medium вдвое дольше slim на картинке 240×180, и разрыв растёт
> с размером — сеть глубже, и каждый дополнительный пиксель стоит дороже.
>
> Оставить общий потолок значило бы, что переключение модели молча учетверяет
> ожидание на предельной картинке. Пользователь связал бы это не с настройкой,
> а с «расширение стало тормозить».

### Шаг 3. Отказ до начала работы

```ts
if (plan.skip) {
  toaster.show(t('errAlreadyBigEnough'))
  return
}
```

> **Почему уведомление показывается сразу, а не через «обрабатываю…»**
>
> Мигнувшее «обрабатываю», сменившееся отказом, читается как сбой. Отказ,
> показанный сразу, читается как ответ.

В очереди отсев идёт раньше:

```ts
const candidates = scanMedia()
  .images.filter((image) => !hasOriginal(image))
  .filter((image) => !planEnhance(image, level, settings).skip)
  .sort(byViewportPriority)
```

### Шаг 4. Поле ввода размера

```ts
targetPx.addEventListener('change', () => {
  const value = Number(targetPx.value)
  const clamped = Math.min(8192, Math.max(64, Math.round(value) || DEFAULT_SETTINGS.targetPx))
  targetPx.value = String(clamped)
  void patchSettings({ targetPx: clamped })
})
```

> **Почему `change`, а не `input`**
>
> `input` срабатывает на каждый символ. При наборе «1920» в хранилище улетели бы
> 1, 19, 192 и 1920 — четыре записи, каждая из которых сбрасывает кеш настроек
> **во всех открытых вкладках**. `change` срабатывает один раз, когда поле
> потеряло фокус или пользователь нажал Enter.

> **Зачем ограничивать значение в коде, если у поля есть `min` и `max`**
>
> Атрибуты `min`/`max` у `<input type="number">` — подсказка браузеру,
> а не гарантия. Вставка из буфера обмена и программное изменение их обходят.
> Значение, попадающее в хранилище, проверяется там, где оно сохраняется.

> **Почему `|| DEFAULT_SETTINGS.targetPx`**
>
> `Number('')` даёт `NaN`, а `Math.round(NaN)` — снова `NaN`. Без запасного
> значения пустое поле сохранило бы `NaN`, и все последующие расчёты дали бы
> `NaN` — то есть картинки перестали бы обрабатываться совсем, без единой ошибки
> в консоли.

### Шаг 5. Скрытие неприменимых настроек

```ts
function syncTargetVisibility(mode: string): void {
  if (targetExtra) targetExtra.hidden = mode !== 'longest-side'
}
```

> **Почему скрываем, а не блокируем**
>
> Неактивное поле с числом выглядит как что-то, что вот-вот заработает,
> и заставляет искать способ его включить. Отсутствующее поле вопросов
> не вызывает.

## Проверка

### Модели

Одна картинка 240×180 → 480×360, уровень «качественно», WebGPU:

| Модель | Время | Резкость |
|---|---|---|
| slim | 68 мс | 4.12 |
| medium | 137 мс | 4.27 |

В логе видна перезагрузка воркера при переключении:

```
ML готов: модель slim, бэкенд webgpu, загрузка 387 мс
Модель сменилась на medium, перезагружаю воркер
ML готов: модель medium, бэкенд webgpu, загрузка 366 мс
```

> Замер сделан на **синтетической** картинке — градиенты и шахматный узор.
> SR-модели обучены на фотографиях, и на реальном фото разрыв между слим
> и medium может оказаться заметнее, чем 3.6%. Приводить это число как
> универсальное было бы неверно.

### Целевой размер

| Сценарий | Результат |
|---|---|
| 240×180, цель 1000 | 960×720 — сработал потолок увеличения уровня (×4) |
| 800×600, цель 1000 | 1000×750, `canvas-lanczos` (коэффициент 1.25, модели не хватает) |
| 800×600, цель 400, галочка выключена | 400×300 |
| 1200×900, цель 600, галочка включена | Не тронута, «Картинка уже нужного размера» |
| «Вся страница», цель 600 | В очередь 13 из 16, «13 из 13» без пропусков |

Обратите внимание на первую строку: запрошена 1000, получено 960. Потолок
увеличения из уровня качества применяется и здесь. Поведение защитное
и правильное, но пользователю о нём не сообщается — записано в ограничения.

### Проверка в браузере

```bash
npm run package
```

1. **Модель.** В настройках выбрать тяжёлую, обработать картинку. В консоли
   с подробными логами: `ML готов: модель medium`. Время должно вырасти.
2. **Переключение.** Сменить модель обратно и обработать снова — в логе должна
   появиться строка о перезагрузке воркера.
3. **Целевой размер.** Выбрать «Привести длинную сторону», поставить 1200.
   Обработать мелкую картинку — результат должен быть ровно 1200 по длинной
   стороне (если не упёрся в потолок уровня).
4. **Уменьшение.** Снять галочку «не трогать», обработать картинку крупнее цели —
   она должна уменьшиться.
5. **Пропуск.** Вернуть галочку, обработать ту же крупную картинку — должно
   появиться сообщение, картинка остаться прежней.
6. **Режим «вся страница».** На странице с картинками разного размера счётчик
   должен показывать только те, что реально обрабатываются.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Результат меньше запрошенного размера | Сработал потолок увеличения уровня качества (×2/×3/×4) | Ожидаемо; поднять уровень или уменьшить цель |
| Картинки перестали обрабатываться, ошибок нет | В `targetPx` попал `NaN` из пустого поля | Запасное значение при разборе числа |
| Настройки сбрасывают кеш на каждый символ | Сохранение по `input` | Сохранять по `change` |
| Переключение модели ничего не меняет | Воркер не пересоздаётся, работают старые веса | Уничтожать рантайм при смене модели |
| После смены модели память выросла вдвое | Старый воркер не уничтожен | `destroy()` на прежнем рантайме |
| «40 из 40 · пропущено 37» | Отбраковка внутри очереди вместо отсева до неё | Фильтровать кандидатов до старта |
| Вертикальные картинки вырастают несоразмерно | Цель задана по ширине | Считать по длинной стороне |
| Муар после уменьшения | Окно фильтра не растянуто при `scale < 1` | Заложено на этапе 2, проверить `filterScale` |
| Тяжёлая модель работает минутами | Нет WebGPU | Ожидаемо; предупреждение стоит в описании варианта |

## Итог этапа

### Новые настройки

| Ключ | Значения | По умолчанию |
|---|---|---|
| `model` | `slim` / `medium` | `slim` |
| `targetMode` | `auto` / `longest-side` | `auto` |
| `targetPx` | 64…8192 | 1920 |
| `skipIfLargeEnough` | да / нет | да |

### Что изменилось в архитектуре

`resolveTargetScale` встал рядом с `resolveScale` как второй способ получить
коэффициент; всё, что дальше по пайплайну, не изменилось — там по-прежнему
просто число. Модель стала параметром `runEnhance`, а не константой внутри
клиента.

### Размер пакета

Вырос с 2.8 до 5.5 МБ из-за второй модели. `content.js`, внедряемый в каждую
страницу, не изменился.
