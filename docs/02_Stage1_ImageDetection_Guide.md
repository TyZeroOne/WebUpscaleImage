# Этап 1: Детекция и UI-точки входа

## Цель этапа

Дать пользователю два способа сказать «улучши вот эту картинку»:

1. **Кнопка при наведении** — навёл курсор на картинку, в её углу появилась кнопка.
2. **Пункт контекстного меню** — правый клик по картинке, «Улучшить это изображение».

Оба пути должны доходить до service worker'а и возвращать ответ, который виден
пользователю. Самой обработки на этом этапе нет: service worker отвечает
«картинка найдена, обработка появится на этапе 2», и этот ответ показывается тостом.

Звучит просто, но здесь впервые возникает настоящая сложность проекта: **мы рисуем свой
интерфейс поверх чужой страницы, про которую не знаем ничего**. У неё может быть любой
CSS, любые обработчики событий и любая структура DOM. Большая часть этапа — про то,
как не сломать её и не сломаться самим.

## Теория

### Shadow DOM: зачем он и что именно он изолирует

Представим, что мы просто добавили на страницу `<div class="button">Улучшить</div>`.
Что может пойти не так:

- на сайте есть правило `.button { display: none }` — наша кнопка не покажется;
- на сайте есть `* { box-sizing: content-box }` — наши размеры поедут;
- на сайте есть `div { font-family: 'ComicSans' }` — кнопка будет выглядеть чужеродно;
- наше правило `.button { ... }` подействует на кнопки сайта — мы сломаем страницу.

Уникальные имена классов (`.ie-x7f2-button`) решают только последнюю проблему и половину
первой. Наследуемые свойства и универсальные селекторы всё равно достанут наш элемент.

**Shadow DOM** решает это по-настоящему. Это отдельное поддерево DOM, прикреплённое
к обычному элементу («хозяину», host). Граница между ними непроницаема для CSS:

- селекторы страницы **не достают** внутрь shadow root;
- селекторы изнутри **не достают** наружу;
- исключение — **наследуемые** свойства (`font`, `color`, `line-height`, `visibility`),
  которые наследуются от host-элемента внутрь. Их сбрасывают правилом `:host { all: initial }`.

```
document
 └── html
      ├── body               ← страница живёт здесь
      └── image-enhancer-root  ← host, обычный элемент в DOM страницы
           #shadow-root         ← граница; CSS через неё не проходит
            ├── <style>         ← наши стили, видны только внутри
            └── <div class="layer">
                 ├── button
                 ├── highlight
                 └── toasts
```

Важно: изолирован **только CSS**. JavaScript-контекст общий (тот же изолированный мир
content script'а), а DOM-события из shadow root наружу всплывают — с оговоркой, разобранной
ниже.

**`mode: 'open'` против `'closed'`.** У открытого shadow root есть свойство
`host.shadowRoot`, через которое до содержимого может добраться кто угодно, включая
скрипты страницы. У закрытого `host.shadowRoot === null`, и добраться нельзя.

Для расширения это имеет практический смысл: сайт не сможет найти и спрятать нашу кнопку
(а сайты, зарабатывающие на просмотрах картинок, вполне могут захотеть). Обратная сторона:
закрытый shadow root **не разворачивается в панели Elements DevTools**, и верстать вслепую
невозможно. Отсюда решение: `open` в dev-сборке, `closed` в проде.

### Делегирование событий, и почему здесь не нужен MutationObserver

Напрашивающееся решение задачи «показать кнопку при наведении на картинку»:

```js
// НЕ ДЕЛАЕМ ТАК
for (const img of document.querySelectorAll('img')) {
  img.addEventListener('mouseenter', showButton)
}
// а для новых картинок — MutationObserver
```

Проблемы:

1. **Сотни слушателей.** На новостной ленте это сотни объектов, каждый со своей замыканием.
   На бесконечной прокрутке их число растёт без предела.
2. **`MutationObserver` на всём документе — дорогое удовольствие.** Он срабатывает на
   каждое изменение DOM: анимации, обновления счётчиков, реклама. На современном сайте это
   тысячи вызовов в минуту, и в каждом мы обязаны отработать быстро, иначе затормозим сайт.
3. **Он всё равно не покрывает все случаи.** Картинка могла не появиться, а просто
   догрузиться и изменить размер — мутации DOM при этом нет.

**Делегирование событий** решает всё три разом: один слушатель на `document`, который
в момент события выясняет, что под курсором. Картинки, появившиеся после загрузки,
работают автоматически — их не нужно «регистрировать», потому что регистрации нет вообще.

> `MutationObserver` — не плохой инструмент, он просто решает другую задачу: «поддерживать
> актуальный СПИСОК элементов». Для одной картинки под курсором список не нужен.
> На этапе 3, где появится очередь обработки всех картинок страницы, вопрос вернётся.

### `event.target` против хит-теста по координатам

Внутри слушателя логично спросить: `event.target instanceof HTMLImageElement`.
На практике это часто даёт `false` там, где картинка видна.

Причина — распространённый приём вёрстки: картинку накрывают прозрачным слоем.

```html
<div class="thumb">
  <img src="photo.jpg">
  <div class="overlay"></div>   <!-- прозрачный, ловит клики -->
</div>
```

Так делают галереи (чтобы перехватить клик), ленты (чтобы показать градиент с подписью),
сайты с защитой от сохранения картинок. Курсор физически над картинкой, но событие
получает `div.overlay`, и `event.target` — это он.

**`document.elementsFromPoint(x, y)`** возвращает **все** элементы в этой точке,
сверху вниз по порядку отрисовки. Достаточно найти в этом списке первый `<img>`:

```
elementsFromPoint(x, y) → [ div.overlay, img, div.thumb, div.row, body, html ]
                                          ↑ вот она
```

Две важные особенности этой функции:

- она **уважает `pointer-events: none`**: элементы с ним в список не попадают. Это то,
  что делает возможным наш прозрачный слой на весь экран — он не мешает хит-тесту;
- для элементов внутри shadow root она возвращает **host-элемент**, а не то, что внутри.
  Это тоже используется: увидев в списке наш host, мы понимаем, что курсор на нашей
  кнопке, и не прячем её.

### Всплытие событий из shadow root и ретаргетинг

События из shadow root всплывают наружу, но при пересечении границы браузер **подменяет
`event.target`** на host-элемент. Это называется ретаргетингом, и он существует, чтобы
внешний код не узнал о внутреннем устройстве компонента.

Практическое следствие, которое легко упустить: клик по нашей кнопке для страницы
выглядит как **клик по элементу `<image-enhancer-root>`**. Обработчики страницы
вида `document.addEventListener('click', ...)` — а это почти каждый SPA, каждая галерея,
каждый лайтбокс — его увидят и могут отреагировать: закрыть просмотрщик, свернуть меню,
перейти по маршруту.

Поэтому `event.stopPropagation()` на нашей кнопке обязателен. Заметьте: **не** потому,
что кнопка «внутри ссылки» — она не внутри, она в отдельном поддереве, и нажать ссылку
не может. Именно из-за делегированных обработчиков на уровне документа.

### Контекстное меню в MV3

`chrome.contextMenus` позволяет добавить свой пункт в меню по правому клику.
Указав `contexts: ['image']`, мы получаем пункт, который Chrome показывает только
на картинках — и кладёт адрес картинки в `info.srcUrl`.

Это не дублирование кнопки, а закрытие её слабых мест:

- кнопка появляется по наведению, а **наведения не существует на сенсорных экранах**;
- кнопка недоступна с клавиатуры, а контекстное меню открывается клавишей `Menu`
  или `Shift+F10`;
- Chrome определяет «под курсором картинка» надёжнее нашего хит-теста, в том числе
  **внутри iframe**, куда мы не внедряемся.

**Ловушка MV3.** Service worker выгружается и поднимается заново, и код верхнего уровня
выполняется при каждом подъёме. Если вызвать `chrome.contextMenus.create()` на верхнем
уровне, второй подъём даст ошибку `Cannot create item with duplicate id`. Пункты меню,
в отличие от переменных, **переживают выгрузку worker'а** — их хранит браузер. Поэтому
создавать их нужно один раз, в `chrome.runtime.onInstalled`.

А вот **слушатель** `onClicked` регистрируется при каждом подъёме, синхронно — по общему
правилу MV3 из этапа 0.

### Два разных канала сообщений

В расширении две функции отправки, и путаница между ними — типовая причина сообщений,
уходящих в никуда:

| Функция | Кому доставляется |
|---|---|
| `chrome.runtime.sendMessage` | Всем контекстам расширения: service worker, popup, options. **Content script не получит.** |
| `chrome.tabs.sendMessage(tabId, ...)` | Content script'ам указанной вкладки. |

Обе не выдают ошибок, если получателя нет, — только отклоняют промис. Поэтому в проекте
две обёртки, `sendToBackground` и `sendToTab`, и они не взаимозаменяемы.

На этом этапе `sendToTab` используется дважды: service worker передаёт во вкладку выбор
пункта меню, а popup спрашивает у вкладки, сколько на ней картинок (сам popup — отдельный
документ, DOM страницы ему недоступен).

## Что делаем

1. Заводим корень UI: host-элемент и shadow root со стилями.
2. Пишем компоненты: кнопку, тост, рамку-подсветку.
3. Пишем отслеживание картинки под курсором через хит-тест и делегирование.
4. Добавляем в контракт сообщений три новых типа и функцию `sendToTab`.
5. Регистрируем пункт контекстного меню в service worker'е.
6. Замыкаем сквозной путь: клик → сообщение → заглушка-ответ → тост.
7. Проверяем — сначала на локальном стенде, потом руками в браузере.

## Пошаговая инструкция

### Шаг 1. Корень UI и Shadow DOM

`src/content/ui-root.ts` создаёт единственный host-элемент, вешает на него shadow root
и кладёт туда стили и слой для элементов.

```ts
const HOST_TAG = 'image-enhancer-root'

const hostStyle: Record<string, string> = {
  position: 'fixed',
  inset: '0',
  'z-index': '2147483647',
  'pointer-events': 'none',
  display: 'block',
  /* ... margin, padding, border, visibility, opacity, transform, filter ... */
}
for (const [prop, value] of Object.entries(hostStyle)) {
  host.style.setProperty(prop, value, 'important')
}
```

> **Почему стили host'а — инлайновые и с `!important`**
>
> Внутрь shadow root стили страницы не проходят. Но **сам host-элемент — обычный узел
> в DOM страницы**, и правила сайта на него действуют.
>
> Это не теоретический риск. Правила вида `body * { position: static !important }`
> встречаются в «режимах чтения», печатных стилях и на сайтах, борющихся с рекламными
> оверлеями. Такое правило сместило бы весь наш интерфейс в поток документа.
>
> Инлайновое объявление со своим `!important` имеет наивысший приоритет из возможных
> для автора страницы, и перебить его нельзя ничем.
>
> Отсюда же длинный список сбрасываемых свойств: `visibility`, `opacity`, `transform`,
> `filter` — всё, чем страница может нечаянно спрятать или исказить наш слой.

> **Откуда `z-index: 2147483647`**
>
> Это максимальное 32-битное знаковое целое, то есть максимально возможный `z-index`.
> Число не «магическое» и не взято с потолка: сайты регулярно используют значения вроде
> `9999` или `999999`, и единственный надёжный способ оказаться выше — взять предел.
>
> Оговорка: `z-index` работает внутри контекста наложения. Наш host — прямой ребёнок
> `<html>`, поэтому он в корневом контексте, и предельное значение действительно
> ставит его выше всего. Будь он вложен в элемент с `transform` или `filter`,
> предельный `z-index` не помог бы — контекст наложения родителя ограничил бы его.

> **Почему `pointer-events: none` на слое**
>
> Слой растянут на весь экран (`inset: 0`). Без `pointer-events: none` он перехватывал бы
> **все** клики на странице — сайт стал бы полностью неработоспособным.
>
> Интерактивные элементы внутри (кнопка) включают `pointer-events: auto` обратно точечно.
> Это стандартный приём для оверлеев.

> **Почему вставляем в `documentElement`, а не в `body`**
>
> `<body>` заменяют целиком чаще, чем кажется: SPA при смене маршрута, «режимы чтения»,
> страницы ошибок. Вместе с телом исчез бы и наш узел. `documentElement` (`<html>`)
> переживает такие замены.

> **Почему собственный тег `image-enhancer-root`, а не `div`**
>
> Селекторы сайта почти наверняка содержат `div`, но почти наверняка не содержат
> `image-enhancer-root`. Это не защита (стили host'а мы всё равно закрепили `!important`),
> а вторая линия обороны и понятность: увидев такой тег в DevTools, сразу ясно, чей он.

Стили подключаются так:

```ts
import contentCss from '@/ui/styles/content.css?inline'
// ...
const style = document.createElement('style')
style.textContent = contentCss
shadow.append(style)
```

> **Что делает `?inline` и почему CSS не отдельным файлом**
>
> Суффикс `?inline` — возможность Vite: вместо того чтобы вынести CSS в отдельный файл
> и подключить его тегом `<link>`, он возвращает содержимое **строкой**.
>
> Для content script это принципиально. Отдельный CSS-файл пришлось бы объявить
> в манифесте (`content_scripts[].css`), а тогда Chrome применил бы его **ко всей
> странице**, а не к нашему shadow root — то есть ровно то, чего мы избегаем.
> Внутрь shadow root стили можно доставить только через `<style>` в нём самом,
> а для этого нужна строка.

### Шаг 2. Кнопка при наведении

`src/ui/overlay-button.ts`. Главное решение — **единственный экземпляр**.

```ts
showFor(rect: DOMRect) {
  button.dataset.compact = String(rect.width < COMPACT_BELOW_PX)
  button.style.top = `${rect.top + INSET_PX}px`
  button.style.right = `${document.documentElement.clientWidth - rect.right + INSET_PX}px`
  button.dataset.visible = 'true'
}
```

> **Почему одна кнопка на страницу, а не по кнопке на картинку**
>
> Вариант «по кнопке на картинку» кажется проще: создал при инициализации, показал
> через `:hover` средствами CSS, никакого JS. Он не выдерживает столкновения
> с реальностью:
>
> - на странице бывают сотни картинок → сотни узлов DOM, каждый со своим пересчётом
>   стилей при прокрутке;
> - на бесконечной ленте их число растёт неограниченно, и память утекает;
> - кнопку нужно куда-то вставить — либо внутрь вёрстки сайта (сломается позиционирование
>   и наши стили окажутся под влиянием страницы), либо всё равно в свой слой,
>   и тогда позиции всё равно придётся считать в JS.
>
> Один экземпляр стоит одинаково при одной картинке и при тысяче.

> **Почему `position: fixed` и координаты прямо из `getBoundingClientRect()`**
>
> `getBoundingClientRect()` возвращает координаты **относительно окна просмотра**.
> `position: fixed` использует ту же систему координат. Значит, значения ставятся
> как есть, без пересчётов.
>
> Будь кнопка `absolute`, пришлось бы прибавлять `scrollX`/`scrollY` **и** учитывать
> все `transform` у предков картинки (внутри трансформированного предка `absolute`
> позиционируется от него, а не от документа). Это классический источник ошибок
> вида «кнопка на 200 пикселей левее картинки на некоторых сайтах».

> **Откуда `right`, а не `left`**
>
> Кнопка прижата к правому верхнему углу картинки. Для `position: fixed` свойство
> `right` отсчитывается от правого края окна, отсюда
> `clientWidth - rect.right + INSET_PX`.
>
> Через `left` пришлось бы знать ширину кнопки, а она зависит от того, компактная
> она или с подписью, — то есть от значения, которое мы только что вычислили.
> Через `right` ширина не нужна вовсе.

> **Откуда 148 px в `COMPACT_BELOW_PX`**
>
> Кнопка с подписью «Улучшить» занимает около 100 px, плюс отступы 8 px с каждой
> стороны — примерно 116 px. Порог взят с запасом ~30 px, чтобы кнопка не занимала
> почти всю ширину картинки и та оставалась видна. Ниже порога подпись скрывается
> и остаётся круглая кнопка-иконка 28×28.

> **Почему `hide()` ещё и уводит кнопку за экран**
>
> ```ts
> button.dataset.visible = 'false'
> button.style.top = '-9999px'
> ```
> Скрытие идёт через `opacity`, чтобы был плавный переход. Но элемент с `opacity: 0`
> **продолжает ловить клики**. Пока идёт 120-миллисекундная анимация исчезновения,
> невидимая кнопка перехватывала бы клик пользователя по странице. Увод за пределы
> окна это исключает.

### Шаг 3. Отслеживание картинки под курсором

`src/content/hover.ts` — ядро этапа.

```ts
const imageAtPoint = (x: number, y: number): HTMLImageElement | null | 'own-ui' => {
  const stack = document.elementsFromPoint(x, y)
  for (let i = 0; i < Math.min(stack.length, HIT_TEST_DEPTH); i++) {
    const element = stack[i]
    if (!element) break
    if (element === host) return 'own-ui'
    if (element instanceof HTMLImageElement) {
      return isEnhanceableImage(element) ? element : null
    }
  }
  return null
}
```

> **Почему возвращается три разных вещи, а не картинка или `null`**
>
> Состояний действительно три:
> - **картинка** — показать кнопку;
> - **`null`** — спрятать кнопку;
> - **`'own-ui'`** — курсор на нашей кнопке, **ничего не менять**.
>
> Без третьего состояния получается неприятный баг: пользователь ведёт мышь
> с картинки на кнопку, курсор уходит с картинки, хит-тест возвращает «не картинка»,
> кнопка прячется — ровно в момент, когда на неё пытаются нажать. Кнопка становится
> ненажимаемой.
>
> Работает это благодаря особенности `elementsFromPoint`: для содержимого shadow root
> она возвращает **host-элемент**. Нам достаточно сравнить с ним.

> **Откуда `HIT_TEST_DEPTH = 5`**
>
> Стек элементов под точкой на реальной странице бывает из полутора десятков элементов
> (вложенные контейнеры, обёртки сетки, `body`, `html`). Просматривать его целиком
> при каждом движении мыши — лишняя работа.
>
> Картинку перекрывают обычно один-два слоя: обёртка-ссылка, градиент подписи, невидимый
> перехватчик кликов. Пять — с запасом. Если картинка оказалась глубже пятого элемента,
> она, скорее всего, и не видна пользователю.

> **Почему `capture: true` у слушателя**
>
> ```ts
> document.addEventListener('mouseover', handlePointer, { capture: true, passive: true })
> ```
> Событие проходит две фазы: сначала вниз от `window` к цели (capture), потом обратно
> вверх (bubble). Обработчик страницы на промежуточном контейнере может вызвать
> `stopPropagation()` — и на фазе всплытия до `document` событие не дойдёт.
>
> На фазе перехвата мы получаем событие **раньше** любого обработчика страницы,
> и заглушить его нам никто не может.
>
> `passive: true` — обещание браузеру, что мы не вызовем `preventDefault()`. Позволяет
> не ждать наш обработчик перед прокруткой.

> **Почему `mouseover`, а не `mousemove`**
>
> `mousemove` срабатывает на каждое движение мыши — десятки раз в секунду. `mouseover`
> срабатывает только при **пересечении границы элемента**. Для задачи «что под курсором»
> этого достаточно, а вызовов на порядок меньше.
>
> Разница существенна: в обработчике мы вызываем `elementsFromPoint`, а это хит-тест,
> требующий актуальной компоновки страницы.

Пересчёт позиции при прокрутке:

```ts
const reposition = (): void => {
  if (!current) return
  if (frame) return
  frame = requestAnimationFrame(() => {
    frame = 0
    if (!current) return
    if (!current.isConnected) { setCurrent(null); return }
    const rect = current.getBoundingClientRect()
    if (rect.bottom <= 0 || rect.top >= window.innerHeight) { setCurrent(null); return }
    button.showFor(rect)
  })
}
```

> **Почему пересчёт через `requestAnimationFrame`, а не прямо в обработчике**
>
> События `scroll` приходят чаще, чем браузер отрисовывает кадры. Вызов
> `getBoundingClientRect()` в каждом из них — это **forced reflow**: браузер обязан
> прямо сейчас пересчитать компоновку, даже если только что её менял.
>
> Симптом при неправильной реализации — рывками идущая прокрутка на слабой машине,
> и виноватым будет выглядеть сайт, а не расширение.
>
> Флаг `frame` гарантирует, что за один кадр пересчёт произойдёт ровно один раз,
> сколько бы событий ни пришло.

> **Зачем проверки `isConnected` и выхода за границы окна**
>
> `isConnected` — картинку могли удалить из DOM во время прокрутки. Так работают
> виртуальные списки: элементы вне экрана уничтожаются. Кнопка осталась бы висеть,
> указывая на несуществующий элемент.
>
> Проверка границ окна — картинка уехала за верхний или нижний край. Кнопка
> позиционируется fixed и осталась бы висеть поверх постороннего содержимого.

> **Почему у `scroll` тоже `capture: true`**
>
> События `scroll` **не всплывают**. Если прокручивается вложенный контейнер
> (`overflow: auto`), а не окно, слушатель на `document` без `capture` их не увидит,
> и кнопка останется на месте, пока картинка уезжает. На фазе перехвата событие
> проходит через `document` в любом случае.

### Шаг 4. Тосты

`src/ui/toast.ts`. Два неочевидных места.

```ts
void toast.offsetHeight
toast.dataset.visible = 'true'
```

> **Зачем читать `offsetHeight` и никуда не сохранять**
>
> Чтобы CSS-переход проиграл, браузер должен **зафиксировать начальное состояние**
> (`opacity: 0`) до того, как мы поставим конечное. Только что созданный узел этого
> состояния ещё не имеет: если добавить его в DOM и тут же поменять `opacity`,
> браузер посчитает стили один раз — сразу с `opacity: 1` — и перехода не будет.
>
> Чтение `offsetHeight` принудительно вызывает пересчёт стилей и компоновки **прямо
> сейчас**. Это тот самый forced reflow, которого мы избегали при прокрутке, — но здесь
> он нужен намеренно и случается один раз на тост.
>
> **Почему не двойной `requestAnimationFrame`** (типичный совет в интернете):
> в невидимой вкладке кадры не отрисовываются и `rAF` **не вызывается вовсе**.
> Это не гипотеза — так и обнаружилось на стенде: тост висел в DOM с `opacity: 0`
> и удалялся по таймеру, ни разу не показавшись. Тост, вызванный фоновой операцией
> (а на этапе 3 очередь будет работать, пока пользователь на другой вкладке),
> не увидел бы никто.

```ts
const active: HTMLElement[] = []
// ...
active.push(toast)
while (active.length > MAX_VISIBLE) {
  const oldest = active[0]
  if (!oldest) break
  remove(oldest)
}
```

> **Почему список живых тостов ведётся отдельно, а не через `stack.children`**
>
> Первая версия была такой:
> ```ts
> while (stack.children.length > MAX_VISIBLE) { remove(stack.firstElementChild) }
> ```
> и **зависала намертво**. Причина: `remove()` не удаляет узел сразу — он сначала
> запускает анимацию исчезновения и убирает элемент через 200 мс. То есть после вызова
> `remove()` узел всё ещё в `stack.children`, длина не уменьшается, условие цикла
> остаётся истинным.
>
> Общий урок: **счётчик и отложенное удаление нельзя брать из одного источника.**

> **Почему текст вставляется через `textContent`, а не `innerHTML`**
>
> В тост попадают URL картинок и сообщения об ошибках — данные со страницы, которым
> нельзя доверять. `innerHTML` здесь был бы XSS внутри нашего же shadow root:
> достаточно картинки с именем файла, содержащим `<img onerror=...>`.
>
> `textContent` вставляет строку как текст, а не как разметку.

### Шаг 5. Контекстное меню

`src/background/context-menu.ts`.

```ts
chrome.runtime.onInstalled.addListener(() => {
  chrome.contextMenus.removeAll(() => {
    chrome.contextMenus.create({
      id: MENU_ID,
      title: 'Улучшить это изображение',
      contexts: ['image'],
    })
  })
})

chrome.contextMenus.onClicked.addListener((info, tab) => { /* ... */ })
```

> **Почему `create` — в `onInstalled`, а `onClicked` — на верхнем уровне**
>
> Это выглядит непоследовательно, но правильно, и различие принципиальное.
>
> **Пункты меню хранит браузер**, они переживают выгрузку service worker'а.
> Создавать их нужно один раз за установку. Вызов `create()` на верхнем уровне
> модуля выполнялся бы при каждом подъёме worker'а и со второго раза давал бы
> `Cannot create item with duplicate id`.
>
> **Слушатели не переживают выгрузку.** Их нужно регистрировать при каждом подъёме,
> синхронно — иначе клик по пункту меню будет некому обработать (общее правило MV3
> из этапа 0).
>
> Ошибка в любую сторону даёт один и тот же симптом «пункт меню не работает», но
> лечится противоположно.

> **Зачем `removeAll` перед `create`**
>
> `onInstalled` срабатывает не только при первой установке, но и при **обновлении**
> расширения. Пункт с тем же `id` при этом уже зарегистрирован браузером — `create`
> упадёт. `removeAll` делает операцию идемпотентной.

> **Зачем передавать `frameId`, если мы не внедряемся в iframe**
>
> ```ts
> void sendToTab(tab.id, 'CONTEXT_MENU_ENHANCE', { srcUrl: info.srcUrl }, info.frameId ?? 0)
> ```
> Chrome показывает наш пункт меню и для картинок **внутри iframe**, а content script
> туда не внедряется (`all_frames: false`). Если бы мы всегда слали в главный фрейм
> (`frameId: 0`), тот получил бы URL картинки, которой у него нет, и показал бы
> пользователю «картинка не найдена» — сообщение, которое ничего не объясняет.
>
> С настоящим `frameId` сообщение честно не доставляется, мы это логируем и знаем
> реальную причину. Обработка этого случая по-человечески — этап 7.

### Шаг 6. Замыкаем путь

Заглушка в `src/background/index.ts`:

```ts
ENHANCE_IMAGE: (payload, sender) => {
  log.info(`Запрос на улучшение из вкладки ${sender.tab?.id ?? '?'} (${payload.trigger}): ...`)
  return {
    accepted: false,
    message: `Картинка найдена: ${payload.naturalWidth}×${payload.naturalHeight}. Обработка появится на этапе 2.`,
  }
}
```

> **Зачем писать обработчик до того, как есть что обрабатывать**
>
> Это не формальность. Сквозной путь «клик → content script → service worker → ответ →
> тост» состоит из шести звеньев, и каждое может быть сломано. Замкнув его на заглушке,
> мы проверяем все шесть **до** появления сложной логики.
>
> Когда на этапе 2 появится реальный пайплайн, встраивать его будет некуда, кроме как
> в это место, а остальной код менять не придётся вовсе.
>
> Обратный порядок — сначала написать обработку, потом подключать UI — приводит
> к отладке двух незнакомых вещей одновременно.

Регистрация обработчиков в content script делается **синхронно**, до `await`:

```ts
bootstrapUi()          // ← регистрирует слушатели сообщений

async function bootstrap() {
  const settings = await getSettings()
  // ...
}
void bootstrap()
```

> **То же правило, что в service worker'е, но по другой причине**
>
> Content script не выгружается, но пользователь может нажать правой кнопкой на картинку
> через долю секунды после загрузки страницы. Если бы `registerMessageHandlers` стоял
> после `await getSettings()`, сообщение из контекстного меню пришло бы раньше слушателя
> и потерялось.
>
> Воспроизводилось бы это только на медленной машине и только при быстром клике —
> то есть у пользователя, а не у разработчика.

## Проверка

### Автоматическая проверка на стенде

Прежде чем идти в браузер, логику UI удобно проверить на локальной странице, подсунув
content script'у заглушку `chrome` API. Приём стоит знать — он экономит много времени
на следующих этапах.

Суть: поднять локальный HTTP-сервер, который отдаёт (а) тестовую страницу с картинками
разных размеров и в разных обёртках, (б) собранный `dist/content.js`. На странице перед
подключением скрипта объявляется объект `chrome` с нужным минимумом:

```js
window.chrome = {
  runtime: {
    getManifest: () => ({ version: '0.1.0' }),
    sendMessage: async (msg) => {
      if (msg.kind === 'ENHANCE_IMAGE') return { accepted: false, message: '...' }
      return undefined
    },
    onMessage: { addListener: (fn) => listeners.push(fn) },
  },
  storage: {
    sync: { get: async (d) => d, set: async () => {} },
    onChanged: { addListener: () => {} },
  },
}
```

Дальше в консоли можно проверять поведение напрямую: разворачивать shadow root
(в dev-сборке он открыт), эмулировать наведение и читать состояние кнопки.

Что было проверено таким образом на этом этапе:

| Проверка | Результат |
|---|---|
| Фильтр по размеру | 6 картинок на странице, обнаружено 5 — сорокапиксельная отсеяна |
| Позиция кнопки | Картинка `top: 75, right: 324` при `clientWidth: 1265` → кнопка `top: 83px, right: 949px`. Совпадает с формулой |
| Компактный режим | Картинка 300 px → с подписью; 100 px → компактная |
| Картинка под прозрачным слоем | Стек: `[span.cover, img, span.covered, div.row]` → кнопка показана |
| Наведение на саму кнопку | Кнопка не прячется |
| Клик по кнопке | Навигации нет; обработчик документа события не получил; сообщение `ENHANCE_IMAGE` с верным payload; тост показан |
| Контекстное меню | `handled: true`, рамка вокруг картинки `top: 73, left: 22, w: 304` при картинке `top: 75, left: 24, w: 300` — отступ 2 px верен |
| Контекстное меню с чужим URL | `handled: false` и тост с ошибкой |
| Ограничение числа тостов | Четыре подряд → на экране три |

Пересчёт позиции при прокрутке на стенде проверить не удалось: он привязан
к `requestAnimationFrame`, а в неотрисовываемой вкладке кадров нет. Его нужно
проверять руками (пункт 5 ниже).

### Проверка в браузере

**1. Собрать и загрузить.**

```bash
npm run dev
```

В `chrome://extensions` нажать кнопку перезагрузки на карточке расширения (после
добавления разрешения `contextMenus` расширение нужно перезагрузить, автоперезагрузка
это сделает сама, если `npm run dev` уже запущен).

**2. Кнопка при наведении.** Открыть любой сайт с картинками. Навести курсор
на крупную картинку — в её правом верхнем углу должна появиться тёмная кнопка
«↑ Улучшить» с плавным появлением. Увести курсор — кнопка исчезает.

Навести на маленькую иконку (аватарку, логотип) — кнопки быть **не должно**.

**3. Клик.** Нажать кнопку. Внизу справа появится тост:
«Картинка найдена: 1920×1080. Обработка появится на этапе 2.»
Числа — реальные размеры файла, а не отображаемые.

Если картинка была ссылкой — переход **не должен** произойти.

**4. Контекстное меню.** Правый клик по картинке → в меню есть пункт
«Улучшить это изображение». Выбрать его. Вокруг картинки на полторы секунды появится
синяя рамка, затем тот же тост.

**5. Прокрутка.** Навести курсор на картинку так, чтобы кнопка появилась,
и прокрутить страницу колесом, не двигая мышь. Кнопка должна **ехать вместе
с картинкой**, а не оставаться на месте. Когда картинка уйдёт за край экрана,
кнопка должна исчезнуть.

**6. Popup.** Открыть popup на странице с картинками. Строки «Изображений на странице»
и «Видео на странице» должны показывать числа. На странице `chrome://extensions`
там будет «нет доступа» — это правильно, туда content script не внедряется.

**7. Консоли.** В консоли страницы:

```
[ImageEnhancer:content] Запрос на улучшение (overlay): https://...
```

В консоли service worker'а:

```
[ImageEnhancer:background] Запрос на улучшение из вкладки 5 (overlay): 1920×1080, https://...
```

**8. Проверка изоляции стилей.** Открыть сайт с агрессивным CSS — подойдёт любой
с тёмной темой и своими стилями кнопок. Наша кнопка должна выглядеть **одинаково**
на всех сайтах. Если на каком-то она поехала — это баг изоляции, и начинать нужно
с инлайновых стилей host-элемента.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Кнопка не появляется вообще | Content script не загрузился либо упал до создания UI | Смотреть консоль страницы; проверить, что `bootstrapUi()` вызывается синхронно |
| Кнопка появляется, но нажать невозможно — исчезает при подведении курсора | Нет обработки состояния «курсор на нашем UI» | `elementsFromPoint` возвращает host-элемент; сравнивать с ним и не сбрасывать текущую картинку |
| Кнопка есть, но клики по странице перестали работать | У слоя нет `pointer-events: none` | Слой растянут на весь экран и перехватывает всё |
| Клик по кнопке закрывает галерею / уводит по маршруту | Нет `stopPropagation` | Событие всплывает до `document`, где его видят делегированные обработчики страницы |
| Кнопка не появляется на картинках в галерее, хотя на обычных работает | Картинка накрыта прозрачным слоем, а логика смотрит на `event.target` | Хит-тест через `elementsFromPoint` |
| Кнопка «отстаёт» при прокрутке или дёргается | Пересчёт позиции не привязан к кадру | `requestAnimationFrame` с флагом, не более одного пересчёта за кадр |
| Кнопка остаётся висеть после прокрутки в ленте | Картинку удалили из DOM (виртуальный список) | Проверять `isConnected` перед пересчётом |
| Тост не появляется, но в DOM он есть с `opacity: 0` | Переход запускался через `rAF`, а вкладка не отрисовывает кадры | Принудительный пересчёт: `void node.offsetHeight` перед сменой класса |
| Страница зависает при показе тостов | Цикл вытеснения считает узлы в DOM, а удаление отложено | Вести отдельный список живых элементов |
| Наш UI съехал или спрятался на конкретном сайте | Правило страницы вида `body * { position: static !important }` достало host-элемент | Инлайновые стили host'а с `!important` |
| Наши стили «протекли» на страницу | UI создан без Shadow DOM либо стили объявлены в `content_scripts[].css` | CSS должен попадать внутрь shadow root через `<style>`, а не в манифест |
| `Cannot create item with duplicate id` в консоли service worker'а | `contextMenus.create` вызывается на верхнем уровне модуля | Создавать пункт только в `onInstalled` |
| Пункт меню есть, но при клике ничего не происходит | Слушатель `onClicked` зарегистрирован асинхронно и не пережил подъём worker'а | Регистрировать слушатель синхронно, на верхнем уровне |
| Контекстное меню отвечает «не удалось найти картинку» | Картинка внутри iframe, куда content script не внедряется | Ожидаемо при `all_frames: false`; смотреть `frameId` в логе |
| Popup показывает «нет доступа» на обычном сайте | Content script ещё не загрузился либо страница только что открыта | Обновить страницу; на служебных страницах это правильное поведение |
| Кнопка появляется на трекинг-пикселях и иконках | Порог `MIN_SIDE_PX` слишком мал или проверяется только `naturalWidth` | Проверять и `naturalWidth`, и отображаемый размер |

| `src/ui/highlight.ts` | Рамка вокруг картинки — обратная связь для действий не по наведению |
| `src/ui/styles/content.css` | Стили UI поверх страницы, попадают в shadow root строкой |

### Новое в контракте сообщений

| Сообщение | Направление | Назначение |
|---|---|---|
| `ENHANCE_IMAGE` | content → service worker | Запрос на улучшение. Пока заглушка |
| `CONTEXT_MENU_ENHANCE` | service worker → content | Передача выбора из контекстного меню |
| `SCAN_PAGE` | popup → content | Сколько картинок и видео на странице |

Появилась функция `sendToTab` — второй канал отправки, не взаимозаменяемый
с `sendToBackground`.

### Новые API

`attachShadow`, `document.elementsFromPoint`, `chrome.contextMenus` (`create`,
`removeAll`, `onClicked`), `chrome.tabs.sendMessage`, `requestAnimationFrame`,
`Element.isConnected`, Vite-суффикс `?inline`.

### Новое разрешение

`contextMenus`. Оно не добавляет предупреждения при установке — Chrome считает его
безопасным.

### Что заложено под видео

Без изменений с этапа 0: `<video>` находится и считается (popup показывает их число),
UI для них не рендерится, флаг `VIDEO_ENHANCEMENT_ENABLED` остаётся `false`.

### Что будет дальше

**Этап 2 — классический апскейл, режим «одно изображение».** Заглушка `ENHANCE_IMAGE`
заменится настоящим пайплайном: получить пиксели картинки, увеличить их интерполяцией
(bicubic/Lanczos), вернуть результат и подменить картинку на странице или предложить
скачать.

Там впервые всплывут две темы, которые определят весь остаток проекта: **tainted canvas**
(почему картинку с чужого домена нельзя просто прочитать) и **где именно выполнять
вычисления**, раз content script занимать нельзя.
