# Этап 4: Вынос вычислений в Web Worker

## Цель этапа

Убрать вычисления из главного потока страницы.

Этапы 2 и 3 работали, но с ценой, которую этап 3 показал в полный рост: на время
обработки страница переставала отвечать. Прокрутка дёргалась, кнопка «Отмена»
срабатывала с задержкой в полсекунды, а параллелизм в очереди был бессмысленным —
задачи всё равно выстраивались в один поток.

К концу этапа те же вычисления идут в отдельных потоках: главный поток занят только
получением пикселей и подменой картинки, отмена срабатывает мгновенно, а очередь
действительно обрабатывает несколько картинок одновременно.

Заодно этот этап — проверка решения, принятого на этапе 2: модуль `core/enhance/`
писался так, чтобы переехать в воркер без правок. Сейчас выяснится, получилось ли.

---

## Теория

### Что такое Web Worker и чего он не умеет

**Web Worker** — отдельный поток JavaScript. У него:

- собственный стек, куча и цикл событий;
- **нет доступа к DOM** — ни `document`, ни `window`, ни элементов страницы;
- нет общих переменных с главным потоком: общение только сообщениями;
- есть `fetch`, таймеры, `OffscreenCanvas`, `ImageBitmap`, `WebAssembly`, WebGPU.

Отсутствие DOM — не недоработка, а условие безопасности. DOM не потокобезопасен:
если бы два потока могли одновременно менять дерево элементов, потребовались бы
блокировки, и любая ошибка приводила бы к зависанию всей страницы. Запретив воркеру
DOM, браузер убирает целый класс проблем.

Для нас это ограничение оказалось необременительным: `core/enhance/` с этапа 2
не обращается к DOM вовсе — он работает с `OffscreenCanvas`, который есть и в воркере.
Именно ради этого момента он так и писался.

### Structured clone и transferable objects

Сообщения между потоками не разделяют память: объект **копируется** по алгоритму
structured clone. Он умеет больше, чем JSON (`Map`, `Set`, `Date`, `Blob`,
`ImageBitmap`, циклические ссылки), но копирование остаётся копированием.

Для картинки 4000×3000 копия — это 48 МБ, которые надо выделить и заполнить.
Дважды: туда и обратно.

**Transferable objects** решают это. Некоторые объекты (`ArrayBuffer`, `ImageBitmap`,
`OffscreenCanvas`, `MessagePort`) можно не копировать, а **передать владение**:

```js
worker.postMessage({ bitmap }, [bitmap])
//                              ↑ список передаваемых объектов
```

Данные физически не двигаются — меняется владелец. Стоимость не зависит от размера.

Плата: **в передающем потоке объект становится недоступен** (detached).
`bitmap.width` вернёт 0, любая операция с ним бросит исключение. Это не мелочь,
а то, что придётся учесть в коде: размеры нужно запомнить до передачи, а освобождать
объект теперь обязан получатель.

### Главное препятствие: JSON между content script и service worker

Естественная схема для MV3 выглядела бы так: content script отдаёт картинку
service worker'у, тот — в воркер, обратно приходит результат.

Она не работает, и причина конкретная: **`chrome.runtime.sendMessage` сериализует
сообщение в JSON**, а не structured clone. Через JSON не проходят ни `ImageBitmap`,
ни `Blob`, ни `ArrayBuffer` — они превратятся в `{}`. Transferable-объекты там
невозможны в принципе.

Плюс к этому service worker в MV3 **вообще не имеет конструктора `Worker`**.

Штатное решение обоих ограничений — **Offscreen Document**: невидимая страница
расширения с полноценным DOM и правом создавать воркеры. Но она не решает главного:
пиксели всё равно надо как-то туда доставить, а канал между контекстами всё тот же
JSON. Остаются два пути:

| Путь | Цена |
|---|---|
| Скачать картинку заново по URL уже в offscreen-документе | Лишняя загрузка на каждое действие. И — важнее — **другой набор доступных картинок**: страница расширения обращается к чужому домену, и без `host_permissions` ей ответят не всегда. Картинки, доступные самой странице, перестали бы обрабатываться. Это регресс |
| Перегнать пиксели в строку base64 | Для 24 Мп это строка на сотню мегабайт, которую ещё надо сериализовать в JSON. Неприменимо |

Вывод: **пиксели надо оставить там, где они получены** — в content script, — и создать
воркер прямо оттуда.

### Почему content script не может создать воркер обычным способом

```js
new Worker(chrome.runtime.getURL('enhance.worker.js'))   // ← упадёт
```

Конструктор `Worker` требует, чтобы скрипт был **того же источника**, что и создающий
контекст. Content script исполняется в изолированном мире, но для проверки источника
относится к **источнику страницы** (`https://сайт`), а файл лежит на
`chrome-extension://<id>`. Источники разные — отказ. Добавление файла
в `web_accessible_resources` это не меняет: оно разрешает загрузку ресурса, а не
снимает требование одинакового источника.

**Обходной путь — blob-URL.** Если код воркера уже есть в виде строки, из него можно
сделать `Blob` и создать воркер из `URL.createObjectURL(blob)`. Blob-URL наследует
источник создавшего его контекста, то есть страницы, и требование выполняется.

Vite делает это одной строкой:

```ts
import EnhanceWorker from '@/workers/enhance.worker?worker&inline'
```

Суффикс `?worker` просит собрать файл как отдельный граф модулей, `&inline` — встроить
результат в бандл строкой вместо отдельного файла. На выходе получается готовый
конструктор. Побочные выгоды: не нужен `web_accessible_resources`, не нужен сетевой
запрос за кодом воркера, нечему рассинхронизироваться между файлами.

Ограничение: страница с политикой безопасности, запрещающей blob-воркеры
(`worker-src`), заблокирует создание. Поэтому резервный путь — вычисления
в потоке страницы, как на этапах 2-3, — остаётся в коде.

### Пул воркеров: зачем он и почему не «воркер на задачу»

Создание воркера стоит времени (новый поток, новый контекст JavaScript) и памяти
(несколько мегабайт на контекст). Создавать его на каждую картинку — значит платить
эту цену многократно, причём на мелких картинках создание может стоить дороже самой
работы.

Пул создаёт воркеры один раз и переиспользует. Из этого следуют две вещи, которые
надо предусмотреть:

1. **Ответы надо сопоставлять с запросами.** Обработчик `message` висит на воркере,
   который уже обслуживал другие задачи; без идентификатора запроса легко поймать
   чужой ответ.
2. **Состояние воркера переживает задачи.** Для классического апскейла состояния нет,
   но на этапе 5 в воркере будет жить загруженная ML-модель — и это станет
   преимуществом пула, а не проблемой.

**Сколько воркеров.** Половина логических ядер, но не больше четырёх.

- *Половина, а не все*: браузеру нужны потоки на отрисовку, композитинг, сеть,
  а системе — на всё остальное. Заняв все ядра, получим отзывчивость хуже при том же
  итоговом времени.
- *Потолок 4* — по памяти, а не по процессору. Каждая задача в работе держит
  промежуточный буфер (66 МБ для 1920×1080 → 3840×2160) плюс исходный `ImageBitmap`
  плюс результат. Четыре одновременно — уже сотни мегабайт.

### Отмена: почему только `terminate()`

`AbortController` из этапа 3 поднимает флаг, а прерывание происходит там, где код
этот флаг проверяет. Фильтр Ланцоша — сплошной цикл по пикселям: он не проверяет
флагов и не читает сообщений, пока не досчитает. Отправить воркеру «отменись»
бесполезно — сообщение он прочитает уже после завершения работы.

`worker.terminate()` убивает поток немедленно, вместе со всей занятой им памятью.
Это грубо, но здесь единственно рабочее. Цена — воркер потерян и его надо создать
заново; в пуле это делается сразу, чтобы пул не усыхал с каждой отменой.

---

## Что делаем

1. Пишем воркер: принимает `ImageBitmap` и параметры, возвращает `Blob`.
2. Пишем пул: размер по числу ядер, очередь ожидающих, сопоставление по идентификатору,
   отмена через `terminate` с заменой.
3. Пишем точку выбора режима: воркеры либо вычисления в потоке страницы.
4. Правим владение `ImageBitmap`: после передачи он принадлежит воркеру.
5. Снимаем ограничение параллелизма в очереди этапа 3.
6. Измеряем: занятость главного потока с воркерами и без.

## Пошаговая инструкция

### Шаг 1. Воркер

```ts
interface WorkerScope {
  postMessage(message: unknown, transfer?: Transferable[]): void
  addEventListener(type: 'message', listener: (event: MessageEvent) => void): void
}
const scope = self as unknown as WorkerScope
```

> **Почему область видимости описана вручную**
>
> Полные типы воркера живут в библиотеке `WebWorker`, а она конфликтует с `DOM`
> в пределах одного `tsconfig`: десятки одинаковых имён с разными сигнатурами
> (`self`, `location`, `fetch`, `addEventListener`...). Правильное решение —
> отдельный `tsconfig.worker.json` и вторая команда проверки типов.
>
> Ради одного небольшого файла это дороже, чем описать три нужных метода локально.
> Когда воркер вырастет (этап 5, ONNX Runtime), решение стоит пересмотреть —
> и это записано в `src/workers/README.md`, чтобы не забыть.

```ts
} finally {
  request.bitmap.close()
}
```

> **Почему освобождает воркер, а не отправитель**
>
> Картинка пришла сюда вместе с **владением**: в отправляющем потоке она отсоединена
> и недоступна. Освободить её может только тот, кто владеет.
>
> Это правило пришлось явно закрепить и на другой стороне — см. шаг 4.

```ts
error: error instanceof Error ? error.message : String(error)
```

> **Почему наружу уходит строка, а не объект ошибки**
>
> `Error` не переживает structured clone целиком: тип и стек теряются, остаётся
> сообщение. Пытаться передать `error` как есть — значит получить на той стороне
> объект, у которого `instanceof RangeError` уже неверен, а вся логика разбора
> ошибок из этапа 2 на этом построена.
>
> Честнее отдать строку и разбирать её на понятную формулировку в вызывающем коде.

### Шаг 2. Пул

```ts
const acquire = (): Promise<Slot> => {
  const free = slots.find((slot) => !slot.busy)
  if (free) {
    free.busy = true
    return Promise.resolve(free)
  }
  return new Promise((resolve) => waiting.push(resolve))
}

const release = (slot: Slot): void => {
  const next = waiting.shift()
  if (next) {
    next(slot)      // busy НЕ сбрасываем: воркер сразу уходит следующему
    return
  }
  slot.busy = false
}
```

> **Почему при передаче воркера следующему в очереди `busy` не сбрасывается**
>
> Если сбросить `busy = false`, а потом отдать слот ожидающему, между этими двумя
> действиями появится момент, когда слот считается свободным. Другой вызов `acquire()`
> в этот момент заберёт тот же слот — и две задачи попадут в один воркер одновременно.
>
> Ошибка тонкая: она не проявится при параллелизме 1 и будет плавающей при большем.

```ts
function onMessage(event: MessageEvent): void {
  const data = event.data as EnhanceWorkerResponse
  if (data.id !== id) return
  // ...
}
```

> **Зачем сверять идентификатор**
>
> Воркер переиспользуется. Обработчик, повешенный для текущей задачи, физически
> может получить ответ на предыдущую — например, если предыдущая была отменена
> по таймауту на нашей стороне, но воркер всё-таки досчитал и ответил.
>
> Без проверки такой хвост был бы принят за результат текущей задачи: пользователь
> получил бы на странице не ту картинку, которую просил. Отладить это по симптомам
> почти невозможно.

```ts
const recycle = (slot: Slot): void => {
  slot.worker.terminate()
  const replacement = spawn()
  if (replacement) {
    slot.worker = replacement
    release(slot)
    return
  }
  const index = slots.indexOf(slot)
  if (index >= 0) slots.splice(index, 1)
}
```

> **Почему убитый воркер сразу заменяется**
>
> `terminate()` вызывается при каждой отмене и при каждой ошибке воркера. Без замены
> пул усыхал бы: три отмены подряд — и от пула из четырёх воркеров остался бы один,
> причём молча.
>
> Ветка со `splice` — на случай, когда создать замену не удалось (кончилась память).
> Слот убирается из пула, чтобы в него не пытались отправлять задачи. Пул продолжает
> работать в уменьшенном составе, а не падает целиком.

```ts
slot.worker.postMessage(request, [input.bitmap])
```

> **Второй аргумент — не оптимизация «на всякий случай»**
>
> Без него `ImageBitmap` был бы **скопирован**: для картинки 4000×3000 браузер выделил
> бы и заполнил ещё 48 МБ. С передачей владения копирования не происходит вовсе.
>
> Проверить, что передача работает, легко: после `postMessage` значение
> `input.bitmap.width` становится 0.

### Шаг 3. Выбор режима

```ts
let pool: EnhancePool | null | undefined
```

> **Почему три состояния, а не два**
>
> `undefined` — пул ещё не пробовали создать. `null` — попытка была и не удалась.
>
> Различать нужно, чтобы не повторять неудачную попытку на каждой картинке: причина
> отказа — политика безопасности страницы, и она не изменится за время жизни страницы.
> Без различения на странице с запретом blob-воркеров мы бы создавали и роняли
> воркер перед каждой картинкой.

```ts
if (pool) {
  return pool.run(input, options, signal)
}
try {
  return await createEnhancer(options.level).enhance(input, options, signal)
} finally {
  input.bitmap.close()
}
```

> **Почему нет отката с воркера на поток страницы**
>
> Соблазн такой: если воркер упал — досчитать на месте, пользователь ничего
> не заметит. Сделать это нельзя: картинка уже передана воркеру **вместе
> с владением**, в этом потоке она отсоединена. Повторить работу физически не на чем.
>
> Откат возможен только *до* отправки — то есть на уровне «пул вообще не создался».
> Именно так он и реализован.

### Шаг 4. Владение `ImageBitmap`

```ts
const sourceSize = `${bitmap.width}×${bitmap.height}`   // ДО передачи
await yieldUntilPainted()
handedOff = true
const result = await runEnhance({ bitmap, sourceUrl }, options, signal)
```

> **Почему размеры запоминаются заранее — реальная ошибка этого этапа**
>
> После `postMessage` с transferable исходный объект отсоединён, и `bitmap.width`
> возвращает 0. В логе появлялись строки вида «0×0 → 3840×2160».
>
> Это безобидно выглядящий симптом очень небезобидного класса ошибок: любой код,
> обращающийся к переданному объекту, получит не исключение, а тихо неверные данные.

```ts
} finally {
  if (!handedOff) bitmap?.close()
}
```

> **Зачем флаг**
>
> Прежний код звал `close()` безусловно. После введения воркеров владельцем стал
> воркер, и вызов оказался обращением к чужому объекту.
>
> Флаг фиксирует правило явно: содержащий поток освобождает картинку, только если
> так и не передал её дальше — например, если исключение случилось между получением
> пикселей и отправкой.

### Шаг 5. Параллелизм

Константа `DEFAULT_CONCURRENCY = 1` из этапа 3 удалена, вместо неё:

```ts
export function resolveConcurrency(): number {
  if (pool === undefined) pool = createEnhancePool()
  return pool ? pool.size : 1
}
```

> **Почему без воркеров параллелизм по-прежнему строго 1**
>
> Ничего не изменилось: вычисления синхронные и в единственном потоке. Две задачи
> «одновременно» лишь удвоят пик памяти, не сократив общее время ни на миллисекунду.

Строка `await yieldUntilPainted()` в очереди осталась, хотя главный поток теперь
свободен:

> **Зачем возвращать кадр, если поток и так не занят**
>
> Две причины:
> 1. **Резервный режим.** Если воркеры недоступны, вычисления снова идут в главном
>    потоке, и без возврата кадра очередь выполнилась бы одним куском.
> 2. **Даже с воркерами** получение пикселей, подмена картинки и обновление панели
>    выполняются в главном потоке. На быстрых мелких картинках задачи заканчиваются
>    плотнее, чем браузер успевает рисовать, и прогресс перескакивал бы рывками.

## Проверка

### Измерение занятости главного потока

Простой и надёжный способ: запустить таймер на 10 мс и записывать **фактические**
интервалы между тиками. Пока главный поток занят, таймер не срабатывает — и в записи
появляется большая пауза.

```js
const gaps = []
let last = performance.now()
const timer = setInterval(() => {
  const now = performance.now()
  gaps.push(now - last)
  last = now
}, 10)
// ... запускаем обработку, ждём завершения
clearInterval(timer)
Math.max(...gaps)   // самая длинная пауза
```

Чтобы сравнение было честным, нужен и второй замер — с заведомо недоступными
воркерами. На стенде это делается подменой конструктора до загрузки content script:

```js
if (location.search.includes('noworker')) {
  window.Worker = function () { throw new Error('worker blocked by harness') }
}
```

### Результаты замеров

Картинка 1400×1000 → 2800×2000:

| | Вычисления в воркере | Резервный путь |
|---|---|---|
| Максимальная пауза главного потока | **12 мс** | **231 мс** |
| Сообщённое время работы | 253 мс | 1261 мс |

231 мс совпадает с замером фильтра из этапа 2 для этого размера — то есть зонд
действительно измеряет то, что нужно.

Режим «вся страница», 15 картинок, 20 логических ядер:

| | Этап 3 | Этап 4 |
|---|---|---|
| Максимальная пауза главного потока | 231 мс | **11 мс** |
| Параллелизм | 1 | 4 |
| Общее время прогона на стенде | ~15 с | **651 мс** |

> Разница в **общем времени** сильно преувеличена артефактом стенда: на главном
> потоке `convertToBlob` в среде без композитинга стабильно стоит ~1015 мс независимо
> от размера холста (описано в документации этапа 2), а в воркере — нет.
> Достоверная величина здесь — **паузы главного потока**.

Отмена: остановка через **85 мс** после нажатия против ожидания конца текущей картинки
(до 600 мс) на этапе 3. Следующий запуск после отмены отработал 13 из 13 — пул
восстановился после `terminate()`.

### Проверка в браузере

```bash
npm run dev
```

1. **Режим воркеров активен.** Открыть консоль страницы. При первой обработке
   появится строка вида `[ImageEnhancer:runner] Вычисления в воркерах, размер пула: 4`.

2. **Отзывчивость.** Запустить режим «вся страница» на странице с десятком картинок
   и **прокручивать страницу во время обработки**. Прокрутка должна оставаться плавной.
   Это главная проверка этапа: на этапе 3 она дёргалась.

3. **Отмена.** Нажать «Отмена» на середине очереди — панель должна перейти
   в «Обработка остановлена» практически сразу, а не через полсекунды.

4. **Повторный запуск после отмены.** Запустить снова — должно работать. Если пул
   не восстанавливается после `terminate()`, очередь молча зависнет на первой задаче.

5. **Воркеры в DevTools.** Вкладка Sources → панель Threads (или Workers) — при
   активной обработке там видны воркеры. Их число должно совпадать с размером пула
   из лога.

6. **Резервный путь.** Проверяется на сайте со строгой политикой безопасности
   (`worker-src`). В консоли появится
   `[ImageEnhancer:runner] Воркеры недоступны, считаю в потоке страницы`,
   и поведение вернётся к этапу 3 — включая рывки при прокрутке.

7. **Память.** Открыть Task Manager Chrome (`Shift+Esc`) и посмотреть на вкладку
   во время обработки очереди. Расход вырастет, но должен вернуться после
   «Вернуть все».

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `Failed to construct 'Worker': Script at 'chrome-extension://...' cannot be accessed from origin '...'` | Воркер создаётся из файла расширения | Только blob-URL: `?worker&inline` |
| В логе «0×0 → 3840×2160» | Размеры читаются после передачи, объект уже отсоединён | Запоминать размеры до `postMessage` |
| `The ImageBitmap could not be allocated` или тихо неверные данные | Обращение к переданному `ImageBitmap` | Владение переходит получателю; отправитель его больше не трогает |
| Пик памяти вырос вдвое, скорость не изменилась | `ImageBitmap` не указан в списке transferable и копируется | Второй аргумент `postMessage` |
| На странице оказалась не та картинка, которую улучшали | Обработчик принял ответ на предыдущий запрос | Сверять идентификатор запроса |
| Две задачи попали в один воркер | В `release` сбрасывается `busy` до передачи слота ожидающему | Не сбрасывать `busy`, если слот уходит следующему |
| Пул усыхает после каждой отмены | `terminate()` без создания замены | Заменять воркер сразу |
| Очередь зависает после отмены | Слот убит, но не возвращён в оборот | `release` после замены |
| Отмена не срабатывает, пока картинка не досчитается | Отмена реализована сообщением в воркер | Синхронный цикл сообщений не читает; только `terminate()` |
| Воркер не создаётся на конкретном сайте | Политика безопасности страницы запрещает blob-воркеры | Ожидаемо; работает резервный путь |
| Ошибка воркера приходит как пустой объект | `Error` не переживает structured clone | Передавать строку сообщения |
| Прогресс в очереди перескакивает рывками | Убран `yieldUntilPainted` между задачами | Вернуть: главный поток всё ещё занят подменой картинок и обновлением панели |
| `WebWorker` и `DOM` в одном `tsconfig` дают сотни ошибок о конфликте типов | Обе библиотеки объявляют одинаковые имена | Отдельный `tsconfig.worker.json` либо локальное описание нужных методов |

## Итог этапа

### Что появилось в архитектуре

| Модуль | Роль |
|---|---|
| `src/workers/enhance.worker.ts` | Вычисления вне главного потока. Ни DOM, ни chrome API |
| `src/content/worker-pool.ts` | Пул: размер по ядрам, очередь ожидающих, отмена через `terminate` с заменой |
| `src/content/enhance-runner.ts` | Выбор режима и правило владения `ImageBitmap` |

Модуль `core/enhance/` переехал в воркер **без единой правки**. Решение этапа 2 —
писать его на `OffscreenCanvas` и не трогать DOM — окупилось ровно так, как
предполагалось.

### Новые API

`Worker`, `postMessage` с transferable, `Worker.terminate()`,
`navigator.hardwareConcurrency`, Vite-суффикс `?worker&inline`.

### Новых разрешений нет

Blob-URL снял бы нужду и в `web_accessible_resources`, если бы она возникла.

### Чего в архитектуре так и не появилось

**Offscreen Document.** Он планировался с этапа 0 и не понадобился: канал между
content script и service worker сериализует сообщения в JSON, поэтому доставить туда
пиксели можно было бы только повторной загрузкой картинки (регресс по CORS) или
строкой base64 (неприменимо). Прогноз в `src/workers/README.md` исправлен.

Скорее всего, offscreen понадобится на **этапе 7**: загрузка картинки в обход CORS
возможна только из контекста расширения с `host_permissions`, и там же встанет
обратная задача — вернуть результат в страницу через тот же JSON-канал.

### Что заложено под видео

Пул и очередь принимают любые асинхронные задачи. Для видео задачами станут кадры,
а `terminate()` останется тем же способом остановить долгую обработку —
с той разницей, что там понадобится сохранять уже обработанную часть.

### Что будет дальше

**Этап 5 — ML-апскейл.** ONNX Runtime Web, WebGPU с фоллбеком на WASM SIMD, лёгкая
SR-модель класса FSRCNN/ESPCN, реальная детекция возможностей устройства
в `core/device/`.

Инфраструктура для этого готова: воркер есть, интерфейс `ImageEnhancer` ждёт второй
реализации, точка выбора в `createEnhancer` — одна. Появятся новые сложности:
модель нужно загрузить один раз и держать в памяти воркера, WASM требует послабления
в политике безопасности расширения (`wasm-unsafe-eval`), а проверка «есть ли WebGPU»
перестанет сводиться к наличию `navigator.gpu`.
