# ImageEnhancer — документация проекта

Браузерное расширение (Manifest V3), которое улучшает качество изображений прямо на веб-странице:
апскейл, шумоподавление, резкость. Все вычисления — **локально, на машине пользователя**.
Картинки никуда не отправляются.

Разработка идёт этапами. Каждый этап закрывается двумя документами в этой папке (`docs/`):
кратким `..._Impl.md` для того, кто хочет быстро понять «что тут сделано», и подробным
`..._Guide.md` для того, кто хочет разобраться, **почему** сделано именно так.

---

## Технический стек

- **Manifest V3**, целевой браузер — Chrome 116+
- **Язык:** TypeScript 7 (нативный компилятор, используется только для проверки типов)
- **Сборка:** Vite 8 (бандлер под капотом — Rolldown)
- **Обработка изображений:**
  - базовый уровень — Canvas 2D API, классическая интерполяция (bicubic/Lanczos)
  - продвинутый уровень — ONNX Runtime Web, WebGPU с фоллбеком на WASM SIMD, лёгкая SR-модель
- **Исполнение тяжёлых вычислений:** Web Worker внутри Offscreen Document
- **Хранение настроек:** `chrome.storage.sync`
- **Зависимостей в рантайме на этап 0:** ноль. Всё, что попадает в пакет расширения, написано в проекте.

## Архитектурные принципы

- **SOLID.** Один модуль — одна ответственность. `core/enhance/` знает только про улучшение
  картинки и ничего не знает ни про DOM страницы, ни про очередь, ни про UI.
- **DRY.** Логика апскейла существует ровно в одном месте — `core/enhance/`. Content script,
  контекстное меню и режим «вся страница» вызывают её, а не переписывают.
- **KISS.** Никаких абстракций «на будущее» там, где сейчас одна реализация. Интерфейс
  заводится тогда, когда за ним точно будет больше одной реализации (как у `ImageEnhancer`:
  классический апскейл и ML — это два разных бэкенда одного контракта).
- **Минимум работы в UI-потоке.** Content script имеет право искать картинки и рисовать
  оверлеи. Считать пиксели он права не имеет — это заморозит сайт пользователя.
  На этапах 2–3 это правило временно нарушено осознанно: сначала нужен работающий
  проверенный алгоритм, и только потом перенос в Worker (этап 4). Цена нарушения
  измерена и записана в документации обоих этапов.
- **Явные типизированные интерфейсы между слоями.** Общение
  `content script -> service worker -> offscreen -> worker` идёт через одну карту сообщений
  (`core/messaging/types.ts`), а не через россыпь объектов с полем `type: string`.
- **Graceful degradation.** Нет WebGPU — работаем на WASM. Нет WASM — работаем на Canvas.
  Картинка испорчена CORS — говорим пользователю понятную причину, а не падаем.
- **Разрешения (permissions) добавляются по мере надобности**, а не все сразу. Каждое
  разрешение — это строчка в предупреждении при установке; лишние строчки отпугивают
  пользователей и вызывают вопросы при ревью в Chrome Web Store.

## Структура папок

```
image-enhancer/
  pages/                — HTML-оболочки страниц расширения (popup, options)
  public/               — то, что копируется в сборку как есть
    manifest.json
    icons/
  scripts/              — скрипты сборки (Node, не попадают в расширение)
  src/
    background/         — service worker: маршрутизация сообщений, контекстное меню, уведомления
    content/            — content script: детекция картинок/видео, оверлеи и плашки
    workers/            — Web Worker'ы: инференс и классический апскейл (с этапа 4)
    core/
      enhance/          — улучшение изображений: интерфейс, ресемплер Ланцоша, реализация
                          на OffscreenCanvas. Не знает ни про DOM, ни про chrome API —
                          готов к переносу в Worker (этап 4)
      device/           — детекция возможностей устройства и выбор уровня качества
      messaging/        — типизированный контракт сообщений между слоями
      settings/         — чтение и запись пользовательских настроек
      log.ts            — единый логгер
    video/              — ЗАГЛУШКА: интерфейсы будущей видео-обработки, без реализации
    ui/                 — переиспользуемые UI-элементы: кнопка-оверлей, тосты, подсветка, стили
    options/            — логика страницы настроек
    popup/              — логика окна по клику на иконку
  models/               — веса ML-моделей (с этапа 5)
  docs/                 — эта документация
```

**Почему деление по роли, а не по типу файла.** Альтернатива — раскладывать по типу
(`components/`, `utils/`, `types/`). Это работает, пока файлов немного, а дальше любое
изменение требует прыжков между тремя папками. Деление по роли держит связанные вещи
рядом: всё про content script лежит в `content/`, и этот модуль можно отдать другому
человеку целиком.

**Отклонения от изначально запланированной структуры** (зафиксированы осознанно):

| Что добавлено | Почему |
|---|---|
| `src/core/messaging/` | Контракт сообщений — общая логика двух и более слоёв, его место в `core/`. Держать его в `background/` неверно: content script и popup тоже его импортируют |
| `src/core/settings/` | То же самое: настройки читают все контексты расширения |
| `src/popup/` + `pages/` | Popup не был в исходном плане, но без него у расширения нет ни одной видимой точки входа на этапе 0 — нечего проверять руками |

## Что заложено «на вырост» под видео

Обработка видео — **будущая функциональность**, её нет ни в одном из этапов 0–9.
Чтобы будущий этап было проще пристыковать, уже сейчас сделано следующее:

- `src/video/types.ts` — контракты `VideoEnhanceTask`, `VideoProgress`, `VideoEnhancer`.
  Прогресс видео описан в кадрах, а не булевым «готово/не готово», потому что очередь
  этапа 3 должна уметь показывать оба вида прогресса без переписывания.
- `src/video/index.ts` — флаг `VIDEO_ENHANCEMENT_ENABLED = false`. Единственный
  переключатель: все точки расширения спрашивают его, а не проверяют наличие модуля.
- `src/content/detect.ts` — `<video>` на странице **уже находится и считается**, просто
  UI для него не рендерится. Точка, куда вешать плашку, существует и покрыта кодом.
  С этапа 1 их число видно в popup — то есть детекция не просто написана, а проверяема.
- `src/ui/` — кнопка-оверлей, тосты и подсветка написаны так, что не зависят от типа
  медиа: они принимают `DOMRect` и текст. Плашка для `<video>` переиспользует их как есть.

Почему сама обработка отложена: любой рабочий путь (WebCodecs, ffmpeg.wasm, MediaRecorder)
требует собственного пайплайна декодирования, покадрового планирования и упаковки обратно
в контейнер. По объёму это сопоставимо со всеми этапами 0–9 вместе взятыми и не
переиспользует ничего, кроме собственно апскейлера одного кадра.

## Как читать документацию этапа

У каждого этапа два файла:

- **`..._Impl.md`** — сводка на 1 страницу: что реализовано, какие технологии, ключевые
  решения, с чем столкнулись, что осознанно не сделано, список изменённых файлов.
  Для того, кто уже знает контекст.
- **`..._Guide.md`** — обучающий разбор: цель, теория, пошаговая инструкция с обоснованием
  каждого нетривиального решения, полный код с разбором, проверка руками, типичные ошибки.
  Блоки, начинающиеся с `>` — это ответы на вопрос «почему именно так». Если шаг понятен
  и без них, при первом чтении их можно пропустить.

## Разрешения расширения: что уже есть и что появится

Разрешения добавляются тем этапом, которому они реально нужны.

| Разрешение | Появилось / появится | Зачем |
|---|---|---|
| `storage` | ✅ этап 0 | Настройки пользователя, состояние очереди |
| `content_scripts` на `http(s)://*/*` | ✅ этап 0 | Оверлеи при наведении невозможны без постоянного присутствия на странице |
| `contextMenus` | ✅ этап 1 | Пункт «Улучшить изображение» по правому клику |
| `offscreen` | этап 4 | Единственный контекст, где можно создать Web Worker и рисовать на canvas |
| `host_permissions` | этап 7 | Загрузка картинки в обход CORS, когда canvas «испорчен» (tainted). На этапе 2 частично решено повторной загрузкой с `crossOrigin` — работает, если сервер отдаёт `Access-Control-Allow-Origin` |
| `downloads` | **не понадобилось** | Скачивание сделано ссылкой `<a download>`; API расширения потребовало бы отдельного предупреждения при установке |
| `notifications` | будущий видео-этап | Уведомление о завершении долгой фоновой обработки |

## Команды

```bash
npm install        # один раз после клонирования
npm run dev        # сборка в режиме разработки + слежение за файлами + автоперезагрузка расширения
npm run build      # продакшн-сборка в dist/
npm run typecheck  # проверка типов (сборка типы не проверяет!)
npm run icons      # перегенерация иконок в public/icons/
npm run clean      # удалить dist/
```
