# Этап 6: Уровни качества и настройки

## Цель этапа

К этому моменту расширение умеет три способа увеличить картинку: масштабирование
средствами браузера, фильтр Ланцоша двух радиусов и нейросеть на двух бэкендах.
Выбор между ними до сих пор делала жёстко зашитая логика.

Задача этапа — отдать выбор пользователю и одновременно сделать так, чтобы
**не выбирать** тоже было хорошим вариантом: расширение должно само подобрать
разумный уровень под железо.

Звучит как «добавить три радиокнопки». Настоящая работа здесь в другом:
решить, что именно означает каждый уровень, и собрать эти решения в одном месте,
а не размазать по пяти модулям.

---

## Теория

### Почему настройки — это в первую очередь вопрос архитектуры

К началу этапа решения про качество были приняты в четырёх разных файлах:

| Где | Что решалось |
|---|---|
| `canvas-enhancer.ts` | Радиус фильтра Ланцоша по уровню |
| `ml-client.ts` | Потолок размера для ML |
| `core/enhance/index.ts` | Коэффициент увеличения (2..4) |
| `enhance-runner.ts` | Пробовать ли ML вообще |

Пока правило в каждом месте было одно, это работало. Но у уровня качества эти
решения **связаны**: «быстро» означает и отсутствие ML, и отсутствие Ланцоша,
и меньший потолок коэффициента. Держать связанные правила в четырёх файлах —
значит гарантированно однажды поменять три из четырёх.

Поэтому первое, что делается на этапе, — не UI, а модуль `core/enhance/policy.ts`,
где уровень превращается в набор конкретных параметров. UI появляется после
и просто выбирает одно из трёх значений.

> Это общий приём: когда у настройки несколько следствий, заводите **одно место**,
> где настройка превращается в следствия, и передавайте дальше уже следствия.

### Что должен означать уровень качества

Наивная трактовка — «насколько красиво». Она бесполезна: пользователь не может
оценить «красивее на 15%», а разработчик не может это реализовать.

Рабочая трактовка — **чем разрешено платить за результат**:

| Уровень | Чем платим | Что получаем |
|---|---|---|
| Быстро | Ничем заметным (единицы мс) | Мягкий результат средствами браузера |
| Сбалансированно | Сотнями миллисекунд | Ланцош радиуса 2; нейросеть, если она бесплатна по времени (WebGPU) |
| Качественно | Секундами | Нейросеть везде, где применима; иначе Ланцош радиуса 3 |

Такая формулировка проверяема замерами и переводится в код без домыслов.

### Автоматический выбор — и где проходит его граница

«Автоматически» должно понижать уровень на слабом железе. Но у автоматики есть
важная граница: **она не имеет права переопределять явный выбор пользователя.**

Если человек выбрал «качественно» на машине без WebGPU, он получит ML и подождёт
секунды. Это его решение. Расширение, которое «знает лучше» и втихую даёт другой
результат, — расширение, настройкам которого нельзя верить.

Поэтому правило простое: автоматика работает **только** когда её об этом просят,
то есть при выборе «автоматически».

### Почему пороги должны браться из замеров

Соблазн написать «если ядер меньше четырёх — быстро» велик, и это будет чистой
выдумкой. У нас есть цифры этапов 2, 4 и 5:

- Ланцош радиуса 2: 253 мс на 1920×1080 → 3840×2160; радиус 3: 325 мс.
- ML на WebGPU: 1200×900 → 2400×1800 за 496 мс.
- ML на WASM: ~11 мкс на пиксель, то есть картинка 500×500 — почти три секунды.

Отсюда пороги выводятся, а не назначаются:

- **Есть WebGPU** → «качественно». Инференс за доли секунды, ждать нечего.
- **Нет WebGPU, но есть SIMD, ≥4 ядер и ≥4 ГБ** → «сбалансированно». ML
  технически возможен, но по времени неприемлем для этого уровня; Ланцош радиуса 2
  укладывается в сотни миллисекунд.
- **Всё остальное** → «быстро». Здесь и Ланцош ощутим.

> **Почему пороги намеренно занижены.** Заниженный уровень пользователь при желании
> поднимет вручную. Завышенный он воспримет как «расширение тормозит» и, скорее
> всего, просто удалит его — не разобравшись, что дело в настройке.

### Кеширование настроек

`chrome.storage` асинхронен. Читать его на каждую картинку в режиме «вся страница» —
полсотни лишних асинхронных вызовов за прогон.

Кеш решает это, но создаёт классическую проблему: настройки меняются **в другом
документе** (страница настроек — отдельная вкладка), и content script об этом
не узнает.

Решение — не таймер и не перечитывание «на всякий случай», а событие
`chrome.storage.onChanged`, которое приходит во все контексты расширения.
По нему кеш просто сбрасывается; следующий запрос перечитает.

---

## Что делаем

1. Пишем правила уровней — `core/enhance/policy.ts`.
2. Убираем знание об уровнях из апскейлера.
3. Добавляем `recommendLevel()` в `core/device/`.
4. Расширяем настройки и добавляем кеш с инвалидацией.
5. Пишем разрешение уровня в content script.
6. Переписываем страницу настроек.
7. Проверяем, что уровни действительно меняют поведение.

## Пошаговая инструкция

### Шаг 1. Правила уровней

```ts
export interface EnhancePlan {
  useMl: boolean
  lanczosRadius: number | null   // null — средствами браузера
  maxScale: number
}

const PLANS: Record<QualityLevel, EnhancePlan> = {
  fast:     { useMl: false, lanczosRadius: null, maxScale: 2 },
  balanced: { useMl: true,  lanczosRadius: 2,    maxScale: 3 },
  quality:  { useMl: true,  lanczosRadius: 3,    maxScale: 4 },
}
```

> **Почему `lanczosRadius: null` вместо отдельного флага «использовать браузер»**
>
> Два поля вместо одного пришлось бы держать согласованными: комбинация
> «радиус 3 и при этом масштабировать браузером» бессмысленна, но выразима.
> `null` делает такое состояние непредставимым.

```ts
export function isMlAllowed(level: QualityLevel, backend: string): boolean {
  if (!resolvePlan(level).useMl) return false
  if (level === 'balanced') return backend === 'webgpu'
  return true
}
```

> **Почему это отдельная функция, а не поле в плане**
>
> Бэкенд выясняется **позже** уровня: узнать его можно только подняв воркер
> и попробовав инициализацию. План строится до того, поэтому правило,
> зависящее от бэкенда, в него не помещается.

> **Почему на «сбалансированно» ML только при WebGPU**
>
> На WASM инференс стоит ~11 мкс на пиксель: картинка 500×500 — почти три секунды.
> Уровень, который пользователь выбрал как компромисс, не должен заставлять ждать
> три секунды. Ланцош радиуса 2 на той же картинке — десятки миллисекунд.

### Шаг 2. Апскейлер перестаёт знать про уровни

Было:

```ts
constructor(private readonly level: QualityLevel) {
  this.backend = level === 'fast' ? 'canvas-bilinear' : 'canvas-lanczos'
}
// ...
const radius = KERNEL_RADIUS[this.level === 'quality' ? 'quality' : 'balanced']
```

Стало:

```ts
constructor(private readonly radius: number | null) {
  this.backend = radius === null ? 'canvas-bilinear' : 'canvas-lanczos'
}
```

> **Почему это не косметика**
>
> В прежнем виде добавление четвёртого уровня требовало правки апскейлера —
> модуля, который про уровни знать не должен и который к тому же исполняется
> в воркере, где никаких настроек нет.
>
> Обратите внимание на выражение `this.level === 'quality' ? 'quality' : 'balanced'`
> в старом коде: это следствие того, что тип допускал `'fast'`, а таблица радиусов —
> нет. Костыль появился потому, что модуль знал лишнее.

### Шаг 3. Рекомендация по железу

```ts
export function recommendLevel(capabilities: DeviceCapabilities): QualityLevel {
  if (capabilities.webgpu) return 'quality'

  const enoughCores = capabilities.logicalCores >= 4
  const enoughMemory = capabilities.memoryGb === null || capabilities.memoryGb >= 4

  if (capabilities.wasmSimd && enoughCores && enoughMemory) return 'balanced'
  return 'fast'
}
```

> **Почему `memoryGb === null` считается достаточной памятью**
>
> `navigator.deviceMemory` есть не во всех браузерах и может быть скрыт настройками
> приватности. Трактовать отсутствие данных как «мало памяти» — значит наказывать
> пользователя за приватность. Неизвестно ≠ плохо.

> **Почему `capabilities.webgpu`, а не `'gpu' in navigator`**
>
> Это результат реального `requestAdapter()` из этапа 5. Наличие объекта
> `navigator.gpu` ничего не гарантирует: адаптер может не выдаться из-за драйвера
> в чёрном списке или запуска в виртуальной машине.

### Шаг 4. Разрешение уровня

```ts
export async function resolveQualityLevel(): Promise<QualityLevel> {
  const settings = await getSettings()
  if (settings.quality !== 'auto') return settings.quality

  const capabilities = await detectCapabilities()
  const level = recommendLevel(capabilities)

  if (!announced) {
    announced = true
    log.info(`Уровень «авто» разрешён в «${level}» (WebGPU: ..., SIMD: ..., ядер: ...)`)
  }
  return level
}
```

> **Почему явный выбор возвращается сразу, без обращения к железу**
>
> Не только ради скорости. Это и есть то самое правило: автоматика включается
> только тогда, когда её просят. Код, где после чтения настройки идёт «а вдруг
> железо слабое», рано или поздно начнёт переопределять выбор пользователя.

> **Зачем флаг `announced`**
>
> Без него режим «вся страница» написал бы это сообщение полсотни раз за прогон
> и утопил бы в нём всё остальное. Один раз за жизнь страницы — ровно столько,
> сколько нужно, чтобы понять, что происходит.

### Шаг 5. Кеш настроек

```ts
let cache: Settings | null = null

export async function getSettings(): Promise<Settings> {
  if (cache) return cache
  // ... чтение
  cache = { ...DEFAULT_SETTINGS, ...stored }
  return cache
}

chrome.storage.onChanged.addListener((changes, areaName) => {
  if (areaName !== 'sync') return
  if (!Object.keys(changes).some((key) => key in DEFAULT_SETTINGS)) return
  cache = null
})
```

> **Почему слушатель на уровне модуля, а не внутри функции**
>
> Изменение приходит из **другого документа** — страницы настроек. Узнать о нём
> надо независимо от того, спрашивал ли кто-то настройки в этот момент. Слушатель,
> зарегистрированный лениво, пропустил бы изменение, случившееся до первого запроса.
>
> Это тот самый вызов на верхнем уровне модуля, от которого мы избавлялись
> на этапе 4 ради tree-shaking. Здесь он оправдан: настройки нужны всегда,
> вырезать этот модуль всё равно не из чего.

> **Почему проверка `key in DEFAULT_SETTINGS`**
>
> В `chrome.storage.sync` может писать не только этот код. Сбрасывать кеш
> на чужие ключи незачем.

### Шаг 6. Страница настроек

Три вещи, которые стоит отметить в вёрстке.

```html
<label class="ie-choice">
  <input type="radio" name="quality" value="balanced" />
  <span>
    <b>Сбалансированно</b>
    <small>Фильтр Ланцоша (радиус 2). Нейросеть — только при работающем WebGPU…</small>
  </span>
</label>
```

> **Почему у каждого варианта есть описание, а не только название**
>
> «Сбалансированно» само по себе не говорит ничего: между чем и чем баланс?
> Описание отвечает на единственный вопрос, который волнует пользователя, —
> сколько придётся ждать и что он за это получит.

```html
<small id="auto-hint">Расширение выберет уровень по возможностям устройства.</small>
```
```ts
hint.textContent = `На этом устройстве — «${LEVEL_NAMES[level]}».`
```

> **Почему «авто» показывает, во что он разрешается**
>
> Иначе это чёрный ящик: пользователь не знает, что именно выбрано, и не может
> понять, стоит ли вмешиваться.

```html
<h2 class="ie-section">Это устройство</h2>
<ul class="ie-rows">
  <li><dfn>WebGPU</dfn><b id="cap-webgpu">—</b></li>
  ...
```

> **Зачем показывать возможности устройства в настройках**
>
> Это не украшение. Когда у пользователя «не работает нейросеть», единственный
> вопрос — есть ли у него WebGPU. Без этого блока ему нечего написать в баг-репорте,
> а разработчику нечего спросить.

```ts
function saveStateFor(input: Element): Element | null {
  return input.closest('li')?.querySelector('.save-state') ?? null
}
```

> **Почему отметка «сохранено» ищется относительно поля**
>
> На этапе 0 переключатель был один, и элемент с фиксированным `id` работал.
> Со вторым переключателем подтверждение показывалось бы не у того поля.
> Типичная мелочь, которая ломается ровно в момент добавления второго экземпляра
> чего угодно.

### Шаг 7. Настройка «подменять картинку на странице»

```ts
const settings = await getSettings()
if (settings.replaceOnPage) replaceOnPage(image, result.blob)
```

> **Зачем это вообще нужно**
>
> Подменённая картинка может сломать вёрстку: сайт мог рассчитывать на конкретные
> размеры файла. Часть пользователей хочет просто получить файл, не трогая страницу.
>
> Следствие в UI: кнопка «Вернуть» в уведомлении не показывается, когда подмены
> не было — возвращать нечего.

## Проверка

### На стенде

Заглушка `chrome.storage` в стенде доработана так, чтобы `set()` вызывал
зарегистрированные обработчики `onChanged`. Это позволяет менять настройки
между прогонами и заодно проверяет инвалидацию кеша.

| Уровень | Ожидалось | Получено |
|---|---|---|
| `fast` | Средства браузера, ML не грузится | `canvas-bilinear`, 32 мс, ML-воркер не загружался |
| `balanced` (есть WebGPU) | ML разрешён | `ml-webgpu`, 254 мс на 800×600 → 1600×1200 |
| `quality` | ML | `ml-webgpu`, 159 мс на 300×300 → 600×600 |
| `auto` | Разрешается по железу | «Уровень «авто» разрешён в «quality» (WebGPU: да, SIMD: да, ядер: 20)», сообщение ровно одно на две обработки |
| `replaceOnPage: false` | Картинка не подменяется | `src` не изменился, в уведомлении только «Скачать» |

Отдельно подтвердилось, что смена настройки между прогонами меняет поведение —
то есть кеш сбрасывается по событию, а не живёт до перезагрузки страницы.

### Найденная ошибка

При первом прогоне с уровнем «качественно» ML не включился, а в консоли было:

```
[ImageEnhancer:ml] Модель не загрузилась: Failed to execute 'fetch' on 'WorkerGlobalScope':
Failed to parse URL from /models/esrgan-slim-x2/model.json
```

**Воркер, созданный из blob-URL, не разрешает относительные URL.** Его базовый
адрес — сам blob, и относительный путь там не превращается в абсолютный вообще.

В настоящем расширении `chrome.runtime.getURL` возвращает абсолютный
`chrome-extension://`-адрес, поэтому ошибка проявилась только на стенде.
Но полагаться на это не стоит: сообщение вылезает глубоко внутри воркера,
и причину по нему не угадать. Теперь URL приводятся к абсолютным явно:

```ts
function absoluteUrl(path: string): string {
  return new URL(chrome.runtime.getURL(path), location.href).href
}
```

Побочный результат оказался ценнее самой ошибки: подтвердилась **деградация**.
ML не поднялся, расширение молча отработало классическим апскейлом, пользователь
ничего не заметил — ровно так, как задумано на этапе 5.

### Проверка в браузере

```bash
npm run dev
```

1. **Страница настроек.** Открыть через popup → «Настройки». Проверить, что
   у варианта «Автоматически» подпись показывает конкретный уровень для этой машины,
   а блок «Это устройство» заполнен.

2. **Сохранение.** Выбрать «Быстро», закрыть вкладку настроек, открыть заново —
   выбор должен сохраниться.

3. **Уровень действительно работает.** С включёнными подробными логами обработать
   картинку на каждом уровне и посмотреть в консоли страницы поле в скобках:
   - «Быстро» → `canvas-bilinear`
   - «Сбалансированно» → `ml-webgpu` при наличии WebGPU, иначе `canvas-lanczos`
   - «Качественно» → `ml-webgpu` / `ml-wasm`, иначе `canvas-lanczos`

4. **На «быстро» модель не грузится.** DevTools → Network. При уровне «быстро»
   запроса за `ml-worker.js` быть не должно вообще.

5. **Настройка применяется без перезагрузки страницы.** Не закрывая вкладку с сайтом,
   поменять уровень в настройках и обработать картинку снова — бэкенд в логе должен
   измениться. Это проверка инвалидации кеша.

6. **Подмена на странице.** Выключить «Подменять картинку прямо на странице»,
   обработать картинку: она должна остаться прежней, а в уведомлении — только
   кнопка «Скачать».

7. **Popup.** Строка «Уровень качества» должна показывать действующий уровень,
   а при «авто» — с пометкой, например «качественно (авто)».

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Настройка сохраняется, но поведение не меняется | Кеш настроек не сбрасывается | Слушатель `chrome.storage.onChanged` на уровне модуля |
| Изменения из страницы настроек не видны во вкладке | Слушатель зарегистрирован лениво и пропустил событие | То же |
| ML не включается ни на каком уровне | Модель не загрузилась; смотреть ошибку в консоли | Часто — относительный URL ресурса |
| `Failed to parse URL` внутри воркера | Воркер из blob-URL не разрешает относительные пути | Приводить URL к абсолютным перед отправкой |
| На «быстро» всё равно грузится 800 КБ | Воркер поднимается до проверки уровня | Проверять `plan.useMl` до `getMlRuntime()` |
| Отметка «сохранено» появляется не у того поля | Один элемент с фиксированным `id` на несколько настроек | Искать отметку относительно самого поля |
| Автоматика переопределяет явный выбор | После чтения настройки идёт проверка железа | Возвращать явный выбор сразу |
| На машине без `deviceMemory` всегда «быстро» | Отсутствие данных трактуется как мало памяти | Неизвестно ≠ плохо |
| Добавление уровня требует правок в пяти файлах | Правила размазаны | Один модуль правил, остальные получают готовый план |

### Что будет дальше

**Этап 7 — устойчивость: CORS и ошибки.** Главное незакрытое ограничение проекта:
картинки с чужого домена без CORS-заголовков не обрабатываются вовсе. Решение —
загрузка из контекста расширения с `host_permissions`, и там встанет задача,
отложенная ещё с этапа 4: как вернуть пиксели обратно в страницу через канал,
который сериализует сообщения в JSON.

Плюс edge-cases, до которых пока не доходили руки: SVG, `data:`-URL, очень большие
изображения, и понятные сообщения вместо «не удалось обработать картинку».
