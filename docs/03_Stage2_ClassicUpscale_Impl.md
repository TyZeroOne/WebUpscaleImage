# Этап 2: Классический апскейл, режим «одно изображение» — реализация

## Что реализовано

- **Фильтр Ланцоша** собственной реализации: разделимый (два одномерных прохода),
  с предрасчётом весов, нормировкой и premultiplied alpha. Радиус 2 и 3.
- **`CanvasEnhancer`** — реализация интерфейса `ImageEnhancer` поверх `OffscreenCanvas`.
  Два пути: нативный `drawImage` (уровень `fast`) и Ланцош (`balanced` / `quality`).
- **Получение пикселей с обходом CORS**: если canvas «испорчен», картинка перезагружается
  с `crossOrigin="anonymous"`. Работает на серверах, отдающих `Access-Control-Allow-Origin`.
- **Подмена картинки на странице** с корректной обработкой `srcset`, `sizes` и `<picture>`,
  и восстановление оригинала.
- **Скачивание результата** через `<a download>` без разрешения `downloads`.
- **Тосты с действиями**: «Обрабатываю…» → «Готово: N×M, X МБ, T мс» с кнопками
  «Скачать» и «Вернуть».
- **Умный коэффициент увеличения**: считается от реальной нехватки пикселей
  (растянута ли картинка стилями, какой devicePixelRatio), а не берётся равным 2 всегда.
- Потолок размера результата 24 Мп с автоматическим снижением коэффициента.
- Защита от повторного запуска на той же картинке.

## Использованные технологии/API

| Что | Деталь |
|---|---|
| `OffscreenCanvas` | Используется вместо `<canvas>` даже там, где доступен DOM — чтобы код был готов к переносу в Worker (этап 4) |
| `createImageBitmap` | Декодирование картинки; `close()` для немедленного освобождения памяти |
| `getImageData` / `putImageData` | Чтение и запись пикселей; `willReadFrequently: true` на исходном холсте |
| `convertToBlob` | Кодирование результата в PNG |
| `URL.createObjectURL` / `revokeObjectURL` | Подмена картинки и скачивание |
| `WeakMap` / `WeakSet` | Хранение состояния по DOM-элементу без утечек |
| `HTMLImageElement.crossOrigin` | Повторная загрузка в CORS-режиме |
| Node 24 native TypeScript | Численные тесты ресемплера запускаются прямо на `.ts` без сборки |

## Ключевые решения

1. **Ланцош, а не bicubic** — при сопоставимой стоимости даёт заметно более резкий
   результат; «звон» на контрастных краях гасится обрезкой в `Uint8ClampedArray`.
2. **Разделимая фильтрация в два прохода** — 2·(2a) умножений на пиксель вместо (2a)²;
   при радиусе 3 это 12 против 36.
3. **Предрасчёт весов по осям** — веса зависят только от номера выходного пикселя;
   для 1920×1080 это 3000 вычислений синуса вместо 20 миллионов.
4. **Premultiplied alpha при фильтрации** — иначе по краям прозрачных областей
   появляется тёмная кайма. Проверено численно.
5. **`core/enhance/` не знает про DOM и chrome API** — только `OffscreenCanvas`,
   который есть и в Worker. Перенос на этапе 4 не потребует правок алгоритма.
6. **Коэффициент увеличения считается, а не задан** — слепое ×2 на картинке, показанной
   в собственном размере на обычном экране, не даёт видимого эффекта: браузер тут же
   ужмёт результат обратно.
7. **PNG, а не JPEG/WebP** — перекодировать с потерями сразу после аккуратного
   пересчёта пикселей противоречит назначению инструмента. Выбор формата — в настройки
   этапа 6.
8. **Обработка идёт в content script** — временно и намеренно. Этап 4 переносит её
   в Worker; сначала нужен работающий проверенный алгоритм.

## Проблемы и как решены

**1. Обработка не завершалась в невидимой вкладке.** Перед началом вычислений код
отдаёт браузеру кадр, чтобы успел отрисоваться тост «Обрабатываю…». Ожидание было
построено на `requestAnimationFrame`, а в невидимой вкладке кадры не рисуются и `rAF`
не вызывается **вовсе** — обработка вставала навсегда. Обнаружено на стенде. Решение:
`rAF` в паре со страховочным `setTimeout(50)`, что бы ни сработало первым.
Тот же класс ошибки, что был найден в тостах на этапе 1.

**2. Подмена картинки откатывалась.** Присвоения `img.src` недостаточно: `srcset`
у самого `<img>` и `<source srcset>` внутри `<picture>` имеют более высокий приоритет,
и браузер пересматривает выбор источника при изменении размера окна. Решение: атрибуты
снимаются и сохраняются для восстановления. Проверено на стенде: после подмены и события
`resize` картинка остаётся результатом обработки.

**3. Замеры времени на стенде оказались недостоверны.** `convertToBlob` стабильно
занимал ~1015 мс **независимо от размера холста** (480×360, 1200×900 и 2400×1800 — все
около 1015–1060 мс). Это артефакт среды без композитинга, а не стоимость кодирования.
Реальную стоимость фильтра пришлось мерить отдельно, вне браузера.

**4. Сдвиг на полпикселя.** Центр выходного пикселя в координатах исходника —
`(i + 0.5) / scale − 0.5`. Без слагаемых 0.5 результат уезжает на полпикселя;
на одном применении почти незаметно, при повторных — картинка явно «ползёт».
Поймано численным тестом на симметрию.

**5. Потеря яркости у краёв.** После обрезки окна фильтра у границ изображения сумма
весов перестаёт равняться единице. Без нормировки по краям появляется видимая рамка.
Поймано тестом «однородная картинка не меняется».

**6. `noUncheckedIndexedAccess` в пиксельных циклах.** Строгая опция из этапа 0 требует
`!` на каждом обращении к типизированному массиву. В горячих циклах это визуальный шум,
но отключать опцию ради одного файла хуже: она уже поймала пару ошибок индексации.
Оставлено как есть.

## Известные ограничения / TODO

- **Вычисления блокируют страницу.** Замеренная стоимость фильтра (радиус 2 / радиус 3):
  640×480→1280×960 — 46/53 мс; 1920×1080→3840×2160 — 253/325 мс;
  3000×2000→4472×2981 — 443/578 мс. Плюс кодирование PNG. Исправляется этапом 4.
- **Картинки с чужого домена без CORS-заголовков не обрабатываются** — показывается
  понятная ошибка. Полный обход (загрузка из service worker с `host_permissions`) — этап 7.
- **Нет шумоподавления и повышения резкости** — только масштабирование. Резкость
  косвенно даёт сам Ланцош.
- **Нет отмены.** `AbortSignal` протянут через интерфейс и проверяется между шагами,
  но UI отмены нет, а сам фильтр не прерывается в середине (он синхронный).
  Полноценная отмена — этап 4, когда работа уедет в Worker.
- **Уровень качества жёстко `balanced`**, коэффициент — 2..4 по расчёту. Выбор
  пользователем — этап 6.
- **PNG всегда** — фотография 4К весит десятки мегабайт. Выбор формата — этап 6.
- **Потолок 24 Мп** подобран по оценке памяти, а не измерен на слабой машине.
- **Не обрабатываются** `background-image`, `<canvas>`, SVG, `<picture>` без `<img>`.
- **Тесты ресемплера не в репозитории** — запускались из временной папки скриптом
  на Node. Кандидат на добавление вместе с тестовой инфраструктурой (не раньше этапа 4).
