# Этап 3: Режим «вся страница» — реализация

## Что реализовано

- **Очередь задач** (`src/content/queue.ts`) — обобщённая, с ограничением параллелизма,
  прогрессом, отменой и возвратом кадра браузеру между задачами. О картинках ничего не знает.
- **Панель хода обработки** в левом нижнем углу: заголовок, полоса прогресса,
  счётчик «N из M · пропущено: K», кнопки «Отмена» / «Вернуть все» / «Закрыть».
- **Оркестрация пакетного режима** (`src/content/page-flow.ts`): сбор кандидатов,
  сортировка по видимости, запуск очереди, группировка ошибок, массовое восстановление.
- **Две точки запуска**: кнопка «Улучшить все на странице» в popup и пункт контекстного
  меню на пустом месте страницы.
- **Разделение потока обработки** на `enhanceImageCore` (работа без UI, общая для обоих
  режимов) и `createEnhanceFlow` (обёртка с тостами для одной картинки).
- Пропуск уже улучшенных картинок при повторном запуске.
- Защита от двойного запуска очереди.
- Потолок 50 картинок за запуск с явным сообщением о пропущенных.

## Использованные технологии/API

| Что | Деталь |
|---|---|
| `AbortController` / `AbortSignal` | Отмена: один контроллер на запуск, сигнал протянут в каждую задачу |
| Пул исполнителей с общим курсором | Задачи разной стоимости разбираются по мере освобождения, а не делятся заранее |
| `getBoundingClientRect` | Сортировка по удалённости от центра экрана |
| `Map` для группировки причин | Один тост на причину вместо одного на картинку |
| `chrome.contextMenus` c `contexts: ['page']` | Второй пункт меню, не пересекающийся с пунктом для картинок |

## Ключевые решения

1. **Очередь живёт в content script, а не в service worker** — задачи ссылаются на DOM-узлы,
   прогресс рисуется на странице, отмена относится к конкретной вкладке. Service worker
   к тому же выгружается по простою, и очередь пришлось бы восстанавливать из хранилища.
2. **Параллелизм равен 1 — осознанно.** Вычисления синхронные и в главном потоке;
   «параллельные» задачи всё равно выполнились бы последовательно, зато удвоили бы пик
   памяти. Лимит вынесен в константу и начнёт иметь смысл на этапе 4.
3. **Возврат кадра между задачами обязателен** — без него очередь выполнилась бы одним
   куском: прогресс не обновился бы ни разу, а «Отмена» не дошла бы до обработчика.
4. **Порядок — по удалённости от центра экрана**, а не по DOM. Пользователь смотрит
   на видимую часть; иначе первые секунды кажется, что ничего не происходит.
5. **Список картинок снимается один раз, `MutationObserver` не добавлен** — на странице
   с ленивой загрузкой очередь никогда бы не заканчивалась, а знаменатель в «N из M»
   рос бы на ходу.
6. **Ошибки группируются по причине** — на странице, где все картинки на CDN без
   CORS-заголовков, сорок одинаковых уведомлений не сообщили бы ничего сверх одного.
7. **Панель слева, тосты справа** — прогресс должен оставаться виден, когда всплывает
   ошибка по отдельной картинке: именно в этот момент пользователь и хочет нажать «Отмена».
8. **Работа разделена на ядро и UI-обёртку** — иначе два режима начали бы расходиться
   в поведении.

## Проблемы и как решены

**1. «Вернуть все» относится только к последнему запуску.** Список заменённых картинок
обнуляется при старте новой очереди. Обнаружено на стенде: клик по кнопке во время
нового запуска восстановил 0 картинок. В реальном UI кнопка в этот момент скрыта
(`panel.show()` прячет её), поэтому дефект не проявляется, но ограничение осталось —
зафиксировано ниже.

**2. Отмена не прерывает текущую картинку.** При отмене на счётчике «2 из 14» очередь
остановилась на «3 из 14»: задача, начатая до нажатия, досчиталась до конца. Фильтр
Ланцоша синхронный, прервать его на середине невозможно без разбиения на куски.
Оставлено как есть: разбиение усложнило бы алгоритм ради задержки в доли секунды,
а на этапе 4 задача уедет в Worker, который можно завершить принудительно.

**3. Повторный запуск на странице, где все картинки закрыты CORS.** Такие картинки
не попадают в «уже улучшенные» (улучшение не удалось), поэтому очередь берёт их снова
при каждом запуске. Признано корректным: разрешения на сервере могли измениться,
а тихо игнорировать картинку навсегда — хуже.

**4. Наблюдение о достоверности замеров.** На стенде каждая картинка обрабатывалась
около секунды независимо от размера — это уже известный по этапу 2 артефакт среды без
композитинга (`convertToBlob` там стоит фиксированные ~1015 мс). Реальная стоимость
очереди — сумма замеров фильтра из этапа 2 плюс кодирование PNG.

## Известные ограничения / TODO

- **Страница ощутимо замирает.** Каждая картинка блокирует главный поток на сотни
  миллисекунд, и очередь из двадцати штук — это несколько секунд рваной отзывчивости.
  Кадр возвращается только между задачами. Решается этапом 4.
- **Отмена срабатывает по границе задачи**, а не мгновенно.
- **«Вернуть все» покрывает только последний запуск.**
- **Нет дедупликации по URL** — одна и та же картинка, встречающаяся на странице
  несколько раз, обрабатывается каждый раз заново.
- **Ленивая загрузка не поддерживается**: обрабатывается то, что уже загружено.
  Чтобы захватить больше, нужно сначала прокрутить страницу.
- **Потолок 50 картинок** подобран по оценке памяти, а не измерен.
- **Прогресс не виден из popup** — только на самой странице. Popup закрывается сразу
  после запуска.
- **Параллелизм зафиксирован на 1** до появления Worker'ов.
