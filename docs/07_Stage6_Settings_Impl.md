# Этап 6: Уровни качества и настройки — реализация

## Что реализовано

- **Три уровня качества** плюс «автоматически», с сохранением в `chrome.storage.sync`.
- **Правила уровней** вынесены в `src/core/enhance/policy.ts` — единственное место,
  где уровень превращается в конкретные действия.
- **Авто-понижение по железу**: `recommendLevel()` в `core/device/` использует
  реальную детекцию из этапа 5.
- **Страница настроек** переписана: выбор уровня с объяснением каждого варианта,
  переключатель подмены картинки на странице, блок «это устройство» с тем, что
  расширение о нём знает.
- **Кеш настроек** с инвалидацией по `chrome.storage.onChanged` — режим «вся страница»
  больше не читает хранилище на каждую картинку.
- **Настройка `replaceOnPage`**: результат можно только скачивать, не трогая вёрстку сайта.
- Popup показывает **действующий** уровень, а не значение настройки.

## Ключевые решения

1. **Явный выбор пользователя не корректируется автоматикой.** Если человек выбрал
   «качественно» на слабой машине — так и будет. Понижение работает только при
   выборе «автоматически»; иначе настройка была бы враньём.
2. **ML разрешён на «сбалансированно» только при WebGPU.** На WASM инференс стоит
   ~11 мкс на пиксель — картинка 500×500 считалась бы почти три секунды, и это
   перестало бы быть компромиссом.
3. **На «быстро» ML-воркер вообще не поднимается** — иначе расширение платило бы
   800 КБ загрузки за возможность, которой не воспользуется.
4. **Правила уровней — отдельный модуль.** Раньше решения были размазаны: радиус
   фильтра выбирался в `canvas-enhancer`, применимость ML — в `ml-client`,
   коэффициент — в `core/enhance/index`. С тремя уровнями их стало нужно
   согласовывать, а согласовывать проще то, что лежит рядом.
5. **`CanvasEnhancer` больше не знает про уровни** — принимает радиус фильтра.
   Апскейлеру незачем знать, откуда взялось число.
6. **Кеш настроек сбрасывается событием, а не по таймеру** — изменение приходит
   из другого документа (страница настроек), и узнать о нём надо независимо
   от того, спрашивал ли кто-то настройки.

## Проблемы и как решены

**1. Воркер не разрешает относительные URL.** При инициализации ML модель
не загружалась: `Failed to execute 'fetch' on 'WorkerGlobalScope': Failed to parse
URL from /models/esrgan-slim-x2/model.json`. Воркер создан из blob-URL, его базовый
адрес — сам blob, и относительный путь там не разрешается вообще.

В настоящем расширении `chrome.runtime.getURL` возвращает абсолютный
`chrome-extension://`-адрес, поэтому ошибка проявилась только на стенде. Но полагаться
на это не стоит: сообщение вылезает глубоко внутри воркера, и причину по нему
не угадать. URL теперь приводятся к абсолютным явно.

Побочный полезный результат: подтвердилась **деградация**. ML отвалился, расширение
молча отработало классическим апскейлом, пользователь ошибки не увидел — ровно так,
как задумано.

**2. Отметка «сохранено» была одна на всю страницу.** С появлением второго
переключателя единственный элемент с фиксированным `id` показывал бы подтверждение
не у того поля. Теперь отметка ищется внутри той же строки списка.

## Известные ограничения / TODO

- **Уровень применяется к следующей обработке, а не к текущей.** Смена настройки
  во время работы очереди на неё не влияет — уровень разрешается один раз на картинку.
- **Нет отдельной настройки формата результата.** PNG всегда; для фотографий это
  десятки мегабайт.
- **Нет настройки коэффициента увеличения** — он считается автоматически, потолок
  задаётся уровнем (2 / 3 / 4).
- **Нет настройки лимита очереди** (50 картинок) и лимита размера для ML.
- **Пороги `recommendLevel` проверены на одной машине.** WebGPU → «качественно»
  подтверждено замером; ветки «сбалансированно» и «быстро» проверены только логикой.
- **Переключение уровня из popup не сделано** — только просмотр действующего.
- **Настройки не синхронизируются в открытые вкладки мгновенно** в том смысле,
  что уже идущая очередь продолжит работать со старым уровнем.
