# Этап 7: Устойчивость — CORS и ошибки — реализация

## Что реализовано

- **Третья попытка получения пикселей**: загрузка картинки service worker'ом
  с `host_permissions`. Запросы расширения из фонового контекста CORS не ограничивает,
  поэтому этот путь работает там, где не работают первые два.
- **Передача двоичных данных через JSON-канал**: service worker кодирует картинку
  в `data:` URL порциями по 32 КБ.
- **Отсечение векторной графики** на уровне детекции: над SVG кнопка не показывается.
- **Предпроверка размера** исходной картинки (40 Мп) — отказ понятным сообщением
  вместо нехватки памяти в середине фильтра.
- **Переписаны все сообщения об ошибках**: каждое отвечает на вопрос «что теперь
  делать», а не «что сломалось».
- Разрешение `host_permissions` на `http(s)`.

## Ключевые решения

1. **Загрузка через service worker — последняя попытка, а не первая.** Порядок
   от дешёвого к дорогому: уже загруженная картинка (сети нет вообще) → перезагрузка
   с `crossOrigin` (один запрос из страницы) → запрос расширения (запрос плюс
   кодирование в base64 плюс передача через JSON).
2. **`credentials: 'omit'` при загрузке.** С куками расширение могло бы скачать
   личную страницу пользователя по любому адресу, который назовёт сайт, — ровно
   та атака, от которой защищает CORS. Цена: картинки, требующие авторизации,
   этим путём не загрузятся.
3. **`data:` URL, а не массив чисел.** Канал сообщений сериализует всё в JSON;
   base64 даёт рост на треть, а массив чисел — вчетверо.
4. **Кодирование порциями по 32 КБ.** `String.fromCharCode(...bytes)` на картинке
   в мегабайт падает с переполнением стека вызовов.
5. **SVG отсекается детекцией, а не обработкой.** Кнопка над картинкой, которая
   и так чёткая в любом размере, — обещание, которое расширение не может выполнить.
6. **Потолок размера проверяется до начала работы.** Отказ на входе объясним;
   нехватка памяти в середине фильтра — нет.
7. **`host_permissions` не добавляет нового предупреждения при установке**:
   оно уже вызвано `content_scripts` на `http(s)://*/*`.

## Проблемы и как решены

**1. Сообщения об ошибках ничего не сообщали.** Формулировки вроде «Не удалось
обработать картинку» и «Сайт не разрешает читать эту картинку» одинаково бесполезны:
из них не следует ни одного действия. Переписаны все: например, нехватка памяти
теперь предлагает уровень «быстро», а векторная картинка объясняет, что обработка
ей не нужна, а не притворяется ошибкой.

**2. Ссылка `detect.ts → image-source.ts`.** Проверка на вектор понадобилась
в детекции, а живёт она в модуле получения пикселей. Импорт добавлен туда, где
проверка нужна; дублировать регулярное выражение было бы хуже.

```

Картинка получена через расширение: 62 КБ
Готово за 5 мс: 200×200 → 400×400
```

## Известные ограничения / TODO

- **Не проверено в настоящем расширении.** На стенде роль service worker'а играл
  прокси на том же сервере — он воспроизводит главное свойство (запрос без
  ограничений CORS), но не проверяет ни `host_permissions`, ни реальный канал
  сообщений с многомегабайтной строкой.
- **Картинки, требующие авторизации, не загрузятся** — следствие `credentials: 'omit'`.
- **Потолок 12 МБ** на картинку, идущую через канал сообщений. Подобран оценкой,
  не измерен.
- **Обнаружение SVG — по расширению и `data:`-схеме.** Сервер, отдающий SVG
  по адресу без расширения, не будет распознан; ошибка безобидна — картинка просто
  обработается как растровая.
- **Анимированные GIF и WebP не распознаются**: результат будет статичным первым
  кадром, и пользователя об этом не предупреждают.
- **Нет повторов при сетевой ошибке** — одна попытка.
- **Нет кеша загруженных через расширение картинок**: повторная обработка той же
  картинки скачает её заново.
- **`host_permissions` на все сайты** — самое серьёзное разрешение в проекте.
  Оно нужно ровно для одного: скачать картинку, которую пользователь явно выбрал.
  Ограничить его до нужного домена в момент действия (`optional_host_permissions`)
  было бы честнее, но потребовало бы диалога подтверждения на каждый новый домен.
