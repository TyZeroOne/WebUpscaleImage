# Этап 5: ML-апскейл

## Цель этапа

Научить расширение увеличивать картинки нейросетью, а не интерполяцией.

Разница принципиальная. Классический апскейл из этапа 2 умеет только **сглаживать
имеющееся**: он вычисляет промежуточные пиксели как взвешенное среднее соседей.
Новых деталей взяться неоткуда — их нет во входных данных.

Нейросеть, обученная на парах «уменьшенная картинка → оригинал», умеет другое:
она **достраивает** детали, которых в маленькой картинке нет, опираясь на то, как
выглядели похожие фрагменты в обучающей выборке. Текстура кожи, буквы, края объектов
получаются не размытыми, а правдоподобными.

Плата — скорость (порядки, а не проценты), размер пакета расширения и зависимость
от возможностей железа.

## Теория

### Super-resolution: как модель «придумывает» детали

Модель обучают так: берут набор качественных картинок, уменьшают их вдвое
и показывают сети пары «уменьшенная → оригинал». Сеть подбирает веса так, чтобы
из первой получалась вторая. Миллионы таких пар учат её типичным закономерностям:
как выглядит резкий край, как выглядит текстура ткани, как выглядит мелкий текст.

Важно понимать границу: сеть не «восстанавливает» утраченное, она **выдумывает
правдоподобное**. На фотографии это почти всегда выглядит лучше интерполяции.
На тексте, который она видит впервые, может дорисовать не ту букву. Это свойство
метода, а не дефект реализации.

**RDN (Residual Dense Network)** — архитектура, которую мы используем. Ключевых
идей две:
- **Dense-связи**: выход каждого свёрточного слоя подаётся на вход всем последующим
  внутри блока. Сеть переиспользует признаки всех уровней, а не только последнего.
- **Глобальный residual**: итог складывается с увеличенным входом. Сеть учится
  не всей картинке, а только **разнице** между простым растяжением и хорошим
  результатом. Обучение так идёт устойчивее.

Второе свойство ещё аукнется — оно делает одну конкретную ошибку почти невидимой
(см. раздел про диапазон входа).

### TensorFlow.js: два формата моделей и почему это важно

TensorFlow.js умеет загружать модели двумя способами:

| Формат | Функция | Что внутри |
|---|---|---|
| **Layers model** (наш) | `tf.loadLayersModel` | Описание слоёв в стиле Keras. Можно дообучать, можно смотреть структуру |
| Graph model | `tf.loadGraphModel` | Замороженный граф операций. Быстрее грузится, но это чёрный ящик |

Определить формат можно прямо в `model.json` по полю `format`: у нас там
`layers-model`. Перепутать функцию — значит получить ошибку загрузки,
которая ничего не объясняет про причину.

Модель состоит из двух файлов: `model.json` (топология и манифест весов)
и `group1-shard1of1.bin` (собственно веса, 880 КБ). `model.json` ссылается
на файл весов по **относительному** имени, поэтому они обязаны лежать рядом.

### Кастомные слои — и как понять, нужны ли они

Если автор модели описал свой слой, в `model.json` он записан только именем класса.
TensorFlow.js такого класса не знает и при загрузке падает с `Unknown layer: X`.
Лечится регистрацией **до** загрузки:

```ts
class MyLayer extends tf.layers.Layer { static className = 'X'; /* ... */ }
tf.serialization.registerClass(MyLayer)
```

Проверить, нужно ли это, можно не запуская код: открыть `model.json` и посмотреть
на `class_name` всех слоёв. Если все имена стандартные (`Conv2D`, `Add`,
`Concatenate`, `Activation`, `UpSampling2D`) — регистрировать нечего.

Для нашей модели именно так и оказалось, хотя пакет, из которого она взята,
регистрирует два самописных слоя для **другой** своей архитектуры.

### WebGPU и WASM: два бэкенда, две разные проблемы

**WebGPU** — доступ к видеокарте из браузера. Свёртки — это перемножение матриц,
а видеокарта делает это на порядки быстрее процессора. Но доступен он не везде:
нужен Chrome 113+, поддерживаемый драйвер и видеокарта не из чёрного списка.

**WASM** — запасной путь на процессоре. Медленнее, но работает почти всегда.
Расширение SIMD (обработка нескольких чисел одной инструкцией) даёт кратное
ускорение, поэтому бэкенд везёт три разных `.wasm`-файла и выбирает нужный
в рантайме.

Проверять наличие WebGPU через `'gpu' in navigator` **недостаточно** — объект
может быть, а адаптер не выдаться. Единственная честная проверка:

```ts
const adapter = await navigator.gpu.requestAdapter()
if (!adapter) { /* WebGPU объявлен, но не работает */ }
```

У бэкендов принципиально **разные ограничения**, и это определит архитектуру:
- у WebGPU жёсткий потолок размера вычислительной сетки — на большой картинке
  инференс просто падает;
- у WASM потолка нет, но время растёт линейно по пикселям, и мегапиксель
  считается около десяти секунд.

### Обработка плитками

Решение обеих проблем — резать картинку на плитки фиксированного размера
и обрабатывать по одной. Тогда и размер вызова, и расход памяти постоянны
и не зависят от картинки.

Наивная нарезка даёт **швы**. Свёртка с `padding='same'` у края плитки видит
«обрыв» изображения и достраивает его нулями; результат у границы искажается,
и на стыках появляется видимая сетка.

Лечится **полями (overlap)**: плитка расширяется во все стороны, считается целиком,
а наружу берётся только центральная часть.

```
   плитка N                плитка N+1
┌────────┬────┐        ┌────┬────────┐
│        │поле│        │поле│        │
│ отдаём │ ▒▒ │        │ ▒▒ │ отдаём │
│        │выбр│        │выбр│        │
└────────┴────┘        └────┴────────┘
         └─ эти области считаются дважды и выбрасываются
```

Ширина полей должна покрывать **рецептивное поле** сети — расстояние, на которое
входной пиксель влияет на выходной. Считается по слоям: каждая свёртка 3×3
расширяет его на 1 пиксель в каждую сторону, 5×5 — на 2, 1×1 — не расширяет.

Если поля шире рецептивного поля, результат с плитками **математически совпадает**
с результатом без них, и швов нет вообще.

## Пошаговая инструкция

### Шаг 1. Разобраться, что за модель досталась

```bash
npm install @tensorflow/tfjs-core @tensorflow/tfjs-layers \
            @tensorflow/tfjs-backend-webgpu @tensorflow/tfjs-backend-wasm \
            @upscalerjs/esrgan-slim
```

> **Почему не полный пакет `@tensorflow/tfjs`**
>
> Он тянет все бэкенды, включая ненужные нам CPU и WebGL, и весь API для обучения.
> В расширении, где каждый килобайт лежит в пакете пользователя, это лишнее.
>
> Цена решения обнаружится сразу: в `tfjs-core` не зарегистрированы **цепочечные
> методы** (`tensor.div()`, `.squeeze()`, `.toFloat()`) — они подключаются
> отдельным импортом и есть только в полном пакете. Придётся писать
> функционально: `tf.div(x, 255)`. Это не хуже, просто непривычно.

> **Первое, что нужно сделать с чужой моделью, — прочитать её описание, а не код**
>
> В `node_modules/@upscalerjs/esrgan-slim/models/x2/model.json`:
> - `"format": "layers-model"` → грузить через `loadLayersModel`, не `loadGraphModel`;
> - имена слоёв: `RDB_Concat_1_1`, `LFF_1`, `GFF_2`, `LRL_1` — это **RDN**,
>   а не ESRGAN, несмотря на название пакета;
> - все `class_name` стандартные → кастомные слои регистрировать не нужно;
> - вход `[null, null, null, 3]` → сеть полностью свёрточная, принимает любой размер.
>
> А в `dist/umd/models/esrgan-slim/src/x2/index.js` — самое важное:
> ```js
> meta: { architecture: "rdn", patchSize: 128, ... }
> ```
> и в общем коде:
> ```js
> if (architecture === 'rdn') { return { ..., inputRange: [0, 255] } }
> // иначе inputRange: [0, 1]
> ```
>
> Полчаса на чтение чужого пакета здесь экономят день отладки. Про диапазон
> входа — отдельный разговор ниже, это оказалось главной ловушкой этапа.

### Шаг 2. Выбор бэкенда

```ts
async function selectBackend(request: MlInitRequest): Promise<string> {
  if (request.preferWebgpu) {
    try {
      await tf.setBackend('webgpu')
      await tf.ready()
      if (tf.getBackend() === 'webgpu') return 'webgpu'
    } catch { /* ниже отработает WASM */ }
  }
  setWasmPaths(request.wasmBaseUrl)
  await tf.setBackend('wasm')
  await tf.ready()
  return tf.getBackend()
}
```

> **Почему проверка `tf.getBackend() === 'webgpu'` после `setBackend`**
>
> `setBackend` возвращает `false` вместо исключения, если бэкенд не поднялся,
> а `await tf.ready()` при этом спокойно завершится — просто активным останется
> другой бэкенд. Проверять надо результат, а не отсутствие ошибки.

> **Почему `setWasmPaths` обязателен и обязательно ДО `setBackend('wasm')`**
>
> Бэкенд скачивает `.wasm` при инициализации и по умолчанию ищет его рядом
> с собой — то есть по blob-URL, где ничего нет. Симптом при пропуске:
> ошибка загрузки файла с бессмысленным путём вида `blob:https://.../....wasm`.

> **Почему падение WebGPU не показывается пользователю**
>
> Для него это разница в скорости, а не в работе: результат он получит в любом
> случае. Сообщение «WebGPU недоступен» ничего ему не даёт и требует действий,
> которых он предпринять не может.

### Шаг 3. Прогрев

```ts
async function warmUp(loaded: LayersModel): Promise<void> {
  const probe = tf.zeros([1, WARMUP_SIZE, WARMUP_SIZE, 3])
  const output = loaded.predict(probe) as tf.Tensor
  output.dataSync()
  probe.dispose()
  output.dispose()
}
```

> **Зачем гонять модель на пустом входе**
>
> Первый инференс всегда дороже остальных: бэкенд компилирует шейдеры (WebGPU)
> или инстанцирует модуль WebAssembly, и делает это **лениво**, при первом вызове
> каждого ядра. Без прогрева эта плата легла бы на первую настоящую картинку
> пользователя и выглядела бы как «первый раз почему-то тормозит».
>
> 16×16 достаточно: нужны сами ядра, а не осмысленный результат.

> **Почему `dataSync()`, а не просто `predict()`**
>
> На GPU-бэкенде `predict` только ставит работу в очередь. Без чтения результата
> прогрев вернулся бы раньше, чем что-либо посчиталось, и не прогрел бы ничего.
> `dataSync()` дожидается фактического выполнения.

### Шаг 4. Диапазон входа — главная ловушка этапа

```ts
const pixels = tf.browser.fromPixels(tile)
const batched = tf.expandDims(tf.cast(pixels, 'float32'), 0)   // 0..255, БЕЗ деления
const predicted = model.predict(batched) as tf.Tensor
const clipped = tf.clipByValue(tf.squeeze(predicted, [0]), 0, 255)
return tf.div(clipped, 255)   // toPixels ждёт 0..1
```

> **Почему 0..255, хотя «нормализовать вход» — общее правило**
>
> Потому что так обучена именно эта модель. Общего правила нет: у ESRGAN
> в том же пакете диапазон 0..1, у RDN — 0..255. Единственный источник истины —
> описание модели, и оно есть в исходниках пакета.

> **Почему эта ошибка не ловится «на глаз» — и чем она опасна**
>
> Сначала было написано деление на 255. Проверка казалась убедительной:
> средний цвет входа `[169, 121, 109]`, средний цвет выхода `[169, 121, 108]` —
> разница в один пункт, картинка на вид нормальная, размер удвоился. Вывод
> «работает» был неверным.
>
> Причина в глобальном residual из теории: итог = увеличенный вход + поправка сети.
> Если вход занижен в 255 раз, поправка вычисляется на почти нулевых значениях
> и выходит близкой к нулю. Остаётся **просто растянутая картинка** — та самая,
> которую мы уже умеем делать без всякой нейросети.
>
> То есть неверная нормализация не ломает результат, а **тихо выключает модель**.
> Расширение считает 800 КБ весов, тратит время на GPU и выдаёт то же, что дал бы
> `drawImage`.
>
> **Проверка, которая это ловит:** сравнить резкость результата с обычным
> билинейным растяжением того же изображения. Рабочая модель обязана быть резче.
> Мера — средний модуль лапласиана по яркости:
>
> ```js
> lap = 4*L(x,y) - L(x-1,y) - L(x+1,y) - L(x,y-1) - L(x,y+1)
> sharpness = среднее |lap|
> ```
>
> После исправления: 3.61 у билинейного против 4.37 у ML, то есть +21%.
> До исправления результат совпадал бы с билинейным.
>
> **Общий урок:** проверка «выход похож на вход» не проверяет ничего. Проверять
> надо то свойство, ради которого всё затевалось.

### Шаг 5. Плитки

```ts
for (let y = 0; y < height; y += TILE_SIZE) {
  for (let x = 0; x < width; x += TILE_SIZE) {
    const tileWidth = Math.min(TILE_SIZE, width - x)
    const tileHeight = Math.min(TILE_SIZE, height - y)

    const padLeft = Math.min(TILE_OVERLAP, x)
    const padTop = Math.min(TILE_OVERLAP, y)
    const padRight = Math.min(TILE_OVERLAP, width - (x + tileWidth))
    const padBottom = Math.min(TILE_OVERLAP, height - (y + tileHeight))

    const tile = sourceContext.getImageData(x - padLeft, y - padTop, /* ... */)
    const resultPixels = await inferTile(tile)

    outContext.putImageData(
      resultData,
      (x - padLeft) * ML_SCALE, (y - padTop) * ML_SCALE,   // куда класть весь блок
      padLeft * ML_SCALE, padTop * ML_SCALE,               // откуда брать
      tileWidth * ML_SCALE, tileHeight * ML_SCALE,         // сколько брать
    )
  }
}
```

> **Почему плитки вообще понадобились — это не оптимизация**
>
> Без них инференс на входе 960×720 падает с ошибкой
> `Dispatch size exceeds WebGPU limits in Y or Z dimension`: размер вычислительной
> сетки упирается в лимит устройства. При 640×480 работал. То есть без плиток
> ML работал бы только на миниатюрах.
>
> Заодно решается вторая задача: расход памяти перестаёт зависеть от размера
> картинки.

> **Откуда `TILE_SIZE = 224`**
>
> С полями получается вход не больше 272×272 (74 тыс. пикселей), а падать WebGPU
> начинал при 691 тыс. Запас шестикратный — на видеокарты со более строгими лимитами.
>
> Меньше делать невыгодно: у каждого вызова модели есть постоянные накладные
> расходы, и на WebGPU они больше самих вычислений. Замер: 120 тыс. пикселей —
> 164 мс, 307 тыс. — 189 мс. Объём вырос в 2.5 раза, время — на 15%.

> **Откуда `TILE_OVERLAP = 24`**
>
> Из рецептивного поля сети, посчитанного по `model.json`:
> восемь свёрток 3×3 (по 1 пикселю каждая) плюс одна 5×5 (2 пикселя) —
> итого около 10 пикселей. Свёртки 1×1 не расширяют. Взято 24 — двойной запас.
>
> Проверять надо не расчётом, а замером (см. раздел «Проверка»): если полей
> хватает, результат с плитками совпадает с результатом без них.

> **Как работает `putImageData` с шестью аргументами**
>
> Первые два — куда класть блок целиком, следующие четыре — прямоугольник
> внутри блока, который реально записывается. Итоговая позиция —
> сумма смещения и координат прямоугольника.
>
> Это и есть механизм «посчитали с полями, положили без полей». Альтернатива —
> резать пиксельный массив вручную — то же самое, но в десять строк.

### Шаг 6. Отдельная сборка и ленивая загрузка

ML-воркер собирается **третьей** конфигурацией (`vite.mlworker.config.ts`)
в отдельный файл `dist/ml-worker.js`, а не встраивается в `content.js`.

> **Почему не `?worker&inline`, как на этапе 4**
>
> Вместе с TensorFlow.js и двумя бэкендами это 817 КБ. Встроенный в `content.js`,
> он попадал бы в **каждую открытую страницу** — включая те, где пользователь
> ничего не улучшает. Расширение, которое добавляет почти мегабайт к загрузке
> каждой вкладки, никуда не годится.
>
> Отдельный файл загружается лениво, при первом обращении к ML. `content.js`
> остался 29 КБ.

Загрузка — тем же приёмом с blob-URL, что и на этапе 4:

```ts
const response = await fetch(chrome.runtime.getURL(WORKER_PATH))
const source = await response.text()
const blobUrl = URL.createObjectURL(new Blob([source], { type: 'text/javascript' }))
try {
  return new Worker(blobUrl)
} finally {
  URL.revokeObjectURL(blobUrl)
}
```

> **Почему `revokeObjectURL` в `finally`, сразу после создания**
>
> Воркер к этому моменту уже прочитал код. Ссылка держала бы 817 КБ в памяти
> до закрытия страницы — впустую.

> **Почему воркер один, а не пул, как на этапе 4**
>
> Он держит в памяти загруженную модель и буферы бэкенда. Второй экземпляр
> удвоил бы расход, не ускорив ничего: и WebGPU, и WASM упираются в одно
> и то же железо, а не в число потоков JavaScript.

### Шаг 7. Что положить в пакет расширения

```js
// scripts/copy-assets.mjs — запускается перед сборкой
await cp(modelSource, modelTarget, { recursive: true })   // model.json + веса
for (const name of wasmFiles) await cp(...)               // три .wasm
```

> **Почему копируем при сборке, а не коммитим в репозиторий**
>
> Это чужие артефакты, у них есть версия в `package.json`. Вторая копия в истории
> git однажды разойдётся с версией пакета, и никто не заметит.
>
> `public/models/` и `public/wasm/` добавлены в `.gitignore`.

> **Почему модель лежит в пакете, а не скачивается при первом использовании**
>
> Требование проекта: картинки пользователя не покидают машину. Самый надёжный
> способ это гарантировать — не иметь сетевых запросов в момент работы вообще.
> Разовая загрузка при установке расширения этому не противоречит, а загрузка
> в момент обработки картинки — уже спорно.
>
> Цена: пакет расширения вырос до 2.9 МБ.

> **Почему `.wasm` три штуки**
>
> Базовый, с SIMD и с SIMD+потоками. Бэкенд выбирает нужный в рантайме
> по возможностям браузера; заранее знать, какой понадобится, нельзя.

### Шаг 8. Манифест

```json
"content_security_policy": {
  "extension_pages": "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'"
},
"web_accessible_resources": [
  { "resources": ["ml-worker.js", "models/*", "wasm/*"], "matches": ["http://*/*", "https://*/*"] }
]
```

> **Зачем `wasm-unsafe-eval`**
>
> По умолчанию CSP расширений запрещает компиляцию WebAssembly — она подпадает
> под те же правила, что `eval`. Токен `'wasm-unsafe-eval'` разрешает именно
> WebAssembly, не открывая `eval` целиком. Без него WASM-бэкенд не запустится
> на страницах расширения.

> **Зачем `web_accessible_resources`**
>
> Воркер создаётся из blob-URL с источником страницы. Чтобы страница могла
> скачать `ml-worker.js`, модель и `.wasm`, они должны быть объявлены доступными.
> Это не дыра в безопасности: там нет ни данных пользователя, ни ключей —
> только код и веса, которые и так лежат в открытом npm-пакете.

> **Открытый вопрос, который надо знать**
>
> Компиляция WebAssembly в blob-воркере подчиняется CSP **страницы**, а не
> расширения. На сайтах со строгим `script-src` без `wasm-unsafe-eval`
> запасной путь может оказаться недоступен. WebGPU при этом работать должен —
> он не использует WebAssembly.
>
> Радикальное решение — перенести инференс в offscreen-документ, где действует
> наш собственный CSP. Но туда не доставить пиксели (разобрано на этапе 4),
> и вопрос остаётся открытым.

## Проверка

### Как проверять модель, чтобы проверка что-то значила

Это главный урок этапа. Первая проверка выглядела разумной и была бесполезной.

**Бесполезная проверка:** сравнить средний цвет входа и выхода.
Результат: `[169,121,109]` → `[169,121,108]`. Вывод «работает» — неверный.
Такой результат даст и модель с **неправильной нормализацией**, потому что она
вырождается в обычное растяжение, а растяжение средний цвет сохраняет.

**Правильная проверка:** сравнить с тем, что мы умели раньше. ML-результат обязан
быть резче билинейного растяжения того же изображения.

| | Резкость (средний модуль лапласиана) |
|---|---|
| Билинейное растяжение | 3.61 |
| ML | **4.37** (+21%) |

Средняя абсолютная разница между ML и билинейным — 3.23 пункта из 255,
то есть модель действительно меняет картинку, а не повторяет её.

### Проверка отсутствия швов — и как её случайно провалить

Мера: средняя абсолютная разница между соседними столбцами пикселей. Шов
проявится как локальный всплеск ровно на границе плитки (при `TILE_SIZE = 224`
это выходные координаты 448, 896, ...).

**Первый замер показал шов** — 5.5 и 11.8 при медиане 1.1, то есть в 5–11 раз выше.
Профиль выглядел убедительно: узкий пик ровно на границе.

**Замер был неверен.** Тестовая картинка содержала шахматный узор с периодом
8 пикселей, а сторона плитки 224 кратна 8 — все границы плиток пришлись ровно
на края клеток. Измерялась сама картинка, а не шов.

Повтор на гладком градиенте без периодических структур:

| Позиция | Разница | Отношение к медиане |
|---|---|---|
| Граница плиток x=448 | 0.231 | **0.91** |
| Граница плиток x=896 | 0.471 | **1.85** |
| Контрольная точка x=600 | 0.254 | 1.00 |

Швов нет: на границе плиток разница не отличается от фона. Поля в 24 px достаточны.

> **Урок:** синтетическая тестовая картинка не должна содержать периодических
> структур с периодом, кратным проверяемому шагу. Иначе измеряется сетка, а не дефект.

### Замеры производительности

Вход → выход, время инференса (машина: 20 логических ядер, работающий WebGPU):

| Вход | WebGPU | WASM |
|---|---|---|
| 180×140 | 100 мс | 285 мс |
| 400×300 | 98 мс | 1304 мс |
| 960×720 | 345 мс | — |
| 1200×900 | 496 мс | — |

Загрузка модели: 334 мс на WebGPU (включая компиляцию шейдеров при прогреве),
25 мс на WASM.

Отсюда потолки размера входа: 4 Мп для WebGPU, 250 тыс. пикселей для WASM
(≈2.8 с при 11 мкс на пиксель). Крупнее — классический апскейл.

### Проверка в браузере

```bash
npm run dev
```

1. **Возможности устройства.** Открыть popup. Строка «WebGPU» должна показывать
   производителя адаптера (или «нет»), «WASM SIMD» — «есть» на любом современном Chrome.

2. **Первая ML-обработка.** Навести на картинку размером примерно 300–600 px
   и нажать «Улучшить». В консоли страницы:
   ```
   [ImageEnhancer:ml] ML готов: бэкенд webgpu, загрузка 334 мс
   [ImageEnhancer:enhance] Готово за N мс (ml-webgpu, воркер): ...
   ```
   Первая обработка дольше остальных — грузится модель.

3. **Вторая обработка** той же или другой картинки должна пройти заметно быстрее:
   модель уже в памяти.

4. **Большая картинка.** Взять изображение крупнее 4 Мп (или крупнее 250 тыс.
   пикселей, если WebGPU недоступен). В логе backend должен быть `canvas-lanczos` —
   сработал потолок, и это правильное поведение, а не сбой.

5. **Качество.** Сравнить результат на мелкой картинке с результатом этапа 2.
   ML должен давать более чёткие края и меньше «мыла». На фотографиях разница
   заметна, на скриншотах и тексте — может быть спорной.

6. **Сеть.** Открыть DevTools → Network, обработать картинку. Запросов к внешним
   доменам быть **не должно**: только `chrome-extension://` за воркером, моделью
   и `.wasm`.

7. **Память.** В Task Manager Chrome (`Shift+Esc`) расход вкладки после первой
   ML-обработки вырастет на десятки мегабайт и останется — модель живёт в памяти
   воркера до закрытия страницы.

## Возможные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `Unknown layer: X` при загрузке | Модель использует кастомный слой | Зарегистрировать через `tf.serialization.registerClass` до загрузки. Список слоёв виден в `model.json` |
| Модель не загружается, ошибка про формат | Перепутаны `loadLayersModel` и `loadGraphModel` | Смотреть поле `format` в `model.json` |
| Ошибка загрузки `.wasm` с путём вида `blob:https://...` | Не вызван `setWasmPaths` до `setBackend('wasm')` | Задать базовый URL явно |
| Результат ML не отличается от обычного растяжения | Неверный диапазон входа: модель ждёт 0..255, а получила 0..1 | Проверить `inputRange` в исходниках пакета. Проверять резкостью, а не средним цветом |
| Картинка на выходе чёрная или цветной шум | Диапазон перепутан в другую сторону либо не сделан `clipByValue` | Привести к диапазону модели, обрезать выход |
| `Dispatch size exceeds WebGPU limits` | Слишком большой вход для WebGPU-бэкенда | Обрабатывать плитками |
| Видимая сетка на результате | Поля плиток меньше рецептивного поля сети | Увеличить `TILE_OVERLAP`; проверять на изображении без периодических структур |
| Замер швов показывает шов, которого не видно глазом | Период тестовой картинки кратен шагу плиток | Мерить на гладком градиенте |
| Первая обработка очень долгая, последующие быстрые | Ленивая компиляция ядер бэкенда | Ожидаемо; прогрев уменьшает, но не убирает |
| Память вкладки растёт с каждой картинкой | Тензоры не освобождаются | `tf.tidy` вокруг вычислений, `dispose()` для того, что из него вышло |
| `tensor.div is not a function` | Цепочечные методы не входят в `tfjs-core` | Функциональный API: `tf.div(x, y)` |
| WASM не запускается на конкретном сайте | CSP страницы запрещает компиляцию WebAssembly | Известное ограничение; WebGPU должен работать, классический апскейл работает всегда |
| `npm install` падает с `ECONNRESET` | Пакеты TF.js крупные, соединение обрывается | Увеличить `fetch-retries`, ставить по одному пакету |
| ML не включается никогда | Картинка больше потолка бэкенда либо запрошен коэффициент не около 2 | Ожидаемо; смотреть `backend` в логе |

### Что появилось в архитектуре

| Модуль | Роль |
|---|---|
| `src/workers/ml.worker.ts` | Инференс: бэкенд, модель, прогрев, плитки |

| `scripts/copy-assets.mjs` | Модель и `.wasm` из `node_modules` в пакет |
| `src/core/device/` | Переписан: реальная проверка адаптера и SIMD |

Интерфейс `ImageEnhancer` из этапа 0 получил второй бэкенд (`ml-webgpu` / `ml-wasm`)
без изменения контракта — выбор реализации остался в одной точке.

### Новые API

`tf.loadLayersModel`, `tf.setBackend` / `tf.ready` / `tf.getBackend`, `setWasmPaths`,
`tf.tidy`, `tf.browser.fromPixels` / `toPixels`, `navigator.gpu.requestAdapter`,
`WebAssembly.validate`, `putImageData` с прямоугольником.

### Новые разрешения и послабления

- `content_security_policy.extension_pages` с `'wasm-unsafe-eval'`
- `web_accessible_resources` для `ml-worker.js`, `models/*`, `wasm/*`

### Размер пакета

2.9 МБ, из них 2.8 МБ — модель, `.wasm` и код TensorFlow.js. Ключевая цифра другая:
`content.js`, который внедряется в каждую открытую страницу, остался **29 КБ**.

### Что заложено под видео

Ничего нового, но ML-путь для видео пришлось бы строить иначе: загружать модель
один раз и гонять через неё кадры потоком. Единственный экземпляр воркера
с живущей в памяти моделью — как раз такая заготовка.

### Что будет дальше

**Этап 6 — уровни качества и настройки.** Сейчас выбор между ML и классикой
делает автоматика по размеру картинки и доступности бэкенда, а уровень качества
зафиксирован. Пользователь должен получить явный выбор «быстро / сбалансировано /
качественно», сохранение в `chrome.storage` и автоматическое понижение уровня
на слабом железе — для чего детекция из `core/device/` наконец начнёт использоваться
по назначению.
