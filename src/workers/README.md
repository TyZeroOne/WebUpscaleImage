# `src/workers/`

Web Worker'ы: сюда вынесены все тяжёлые вычисления.

| Файл | Появился | Что делает |
|---|---|---|
| `enhance.worker.ts` | этап 4 | Улучшение одного изображения. Принимает `ImageBitmap`, возвращает `Blob` |

Воркером управляет пул из `src/content/worker-pool.ts`; точка входа для остального
кода — `src/content/enhance-runner.ts`.

## Поправка к прогнозу этапа 0

В первой версии этого файла было записано ожидание, что воркеры потребуют
offscreen-документа и отдельного `tsconfig`. На практике не понадобилось ни то,
ни другое — и причины стоит знать.

**Offscreen-документ не нужен.** Он был бы обязателен, если бы вычисления запускались
из service worker'а. Но данные между content script и service worker ходят через
`chrome.runtime.sendMessage`, а он сериализует сообщение в JSON: ни `ImageBitmap`,
ни `Blob`, ни `ArrayBuffer` через него не проходят. Значит, пиксели всё равно
пришлось бы либо скачивать заново уже в offscreen-документе (лишняя загрузка
и другой набор доступных картинок), либо гнать строкой base64 (сотня мегабайт
на крупную картинку). Проще оставить пиксели там, где они получены, — в content
script — и создать воркер оттуда.

**Отдельная точка входа в конфигурации Vite не нужна.** Суффикс `?worker&inline`
делает всё сам: Vite собирает воркер отдельным графом и встраивает его код в бандл
строкой, из которой воркер создаётся через blob-URL. Это же обходит ограничение,
из-за которого content script не может создать воркер из файла расширения
(`new Worker(chrome.runtime.getURL(...))` падает — конструктор требует тот же
источник, а content script для этой проверки относится к источнику страницы).

**Отдельный `tsconfig` пока не нужен.** Библиотеки типов `WebWorker` и `DOM`
действительно конфликтуют в пределах одного `tsconfig`, но воркеру из всей области
видимости нужны три метода — они описаны локальным интерфейсом прямо в файле.
Заводить второй `tsconfig` и вторую команду проверки типов ради одного небольшого
файла дороже. Когда воркер вырастет (этап 5, ML-инференс), решение стоит пересмотреть.

## Что здесь появится дальше

Этап 5 добавит ML-инференс: ONNX Runtime Web с WebGPU и фоллбеком на WASM.
Скорее всего, отдельным воркером — у инференса другой жизненный цикл
(модель загружается один раз и живёт между задачами), и смешивать его
с одноразовыми задачами классического апскейла не стоит.
